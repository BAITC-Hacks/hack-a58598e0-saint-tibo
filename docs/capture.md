Страница `/capture` находится под существующей проверкой входа `_app`.
`MeetingCapture` (`frontend/src/shared/ui/meeting-capture`) можно вставить в экран

в `frontend/messages/{ru,kk,en}.json` (35 ключей).

## Что работает

Микрофон, аудиотрек выбранной пользователем вкладки/системы или их смесь.
Стандартный `getDisplayMedia` вызывается из клика до других асинхронных разрешений.
Без возвращённого аудиотрека захват отклоняется, даже если микрофон доступен.
Видео требуется браузеру для выбора источника, но в MediaRecorder передаётся
только аудиовыход Web Audio. Названия реально полученных треков показаны локально,
в логи они не отправляются. Перед стартом пользователь подтверждает разрешение
и уведомление участников о записи и возможной локальной/self-hosted транскрибации.
ИИ сейчас не запускается, внешние STT/API не используются.

Каждый источник имеет индикатор уровня; более 3 секунд без сигнала или `muted`
показывают предупреждение. Таймер основан на `performance.now`, не числе chunks.
Stop дожидается последнего `dataavailable`, затем собирает локальный Blob.
Отказ доступа, отсутствие аудио, завершение источника, ошибка MediaRecorder и
приостановка AudioContext обработаны. Потеря выбранного источника завершает всю
смесь как неполную запись. Все исходные треки, включая видео выбора источника,
останавливаются; AudioContext закрывается; blob URL освобождается при удалении
результата и unmount. Позднее разрешение после отмены не оставляет активный трек.

Результат можно прослушать нативным audio и скачать. Ошибка декодирования видна:
неполный контейнер не объявляется воспроизводимым только по наличию Blob.
При уходе со страницы запись теряется; это указано в UI, на закрытие/обновление
вкладки установлен `beforeunload`. Переход внутри SPA также уничтожает запись.

Буфер: до 64 MiB, 4096 частей, 30 минут (строже серверных лимитов).
Остановка начинается при 56 MiB / 4095 частях, оставляя место последнему событию.
Каждая принятая часть не больше 8 MiB. Превышение или слишком большой Blob
останавливает захват как неполный; сохраняется только непрерывный префикс,
после отброшенной части ничего не добавляется. Внутренние буферы самого браузера
не контролируются приложением: `timeslice` может задерживаться при блокировке
экрана/фоновой вкладке, поэтому нельзя обещать жёсткий предел памяти всего процесса.
Не перезапускаем MediaRecorder в середине одной записи.

## Контракт интеграции #8/#9 и плеера #19

`AudioCapture` в `frontend/src/shared/lib/audio-capture.ts` публикует
`CaptureState`; после stop его `result` содержит Blob, неизменяемые chunks и
`is_complete`. `sequence` начинается с 0; `start_ms/end_ms` — целочисленные оценки
от начала записи; MIME одинаков у всех частей. Это фрагменты одного контейнера,
не независимые файлы. Временная шкала playback определяется декодером сервера.

`uploadCapture(result, {putChunk, finalize}, signal)` — рабочая последовательная
передача сохранённого результата через переданные callbacks; HTTP-адаптер и
вызов из UI отсутствуют до появления опубликованного SDK. Это **не live upload**.
После появления #9:

1. Создать запись через generated SDK с `source: live`, сохранить recording_id.
2. Привязать callbacks к этому ID и authenticated SDK; `putChunk` передаёт raw
   Blob, MIME, sequence и интервалы точно как получены. Адаптер должен бросать
   `{status}` при HTTP-ошибках, а не возвращать успешный Promise для error response.
3. Повторяются только network/408/429/5xx, максимум 3 попытки с паузами 0.5/1 s.
   401/403/409/413/415/422 не повторяются. AbortSignal передаётся в SDK.
   Повтор после исчерпания попыток использует тот же recording_id/result:
   sequence, Blob и метаданные не пересоздаются. Сохранённый буфер ограничен.
4. Finalize вызывается только после подтверждения всех частей с
   `{expected_chunks, is_complete}`. При обрыве отправки finalize не вызывается:
   ошибка остаётся у вызывающего кода, сервер применяет receiving timeout.
5. Не показывать ready по локальному stop. Показать серверный RecordingRead;
   только его проверенный `media_url` передавать MeetingPlayer.

Для локального preview в #19 можно создать object URL из `result.blob` и передать
`{id, url, title}`. Владелец URL освобождает его после отключения плеера.
Не подменять им серверный recording_id и не обещать серверный Range.

## Браузеры и ручная приёмка

Используются runtime-проверки secure context, getUserMedia/getDisplayMedia,
AudioContext и MediaRecorder MIME: WebM/Opus → Ogg/Opus → MP4.
Доступность звука определяется **реальными возвращёнными треками**.

| Среда | Что подтверждено / что ещё проверить |
| --- | --- |
| Chrome на macOS, изолированный headless стенд | Синтетический микрофон, настоящий MediaRecorder WebM/Opus и локальное воспроизведение |
| Chrome/Edge, выбор вкладки/системы на целевой ОС | Ручной picker и его переключатель аудио требуют проверки на машине демонстрации |
| Safari / Firefox / мобильные браузеры | Ручная проверка разрешений, MIME и реально доступных аудиотреков ещё не выполнена; системный звук не гарантируется |

Ограничения API: [MDN getDisplayMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getDisplayMedia),
[Chrome screen sharing controls](https://developer.chrome.com/docs/web-platform/screen-sharing-controls).
`audio: true` и `systemAudio: include` не гарантируют аудиотрек; HTTPS/localhost
и непосредственное действие пользователя обязательны. Нельзя захватить чужую
встречу без предоставленного пользователем аудиотрека.
[MDN dataavailable](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/dataavailable_event)
описывает задержки timeslice; сервер объединяет части перед декодированием.

Перед закрытием #21 нужны: реальный picker и отказ доступа на целевых ОС,
обрыв источника/сети при подключённом #9, duplicate/reordered/missing chunks на
настоящем backend, воспроизводимый media_url в #19 и live-проверка родителем.
Этот локальный срез не закрывает acceptance #21.

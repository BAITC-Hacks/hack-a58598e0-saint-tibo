# Ручная проверка и экспорт результата (#13/#14)

Этот срез сохраняет **введённые человеком** саммари и поручения поверх существующей
версии транскрипта #11. Автоматическое извлечение #69 и диаризация #12 сюда не входят.
`completed_stage` остаётся `transcribe`, даже когда человек подтвердил протокол.
Наличие API не означает приёмку качества локальной модели или live-проверку deployment.

## Реальные операции

Общий путь `R = /api/v1/meetings/{meeting_id}/recordings/{recording_id}/results/{result_version_id}`.
Идентификаторы выбираются из существующих meeting/recording/results API, не из mock.

| Метод и путь | operationId | Назначение |
| --- | --- | --- |
| `GET R/review` | `getResultReview` | Последняя ревизия ручной проверки |
| `GET R/review?revision=N` | `getResultReview` | Конкретный сохранённый снимок |
| `PATCH R/review` | `updateResultReview` | Правки с обязательной текущей `revision` |
| `GET R/export?format=pdf\|docx&revision=N` | `exportReviewedResult` | Скачать выбранный проверенный снимок |

Все операции требуют JWT существующей Better Auth сессии. Чтение/экспорт используют
`meeting:read`, PATCH — `meeting:write`; SQL проверяет владельца совещания и всю цепочку
meeting → recording → result. Чужой объект, включая запрос от чужого admin, даёт 404.
Неавторизованный запрос — 401. Экспорт возвращает attachment, правильный Content-Type,
`Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`.

## Форма и сохранение

`GET` возвращает `source:"persisted"`, `result_version_id`, `recording_id`, `revision`,
`reviewed`, `is_incomplete`, `saved_at`, `meeting`, `participants`, `action_items`, `summary`.
Начальная STT-версия имеет revision=1, reviewed=false, saved_at=null и пустые ручные
поля. Это не сгенерированное саммари. После первого PATCH revision=2. Последующие
сохранения увеличивают revision на единицу; `ResultVersion.status` отражает последнюю.

PATCH меняет только переданные поля. `action_items` заменяется целиком; `summary`
заменяется целиком. Для удаления содержимого передайте `[]` / `{}`. Явный null в этих
полях или `reviewed` отклоняется. Одной `revision` без правок недостаточно.
Изменение action_items/summary снимает проверку, если `reviewed:true` не передан явно.
Подтвердить уже сохранённый черновик можно через `{revision:N, reviewed:true}`.

```json
{
  "revision": 1,
  "reviewed": true,
  "summary": {
    "topics": ["Синтетическая тема"],
    "decisions": [],
    "open_questions": [],
    "source_segment_ids": []
  },
  "action_items": [{
    "text": "Введённое человеком поручение",
    "assignee_participant_id": null,
    "assignee_text": null,
    "due_text": "после согласования",
    "due_date": null,
    "status": "open",
    "source_segment_ids": []
  }]
}
```

Каждый action item получает `id` (можно передать свой UUID; при редактировании сохраняйте
его). Ответ дополнительно содержит `result_version_id`; в PATCH это поле не передаётся.
Статусы: `open | in_progress | done | cancelled`. Дубликаты ID в одном снимке запрещены.
Исполнитель — участник этого совещания, независимо от speaker_id исходной реплики.
`assignee_text` и оба поля срока nullable. Сервер **не вычисляет** даты или исполнителя;
переданную человеком ISO дату хранит вместе с исходной формулировкой. Событие или
неизвестный срок остаётся `due_date:null`, пропущенные сведения не дополняются.

Все `source_segment_ids` в поручениях и summary проверяются по выбранным result_version_id
**и** recording_id. Summary хранит общую подборку источников для трёх списков строк;
отдельные ссылки для каждого тезиса пока не представлены. Пустые ссылки допустимы для
ручных заметок и не означают, что модель нашла доказательство. Повторяющиеся поручения
человек объединяет сам; автоматическая дедупликация/извлечение остаются в #69/#13.

Лимиты: до 200 поручений; текст до 2000 символов, исполнитель/исходный срок до 500;
до 100 строк в каждой части summary; до 100 источников на объект. Пустой/пробельный
текст и недопустимые для XML управляющие символы отклоняются. Снимок с метаданными
ограничен 512 KiB. Значения/транскрипты не пишутся в журнал; только ID, ревизия, формат.

## Конкуренция и история

Миграция `0005` добавляет `app.result_reviews` с PK `(result_version_id, revision)` и
JSONB payload. Транзакция блокирует meeting → recording → result и участников,
проверяет revision, атомарно добавляет снимок и обновляет версию. Два PATCH одной
revision дают один успех и один `409 version_conflict`; UI перечитывает данные и
предлагает пользователю согласовать изменения, не повторяет PATCH вслепую.

Снимок содержит также название/дату/часовой пояс совещания и список участников.
Он неизменяем для API: переименование/удаление участника или изменение совещания
**не меняют** старый протокол. При новом сохранении берутся актуальные метаданные;
ссылку на удалённого исполнителя нужно очистить или заменить. ID участника внутри
исторического снимка — историческая ссылка, а не действующее право доступа/FK.
Старые snapshots не обнуляются при удалении участника. Удаление meeting/recording/result
каскадно удаляет snapshots; после удаления экспорт недоступен.

История сохраняется начиная с первой ручной ревизии (2). Исходная revision=1 доступна
как текущий draft до первого сохранения, но не архивируется. Новая обработка создаёт
другой result_version_id и не перезаписывает эти правки. Поручения пока находятся в
JSONB снимке: для запросов напоминаний #15 понадобится отдельная проекция/нормализация.

## Экспорт и адаптер #85

Экспорт требует **явную** revision. Только сохранённый снимок с reviewed=true даёт файл;
черновик — `409 result_not_reviewed`, отсутствующая ревизия — 404. Старый проверенный
снимок остаётся доступен, когда последняя ревизия снова draft. Данные берутся только
из снимка, а не из актуальных названий/участников. Совпадает содержание; время создания
файла и ZIP/PDF метаданные могут отличаться между скачиваниями.

PDF встраивает vendored DejaVu Sans; DOCX задаёт DejaVu Sans, использует возможности
шрифтов/подстановки редактора и не встраивает TTF. Проверены RU/KK символы ӘҒҚҢӨҰҮҺІ
в PDF и после открытия DOCX в LibreOffice. Оба формата используют A4, повторяемую
шапку таблицы, перенос строк/страниц, оригинальную фразу срока рядом с датой.
Неполный источник явно помечен. Заголовки существующего renderer остаются на русском.

Для Артёма: draft mock `/meetings/{id}/review` и `/meetings/{id}/export` не добавлены.
Адаптер выбирает recording/result; speakers пока отсутствуют, segments читаются через
существующий пагинированный `GET R/segments`. Review GET не возвращает speakers/segments.
Для PATCH прочитанных поручений уберите только `result_version_id`, сохраните `id`.
Клиент генерируется из OpenAPI; вручную generated-файлы не правятся.

```ts
const result = await exportReviewedResult({
  client: backendClient,
  path: { meeting_id, recording_id, result_version_id },
  query: { format: "pdf", revision },
  parseAs: "blob",
  throwOnError: true,
});
// result.data — Blob; скачать через временный URL.createObjectURL и затем revokeObjectURL.
```

Это authenticated fetch, не обычная ссылка `<a href>` без JWT и не токен в URL.
Download filename можно построить по result_version_id/revision/format, как в API.

## Проверка и оставшаяся приёмка

Локально: wheel/sdist; новая миграция на отдельном PostgreSQL; HTTP-сценарий FastAPI с
реальной БД и подменой **только identity** синтетическими пользователями. Проверены
save/reload, гонка 200/409, invalid assignee/source 422, чужой admin 404, draft export 409,
снятие approval, snapshots после rename/delete metadata, независимая STT-версия,
PDF/DOCX, большие таблицы и каскадное удаление. Suites/линтеры не запускались.
Визуально открыты PDF и DOCX→PDF в LibreOffice, включая вторую страницу длинной таблицы.

После согласованного deployment независимый аудитор повторяет через настоящий dev-login
и JWT: создать собственное синтетическое совещание/участников/запись; получить STT result
или явно маркированный синтетический result; сохранить ручной review с неизвестным и
событийным сроком; перечитать; stale PATCH → 409; скачать оба формата; чужой admin → 404,
без токена → 401; удалить только свои данные. Проверить точный SHA и журналы без текста.
Synthetic result не доказывает качество STT/LLM. #13 требует отдельной приёмки extraction,
#14 — независимой live-проверки. Merge/deploy и закрытие issues принадлежат координатору.

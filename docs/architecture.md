# Архитектура

## Реализованная основа

Браузер → TanStack Start / Better Auth → PostgreSQL `auth`.
Браузер получает короткоживущий JWT через cookie-сессию и обращается к FastAPI.
API проверяет подпись, issuer/audience, действующую сессию и права из базы.
Прикладные данные принадлежат схеме `app`.

UI: `frontend/src/app` собирает маршруты, `pages` содержит страницы,
`shared` — общие части. FastAPI хранит инфраструктуру в `auth`, `core`, `db`,
HTTP-маршруты в `api`, домены в `modules`. Контракт генерируется из Python;
TypeScript-клиент не редактируется вручную.

В основе нет обработки совещаний, очереди, моделей, объектного хранилища
и серверного deployment. Они добавляются по мере реализации сценария.

## Планируемая обработка

```text
Пользователь → совещание, уведомление участников, запись, дата/часовой пояс
  → проверка файла → фоновое задание
  → декодирование → self-hosted STT и диаризация
  → реплики с таймкодами → подтверждение имён
  → self-hosted извлечение поручений и саммари
  → проверка и правка пользователем → экспорт протокола
```

Тяжёлое распознавание выполняется в отдельном процессе/окружении.
HTTP-запрос не удерживается на время обработки. В PostgreSQL сохраняются
этап и ошибка задания; повторный запрос не создаёт дубликаты.
Доступ к записи и результату проверяется по владельцу на сервере.

| Домен | Ответственность |
| --- | --- |
| `meetings` | Название, дата/часовой пояс, владелец, участники, метаданные файла |
| `processing` | Задание, этапы, ошибки, реплики, speaker id, таймкоды |
| `action_items` | Суть, ответственный, исходный/нормализованный срок, статус, источник |
| `exports` | Протокол из сохранённой версии результата, PDF/DOCX |

Извлечённое поручение связано с репликой; исправления пользователя
не теряются при повторной обработке. Выбор моделей проверяется на кейсе
и доступном CPU/GPU до фиксации зависимостей. Облачный fallback запрещён.

1. Совещание и безопасная загрузка: лимиты, тип, владение, дата/часовой пояс,
   UI RU/KK/EN и состояние фонового задания.

   соответствия speaker id ↔ участник.
3. Поручения и саммари своей моделью: структура, ссылки на реплики,
   редактирование, проверка по двум эталонам.
4. PDF/DOCX и полный проход запись → протокол; затем напоминания
   и интеграции с платформами.

Каждый срез — отдельный issue с закреплёнными файлами.

# Хранение совещаний и записей

Реализация #9 использует текущую авторизацию Better Auth → Bearer JWT → FastAPI.
Совещания, участники, метаданные записей и частей хранятся в PostgreSQL `app`.
Участник — имя в протоколе, не приглашение и не право доступа. Все операции
фильтруются по владельцу совещания в SQL; даже admin получает 404 на чужую запись.
`meeting:read` и `meeting:write` доступны обеим существующим ролям.

HTTP-схемы и operationId находятся в `contracts/openapi.json`; SDK генерируется
командой `bun run api:generate`. Все пути начинаются с `/api/v1/meetings`.

## Загрузка

Создать совещание с `title`, `started_at` (время с offset) и IANA `timezone`.
Создать запись: `{source, original_filename, content_type}`. `source` — `file`,
`live`, `teams`, `google_meet` или `zoom`; имя платформы само по себе не запускает
подключение к ней. Сервер выдаёт UUID, имя файла никогда не используется как путь.

Для `source=file` отправить raw body в `PUT .../recordings/{id}/file`.
Multipart и base64 не нужны. Сервер читает поток с лимитом, проверяет файл и
возвращает `RecordingRead`. Повтор тех же байт возвращает ту же запись; другие
байты для уже готовой записи дают 409 `recording_finalized`.

Для остальных source отправлять raw body в `PUT .../recordings/{id}/chunks/{sequence}`
с `start_ms`, `end_ms` в query и `Content-Type` в заголовке. Нумерация с нуля,
порядок поступления свободный. Одна запись — один непрерывный MediaRecorder-поток;
части не обязаны быть самостоятельными контейнерами. После перезапуска рекордера
нужна новая запись. Отдельные независимо созданные файлы нельзя выдавать за части
одного непрерывного потока.

Повтор определяется по `(recording_id, sequence)`, SHA-256, интервалу и MIME
с каноническими параметрами (включая codecs). Регистр MIME и codecs, порядок параметров
и незначимые пробелы нормализуются; смена кодека отклоняется. Точное повторение не увеличивает размер и не добавляет звук.
Изменение любого из этих значений для занятого sequence даёт 409 `chunk_conflict`.
Клиентские интервалы сохраняются как диагностические оценки; реальную длительность
и шкалу плеера определяет декодированное аудио.

`POST .../recordings/{id}/finalize` принимает `{expected_chunks, is_complete}`.
Для полной записи нужны ровно все части `[0, expected_chunks)`; пропуск или лишние
части дают 409 `missing_chunks`. При `is_complete=false` можно явно сохранить
непрерывный префикс; части после него остаются приватными до удаления записи.
Нулевой префикс означает неполную запись без воспроизводимого медиа. Одинаковый
повтор finalize идемпотентен; после успеха параметры и содержимое неизменны.

Состояния хранения: `receiving`, `ready`, `incomplete`, `failed`. Они не описывают STT.
GET лениво помечает приём без обновлений более 15 минут как `incomplete`.
До finalize его можно продолжить частями или повторить прерванный file PUT.
Явно завершённая неполная запись остаётся неполной, даже если её удалось воспроизвести.
Ошибка декодирования сохраняет `failed` и `error_code`; новый upload требует новой записи.

## Проверка и временная шкала

FFprobe проверяет фактический контейнер и аудиопоток, FFmpeg декодирует первый
аудиопоток. WAV, MP3, FLAC, Ogg, WebM и MP4/M4A могут содержать обложку или видео:
оно не подменяет аудиодорожку. Плейлисты и сетевые протоколы не разрешены.
Клиентскому MIME/расширению и длительности из заголовка не доверяем: проверяется
фактическая длительность декодированного результата. Сырой stderr клиенту не отдаётся.
После проверки `content_type` обозначает найденный тип исходного контейнера;
`media_content_type` и `media_size_bytes` относятся к playback-файлу.

Оригинал хранится приватно. Для плеера и будущей обработки создаётся единый WAV PCM16,
mono, 16 kHz. Нулевая отметка — начало этой записи; паузы в аудио не вырезаются,
ускорение и voice-activity trimming не применяются. `duration_ms` вычисляется по
числу PCM-сэмплов. Транскрипт должен ссылаться на эту же шкалу и recording_id.

Лимиты по умолчанию: 512 MiB входа, 8 MiB на часть, 4096 частей, 4 часа аудио.
Настройки `BACKEND_RECORDING_*` описаны в `.env.example`; лимиты проверяются и при
чтении потока, и перед публикацией. Загрузка и обработка ограничены 600 секундами
каждая. В OpenAPI sequence/expected_chunks ограничены 4096; серверный лимит числа
частей может быть ниже. Декодирование выполняется в этом запросе; перезапуск процесса
не может объявить незавершённую подготовку готовой. Долговечная фоновая обработка — #10.

## Воспроизведение и удаление

Backend `GET/HEAD .../recordings/{id}/media` каждый раз проверяет bearer-сессию,
permission и владельца. Ответ поддерживает Range/If-Range, 206, 416, ETag и HEAD.
Ошибки Range используют общий ErrorResponse. Все ответы медиа приватные и не кешируются.
Браузеру передаётся относительный `media_url`:
`/api/media/meetings/{meeting_id}/recordings/{recording_id}`. Same-origin серверный
proxy получает JWT через действующую Better Auth cookie и пересылает поток и Range.
В URL и браузерное хранилище токен не записывается.

DELETE записи удаляет оригинал, части и WAV; совещание и другие записи сохраняются.
DELETE совещания удаляет все его записи и участников. Новые производные таблицы
должны ссылаться на recording/meeting с `ON DELETE CASCADE`, на participant с
`ON DELETE SET NULL`. Производные файлы должны находиться внутри каталога записи,
чтобы общее удаление не оставляло их на диске.

Операции публикации/удаления сериализуются блокировкой строки; при подготовке медиа
долгая транзакция не удерживается, а версия повторно проверяется перед публикацией.
Одновременное добавление частей даёт 409 `recording_changed` и допускает повтор finalize.
Файлы удаляются перед commit удаления метаданных; при ошибке файловой системы
возвращается 503 `recording_cleanup_failed`, метаданные остаются для повторного DELETE.
При сбое БД после удаления файлов нужно повторить DELETE; отсутствующие файлы допустимы.

## Запуск и данные

Docker backend содержит системный FFmpeg и работает от UID 10001. Named volume
`recordings_data` смонтирован в `/var/lib/saint-tibo/recordings` и сохраняется между
ручными обновлениями. Локально нужен `ffmpeg`/`ffprobe` в PATH; данные лежат в
`.data/recordings` и игнорируются Git. Исходник и playback занимают место отдельно:
при максимальной длительности WAV занимает около 461 MB сверх исходных данных.

Текущий MVP рассчитан на один API-хост. Реплики требуют общего приватного хранилища.
Лимит задаётся на запись; квота пользователя и lifecycle retention пока не реализованы.
Временные файлы удаляются после завершения/ошибки запроса; после аварийного завершения
процесса остатки `.incoming` удаляются оператором только после остановки активных загрузок.
Бэкап должен согласованно сохранять PostgreSQL и `recordings_data`; `down -v` удаляет их.

Compose передаёт frontend `BACKEND_INTERNAL_URL=http://backend:8000`; старые серверные
`.env` продолжают работать. Локальный setup добавляет недостающий internal URL через
BACKEND_PORT, сохраняя остальные настройки и секреты. Обновление остаётся ручным,
без CI/CD. Production и чужие dev-серверы не обновляются командой для dev Данила.

# Быстрый вход и browser-use на dev

Откройте корень своего dev-домена. При отсутствии сессии приложение само
войдёт обычным тестовым пользователем. Пароль вводить не нужно.
Существующая сессия сохраняется, включая аккаунт, созданный вручную.

| Участник | Ветка | Стартовый URL | SSH alias |
| --- | --- | --- | --- |
| Данил | `danil` | https://dev-danil.saint-tibo.win | `saint-dev-danil` |
| Иван | `ivan/lane` | https://dev-ivan.saint-tibo.win | `saint-dev-ivan` |
| Артём | `artem` | https://dev-artem.saint-tibo.win | `saint-dev-artem` |

Ветки не развёртываются автоматически: адрес показывает последний вручную
развёрнутый коммит. После общей интеграции это может быть коммит `dev`.
У каждого сервера отдельная база и host-only cookie; вход на одном домене
не авторизует другой. Для browser-use не требуется SSH-доступ.

## Аккаунты и режимы

| Режим | Email | Пароль |
| --- | --- | --- |
| Обычный пользователь | `dev-user@saint-tibo.local` | `saint-tibo-dev` |
| Администратор | `dev-admin@saint-tibo.local` | `saint-tibo-dev` |

Это общие тестовые аккаунты только для трёх dev-окружений. Храните в них
материалы кейса и синтетические данные. Для одновременных независимых
проверок или проверки чужого доступа создавайте отдельные аккаунты через
`/login` → регистрацию; общая учётка имеет общего владельца данных.

- `/` — автоматический вход обычным пользователем, если сессии нет.
- `/dev-login?role=admin` — быстрый вход администратором.
- `/dev-login?role=user` — явный быстрый вход обычным пользователем.
- `/login` — ручной вход, регистрация и выход, без автоматического входа.
- `/?auth=manual` — открыть приложение с обычной проверкой авторизации,
  пропустив автоматический вход для этого перехода.

Для смены роли сначала выйдите из текущего аккаунта, затем откройте нужный
URL быстрого входа. Ссылка администратора не заменяет активную сессию.
Кнопка выхода ведёт на `/login` и оставляет браузер без сессии. Возврат в
корень dev-домена снова включает быстрый вход.

## Короткий сценарий для агента

1. Открыть нужный dev-домен, дождаться рабочего пространства. При проверке
   входа с нуля сначала выйти через UI или использовать чистый профиль браузера.
2. Убедиться, что видны навигация приложения и кнопка выхода. На `/login`
   при активной сессии отображается email вошедшего пользователя.
3. Выполнить изменённый пользовательский сценарий, включая сохранение
   результата и повторное открытие. Использовать имена вроде
   `dev-danil-82-<время>`, чтобы отличать данные разных запусков.
4. При необходимости выйти и открыть `/dev-login?role=admin`. Для ручного
   входа на `/login` доступны стабильные поля `input[name="email"]`,
   `input[name="password"]` и `button[type="submit"]`.
5. Удалить только созданные этим запуском данные; записать URL, SHA и
   фактический результат в issue. Не удалять общую базу или данные коллег.

Для навигации используйте доступные имена ссылок и кнопок из текущего
снимка браузера: интерфейс поддерживает RU/KK/EN. Не привязывайтесь к
CSS-классам или координатам. Сессия создаётся настоящим Better Auth;
backend проверяет JWT, права и владельца записей в обычном порядке.

По указанию владельца от 2026-09-23 текущая работа выполняется без
написания и запуска тестовых наборов: достаточно сборки для deployment
и короткой проверки изменённого сценария на живом dev-сервере.

## Настройка и восстановление

`scripts/dev-deploy.sh` включает `DEV_LOGIN_ENABLED=true` и запускает
отдельный `seed:dev`. Повторный запуск создаёт недостающие dev-аккаунты;
существующие реальные аккаунты и их пароли не изменяются. Если email
занят посторонним аккаунтом, seed останавливается с ошибкой: сначала
разберите конфликт, не сбрасывайте пароль автоматически.

Если быстрый вход не работает, откройте `/login` и проверьте ручной вход,
затем readiness и логи frontend. Для восстановления конфигурации и seed
повторите deployment нужного закоммиченного дерева:

```sh
sh scripts/dev-deploy.sh saint-dev-danil
ssh saint-dev-danil 'cd /opt/saint-tibo/current && docker compose logs --tail=40 frontend'
```

Подставьте свой alias. Скрипт проверяет текущий SHA сервера и не позволяет
молча затереть неизвестную или расходящуюся историю. Сначала получите и
влейте развёрнутую ветку коллеги, затем повторите запуск. Инструкции по
серверу и секретам — в [dev-server.md](dev-server.md).

Механизм разрешён только при серверном флаге и точном `BETTER_AUTH_URL`
одного из трёх HTTPS dev-доменов. POST `/api/dev-login` принимает только
свой Origin; адрес назначения не приходит от клиента. В production
deployment принудительно выключает флаг, а серверная проверка домена
запрещает быстрый вход даже при ошибочном включении. Эти настройки не
отключают настоящую авторизацию и не дают общей сессии между доменами.

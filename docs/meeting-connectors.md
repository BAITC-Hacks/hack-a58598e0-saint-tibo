# Подключение к внешним встречам

Исследовательская часть [#22](https://github.com/BAITC-Hacks/hack-a58598e0-saint-tibo/issues/22). Проверено по официальной документации 23 сентября 2026 года. Вход в реальную встречу и получение аудио в этом исследовании **не проверялись**; issue остаётся открытым.

## Решение для первого прохода

Рекомендуемый эксперимент: отдельный, явно обозначенный участник Teams в обычном Chrome/Edge на выделенном Linux runner, допущенный организатором; изолированный аудиовыход браузера → FFmpeg → локальный файл/приёмник. Сначала доказать это вручную на тестовой встрече, затем автоматизировать только обычный интерфейс. Это инженерная гипотеза для прототипа, а не поддерживаемый Microsoft SDK для ботов. Если политика организации или платформа запрещает такой способ, остановить адаптер и использовать разрешённый источник записи.

Универсального подтверждённого официального SDK для отдельного участника во всех трёх платформах с полностью локальным production-размещением сейчас не установлено. Для Zoom предпочтителен официальный RTMS, но он получает поток через разрешённое приложение и не заменяет требование отдельного участника автоматически. Для Meet официальный Media API требует доступа к Preview.

Запись и модели остаются на нашей стороне: не включаем облачные captions, транскрибацию, саммари или внешние SaaS-рекордеры. Teams/Meet/Zoom при этом остаются внешним транспортом самой встречи. Для полностью изолированной сети без доступа к этим платформам доступны только загрузка файла и локальная запись; обещать подключение к внешней встрече в таком режиме нельзя.

### Уточнения официальных путей

**Teams.** Для app-only join/media обычно нужны application permissions семейства `Calls.JoinGroupCall*` и `Calls.AccessMedia.All` с admin consent; существует также RSC для конкретного chat/meeting. До сохранения media официальный Graph-путь требует успешного `updateRecordingStatus`; по завершении сначала остановить запись, затем сообщить окончание. Набор прав и пригодность лицензии организатора проверяются на выделенном тестовом tenant, не угадываются по наличию ссылки. [Регистрация и права](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/calls-and-meetings/registering-calling-bot).

**Meet.** Соединение требует присутствующего участника, уполномоченного дать согласие; для consumer-встреч это инициатор. Отзыв разрешения останавливает подключение. Документация указывает ограничения для watermark/encrypted meetings, несовершеннолетних и некоторых hardware clients. Это дополнительные blockers даже при наличии OAuth. [Lifecycle и согласие](https://developers.google.com/workspace/meet/media-api/guides/overview). Для проверки реализации есть официальный C++ reference client, но совместимость его сборки с нашим runner ещё не доказана. [Quickstart](https://developers.google.com/workspace/meet/media-api/guides/cpp).

**Zoom.** Запрашивать только media, необходимые продукту: `meeting:read:meeting_audio`, без transcript scope. [Настройка RTMS](https://developers.zoom.us/docs/rtms/meetings/add-features/). Официальный quickstart показывает собственный receiver и audio callback; production webhook нужно размещать на согласованном HTTPS ingress, а не автоматически подключать сторонний tunnel. Нативный RTMS SDK/его OS-архитектуру проверяем до pin зависимостей; есть путь через WebSocket. [Приём аудио](https://developers.zoom.us/docs/rtms/meetings/quickstart/).

## Минимальный контракт адаптера — предложение к #8

Иван владеет процессом подключения/записи; Данил — авторизованным приёмом, хранением и дальнейшей обработкой. Это проект контракта, не существующий API.

- Вход: `meeting_id`, `session_id`, `platform`, ссылка встречи, отображаемое имя, подтверждение уведомления участников, ссылка на серверную конфигурацию доступов. Секреты и полный meeting URL не попадают в журнал.
- Возможности: `joins_as_participant`, `provides_participant_audio`, `provides_mixed_audio`. UI различает участника и media stream; `participant_id` необязателен.
- Состояния: `queued → connecting → waiting_admission → connected → recording → stopping → completed`. Для RTMS без lobby переход напрямую из `connecting` в `connected`. Из нетерминальных состояний возможны `failed` и `cancelled` только после cleanup.
- Причины остановки: `admission_denied`, `admission_timeout`, `authentication_required`, `permission_revoked`, `media_unavailable`, `meeting_ended`, `duration_limit`, `cancelled`, `worker_failed`. Любая повторная попытка после отказа требует нового запуска пользователем.
- Аудиочасть: `session_id`, монотонный `sequence`, начало/конец на временной шкале записи, codec/sample rate/channel count, checksum, длина. Повтор части идемпотентен; пропуски и разрывы времени явно сохраняются.
- Окончание: итоговый manifest и подтверждение приёмника; локальная запись не считается загруженной до подтверждения. Захват по расписанию и «тишина» сами по себе не доказывают успешную запись.

Смешанный браузерный звук не даёт надёжной привязки к ФИО. Диаризация выполняется локально, затем пользователь подтверждает имена. Наличие roster или индикатора активного говорящего не заменяет эту проверку.

## Что можно сделать без доступов

Подготовить state machine, валидацию ссылок и редактирование секретов в логах, отмену и таймауты, isolated audio sink, поток FFmpeg, manifest и идемпотентную передачу в согласованный приёмник. Проверить на синтетическом аудио, включая отсутствие звука, обрыв процесса, дубли частей и освобождение ресурсов. Не читать cloud captions или внутренние API web-клиента; не скрывать автоматизацию и не обходить login, CAPTCHA, lobby, browser permissions либо запрет записи.

Для браузерного runner разрешать только утверждённые HTTPS-хосты платформ, проверять redirect и запрещать обращения к локальным/служебным адресам. Один sink и рабочий каталог на сессию; не записывать весь системный звук. Оператор явно предупреждает участников до начала записи: видимое имя рекордера само по себе не является достаточным уведомлением.

## Что нужно для живой проверки

1. Teams: согласованная тестовая встреча, организатор для допуска и объявления записи, минимум два тестовых говорящих; если требуется — выделенный разрешённый аккаунт и ручной вход. Сначала доказать обычный browser join и слышимое аудио на целевом Linux runner.
2. Meet: либо контролируемая browser-встреча с допуском, либо подтверждённые Preview enrollment/OAuth/admin settings для официального API и всех участников. Доступ к API ещё не предоставлен.
3. Zoom: аккаунт с Developer Pack, RTMS app/разрешения и тестовый host. Нужен отдельный продуктовый выбор: поток RTMS принимается как интеграция либо требование отдельного участника остаётся blocker. Платные подписки и новые облачные ресурсы в ходе исследования не создавались.

## Доказательство для приёмки #22

На одной реальной контролируемой встрече сохранить безопасный отчёт: версия runner/browser или SDK, время входа/допуска/начала, подтверждение уведомления, локальный файл с голосами двух участников, длительность/codec/checksum и отсутствие audio/text egress к внешнему AI. Проверить воспроизведение, ручной стоп, отказ допуска, истечение таймаута и отсутствие оставшихся процессов/участника. Полные URL, токены и реальные персональные данные в отчёт не включать.

До этого результата матрица выше является оценкой осуществимости, а не заявлением о готовых интеграциях Teams/Meet/Zoom.

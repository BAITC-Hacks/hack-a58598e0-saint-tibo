# Контракт совещаний и записей

Проект контракта для [#8](https://github.com/BAITC-Hacks/hack-a58598e0-saint-tibo/issues/8).
Схемы ниже предназначены для совместной разработки backend, UI и плеера.
Наличие примера **не означает наличие endpoint**. Реализованные операции публикуются
только через FastAPI → `contracts/openapi.json` → сгенерированный TS SDK.
На исходном `25b062f` существуют только auth, `/api/v1/me`, `/api/v1/admin/access`
и health; предметных endpoints ещё нет. Принятие потребителями фиксируется в #8.

## Общие правила

- API prefix `/api/v1`, JSON `snake_case`, `operation_id` в camelCase,
  ошибки `{"error":{"code":"...","message":"...","details":null}}`.
  Следуем [соглашениям репозитория](conventions.md), без смены текущей авторизации.
- Все идентификаторы ниже — отдельные UUID. `owner_id` — непрозрачный ID BetterAuth,
  сервер получает его из действующей сессии, клиент не назначает владельца.
- Текущее право доступа: владелец совещания. Участник совещания — запись в протоколе,
  а не приглашение пользователя и не автоматическое право доступа. `admin` не
  обходит проверку владельца. Неавторизованный запрос получает 401, чужой объект — 404.
- Списки используют `{items,total,limit,offset}`; default limit 20, максимум 100,
  offset ≥ 0; стабильный порядок `created_at DESC, id DESC`.
- Время событий — RFC 3339 с обязательным offset; сервер возвращает UTC.
  `timezone` — IANA, например `Asia/Almaty`. `started_at` и `timezone` обязательны:
  без них относительные сроки не превращаются в календарные даты.
- Таймкоды — целые миллисекунды от начала **конкретной записи**, 0 ≤ start_ms < end_ms.
  Плеер может принимать seek 0. В его callback время тоже в ms, не в секундах.
  Нормализация аудио не удаляет паузы и не изменяет скорость.
- Числовые лимиты и проверки входа присутствуют в OpenAPI реализованной операции.
  UI обрабатывает неизвестный статус как неподдерживаемый, а не как «готово».
- UI локализует `error.code`, технический `message` не содержит аудио, текста реплик,
  токенов, пути на диске и вывода FFmpeg. Секреты и пользовательские записи не попадают
  в Git или логи. Исходники кейса в `input-audio/` добавлены отдельно по прямому
  поручению владельца (#32); это не правило хранения загружаемых пользователями записей.

## Сущности

| Сущность | Идентификатор / обязательные связи | Назначение |
| --- | --- | --- |
| Meeting | `id` (`meeting_id` в ссылках), `owner_id` | Название, started_at, timezone |
| Participant | `id` (`participant_id`), `meeting_id` | Имя и необязательная роль в совещании |
| Recording | `id` (`recording_id`), `meeting_id` | Исходная запись и единая временная шкала |
| ProcessingJob | `id` (`job_id`), `recording_id` | Одна попытка обработки |
| ResultVersion | `id` (`result_version_id`), `recording_id`, `job_id` | Отдельная версия результата |
| Speaker | `id` (`speaker_id`), `result_version_id` | Метка голоса с nullable participant_id |
| Segment | `id` (`segment_id`), `result_version_id`, `recording_id` | Текст, start_ms, end_ms, nullable speaker_id |
| ActionItem | `id` (`action_item_id`), `result_version_id` | Поручение и источники в сегментах |

Имена, метки голосов и временные интервалы не служат ID. Ссылка на участника,
запись или сегмент из чужого совещания отклоняется. Удаление участника сбрасывает
соответствующую ссылку говорящего/исполнителя в null и не стирает исходную реплику.

## Совещания и участники — #9

Операции: `GET/POST /meetings`, `GET/PATCH/DELETE /meetings/{meeting_id}`;
`GET/POST /meetings/{meeting_id}/participants`,
`PATCH/DELETE /meetings/{meeting_id}/participants/{participant_id}`.
Здесь и далее пути дополняются prefix `/api/v1`.

Создание `createMeeting` → 201; чтение/изменение → 200; удаление → 204.
PATCH меняет только переданные поля; обязательные поля нельзя обнулить.

```json
{
  "title": "Демонстрационное совещание",
  "started_at": "2026-09-23T10:00:00+05:00",
  "timezone": "Asia/Almaty"
}
```

```json
{
  "id": "00000000-0000-4000-8000-000000000001",
  "owner_id": "demo-user",
  "title": "Демонстрационное совещание",
  "started_at": "2026-09-23T05:00:00Z",
  "timezone": "Asia/Almaty",
  "created_at": "2026-09-23T05:00:00Z",
  "updated_at": "2026-09-23T05:00:00Z"
}
```

Участник создаётся из `{display_name, role?}`. Его роль — свободная подпись
«секретарь», «юрист», а не системная роль BetterAuth. Исполнитель может отсутствовать
на записи: запись Participant не требует speaker_id. Неизвестный исполнитель — null.

## Записи: состояние хранения отдельно от обработки

`source`: `file | live | teams | google_meet | zoom`. Значение платформы — метаданные
источника, не доказательство работающего адаптера. #23–25 проверяются отдельно.

`status`: `receiving | ready | incomplete | failed`.

- `receiving`: загрузка/приём частей ещё идёт, `media_url=null`.
- `ready`: запись завершена, контейнер и аудиопоток проверены, медиа воспроизводимо.
  Это **не** означает, что есть транскрипт, саммари или поручения.
- `incomplete`: клиент сообщил об обрыве либо истёк период неактивности приёма.
  Возможность восстановления определяется сервером. `media_url` есть только если
  удалось проверить и подготовить воспроизводимый непрерывный префикс.
  До finalization и появления playback-медиа можно возобновить приём частей;
  после восстановления запись остаётся явно неполной и становится неизменяемой.
- `failed`: содержимое некорректно или подготовка медиа закончилась ошибкой;
  `error_code` заполнен, `media_url=null`. Новый upload — новая запись.

Первый срез: максимум 512 MiB входных данных на запись, 8 MiB на live-часть,
4096 частей, 4 часа аудио. Значения настраиваются на сервере; превышение размера
отклоняется во время чтения потока, а не после накопления файла в памяти.
Приём считается прерванным после 15 минут без принятой части/обновления.
Ленивая проверка этого срока при GET/следующей операции допустима; постоянный daemon
для очистки не требуется. UI не показывает stale receiving как успешно завершённый.

Поддерживаемые входы первого среза: WAV, MP3, FLAC, Ogg, WebM, MP4/M4A с аудиопотоком.
Расширение и клиентский MIME не являются проверкой. Сервер проверяет реальный
контейнер, наличие аудио, длительность и возможность декодирования с ограниченным
временем работы. Обложка MP3 не выбирается как видео. Первый аудиопоток выбирается
явно; поддержка выбора альтернативной дорожки относится к #10.

Для одинакового поведения браузеров сервер хранит отдельное playback-медиа WAV PCM16,
mono, 16 kHz с неизменной временной шкалой. Исходник остаётся приватным. В ответе размер и MIME
playback-медиа отделены от исходного размера; не выдаём исходный FLAC/MKV как
гарантированно воспроизводимый во всех браузерах. Если подготовка не удалась,
запись не становится ready. Реализация/лимиты этой подготовки описаны в #9.

## Загрузка файла и live-частей — #9

1. `POST /meetings/{meeting_id}/recordings` (`createRecording`) → 201.
   Тело `{source, original_filename, content_type}`; `content_type` — заявленный MIME,
   не результат проверки. Клиент сохраняет полученный recording_id до отправки байт.
2. Файл: `PUT /meetings/{meeting_id}/recordings/{recording_id}/file`.
   Тело — raw binary, не multipart/base64; MIME в `Content-Type`.
   Полный принятый файл проверяется и становится ready; ответ RecordingRead 200.
3. Live/платформа: `PUT .../recordings/{recording_id}/chunks/{sequence}`
   с query `start_ms` и `end_ms`, raw binary телом и `Content-Type`.
   Нумерация с 0, интервалы относительные, клиентские оценки времени сохраняются
   для диагностики; источником истины для воспроизведения остаётся декодированное аудио.
4. `POST .../recordings/{recording_id}/finalize` с
   `{expected_chunks: 2, is_complete: true}` → 200 RecordingRead после проверки.
5. Явный обрыв: тот же finalize с `is_complete:false`. Только непрерывный полученный
   префикс `[0, expected_chunks)` можно восстановить; итоговый status=incomplete.
6. `GET /meetings/{meeting_id}/recordings` — PageRecordingRead;
   `GET/DELETE .../recordings/{recording_id}` — 200/204.

Идемпотентность части — `(recording_id, sequence)` плюс SHA-256 байт, интервалы и MIME.
Повтор с теми же байтами/метаданными возвращает исходный результат без удвоения звука.
Другие байты/метаданные для занятого sequence → 409 `chunk_conflict`.
Порядок прихода частей может отличаться от sequence. Finalize проверяет отсутствие
дыр и точное expected_chunks, иначе 409 `missing_chunks`, оставляет возможность
дослать части. Нельзя молча соединить участки по обе стороны пропуска.
Повтор идентичного finalize возвращает ту же запись; изменение его параметров
после завершения → 409 `recording_finalized`.

Одна live-запись — один непрерывный поток MediaRecorder с выбранным MIME: части
могут быть фрагментами контейнера, а не самостоятельными файлами. Сервер объединяет
их в порядке sequence и декодирует только после finalize. Перезапуск MediaRecorder,
смена кодека/источника или независимые контейнеры требуют новой recording_id.
Клиент завершает очередь `dataavailable` перед finalize. Беззвучие не считается
ошибкой формата; обнаружение тишины/неверного источника — отдельная проверка #21.

Повтор полного file PUT сравнивает digest и возвращает ту же готовую запись;
другой файл в уже завершённую запись → 409. Разорванный PUT не публикует частичный
файл: повтор допустим, пока запись receiving. Одновременные PUT/finalize/delete
сериализуются для одной записи; временный файл никогда не становится публичным.

Проект RecordingRead (метаданные источника не используются как путь на диске):

```json
{
  "id": "00000000-0000-4000-8000-000000000002",
  "meeting_id": "00000000-0000-4000-8000-000000000001",
  "source": "file",
  "original_filename": "demo.wav",
  "content_type": "audio/wav",
  "status": "ready",
  "size_bytes": 320044,
  "duration_ms": 10000,
  "media_content_type": "audio/wav",
  "media_size_bytes": 320078,
  "media_url": "/api/media/meetings/00000000-0000-4000-8000-000000000001/recordings/00000000-0000-4000-8000-000000000002",
```

## Доступ к медиа и контракт плеера — #9 / #19 / #20

Backend `GET/HEAD /meetings/{meeting_id}/recordings/{recording_id}/media` проверяет
Bearer JWT, активную сессию и владельца при каждом запросе, включая Range и HEAD.
Браузер использует относительный `media_url` из RecordingRead как `<audio src>`:
same-origin frontend GET/HEAD proxy проверяет BetterAuth cookie и получает JWT
на сервере. Proxy обращается только к заданному внутреннему backend, передаёт
`Range`/`If-Range`, возвращает status/stream/range headers, не буферизует файл целиком.
Bearer-токен не попадает в URL, localStorage, props плеера или публичный redirect.

- Полный запрос → 200; допустимый Range → 206 + Content-Range/Content-Length.
- Выход за границу → 416 + `Content-Range: bytes */<size>`.
- HEAD не содержит тело. Медиа поддерживает `Accept-Ranges: bytes`.
- Ответы приватные, `Cache-Control: private, no-store`, без общего CDN-кеша.
- 401 после logout/отзыва сессии; 404 для чужой/удалённой записи;
  409 `recording_not_playable` для непроверенной записи.

Владелец плеера — Иван: компонент принимает browser-playable `media_url`,
отдаёт `seek(timeMs)`, `pause()` и изменение позиции в ms (claim #19).
UI Артёма передаёт recording_id и URL, управляет выбором записи и оформлением.
Seek по сегменту использует его recording_id и start_ms, не индекс строки.
При смене записи прежний звук останавливается. Ошибка медиа не означает ошибку STT.

## Задания и прогресс — проект #10

Выбран один транспорт: **polling HTTP**, интервал 2 секунды во время активного
задания, с паузой при скрытой вкладке/потере сети. SSE/WebSocket для этой задачи
не требуются. После возврата клиент читает сохранённое состояние из API.

`POST .../recordings/{recording_id}/jobs` → 202 `{id, recording_id, ...}`;
`GET .../recordings/{recording_id}/jobs/{job_id}` → 200.
Статус `queued | running | succeeded | failed | interrupted`;
stage `decode | transcribe | diarize | extract | complete`.
`progress` nullable (0..1); не выдаём таймер за реальный прогресс.
Ответ также содержит `attempt`, `error_code`, nullable `result_version_id`, timestamps.
Повторный запуск создаёт новое job_id и result_version_id. Идемпотентный повтор
с тем же клиентским ключом не создаёт вторую задачу. Активное задание на ту же
запись → 409 `processing_in_progress`.

Падение worker/истечение lease → interrupted, а не succeeded. Retry — явное действие.
Неполная воспроизводимая запись требует явного `allow_incomplete:true`; её результат
сохраняет признак неполноты. Части без media_url не допускаются в обработку.
UI всегда отличает статус хранения от статуса задания и ручной проверки результата.

## Реплики, участники и версии — проект #11–13

Segment: `{id, recording_id, result_version_id, speaker_id|null, start_ms, end_ms, text}`.
Speaker: `{id, result_version_id, label, participant_id|null}`. Машинная метка
`SPEAKER_00` не является именем. Человек связывает Speaker с Participant; объединение
голосовых меток сохраняет ссылки реплик. Диаризация не создаёт голосовых отпечатков.

ActionItem: `{id, result_version_id, text, assignee_participant_id|null,
assignee_text|null, due_text|null, due_date|null, status, source_segment_ids}`.
`status`: `open | in_progress | done | cancelled`. `due_date` — ISO дата в timezone
совещания, не выдуманное время UTC. Исходный due_text сохраняется всегда;
неоднозначный относительный срок оставляет due_date=null до ручной проверки.
Исполнитель не выводится автоматически из speaker_id. Все source_segment_ids
принадлежат той же версии/записи. Повтор поручения и уточнение срока не размножают его.

Саммари содержит темы, решения, открытые вопросы и ссылки на source_segment_ids.
Текст записи — данные модели, не системные команды. Обработка полностью локальная,
включая извлечение поручений. Правки сохраняются на сервере с `revision` для проверки
конкурентного изменения: PATCH с устаревшей revision → 409 `version_conflict`.
Проверенная версия помечена `reviewed`; экспорт и напоминания получают конкретные
result_version_id/revision. Новое задание не перезаписывает ручные исправления.

## Подключение к платформам — проект #22–25

Публичный доменный запрос: создать CaptureSession для meeting_id и платформы,
запросить остановку, читать состояние. Сам backend не скачивает произвольный URL.
Сервис Ивана принимает только проверенные адреса/ID Teams/Meet/Zoom, секреты —
в серверной конфигурации/закрытом запросе, без пароля в issue, URL состояния и логах.
UI не получает внутренний service credential. Конкретные service-auth и endpoints
финализируются после проверки SDK/разрешений в #22, публичная регистрация агента
без аутентификации недопустима.

Состояния: `requested → joining → waiting_admission → recording → stopping → completed`.
`joining` может сразу перейти в `recording`; из любого нетерминального состояния
возможны `failed`/`cancelled`. В ответе: id, meeting_id, nullable recording_id,
platform, status, error_code, started_at, ended_at. Терминальное событие не может
вернуть completed обратно в recording. Повтор stop идемпотентен, timeout завершает
процесс и участника. До записи участник заметно обозначен, запись разрешена.

Аудио передаётся backend тем же chunk/finalize контрактом с корректной привязкой
к владельцу и записи. Недопуск/завершение встречи без аудио не создают ready.
Локальная запись вкладки — source=live, она не подменяет отдельного участника платформы.

## Ошибки и удаление

```json
{
  "error": {
    "code": "chunk_conflict",
    "message": "A different chunk already exists at this sequence.",
    "details": null
  }
}
```

| HTTP | Примеры code | Поведение клиента |
| --- | --- | --- |
| 401 | unauthorized | Восстановить вход, не повторять бесконечно |
| 403 | forbidden | У пользователя отсутствует permission |
| 404 | not_found | Объект отсутствует или недоступен владельцу |
| 409 | chunk_conflict, missing_chunks, recording_finalized, recording_not_playable | Проверить актуальную запись/очередь |
| 413 | recording_too_large, chunk_too_large | Не повторять тот же объём |
| 415 | unsupported_media | Выбрать поддерживаемый формат |
| 422 | validation_error, invalid_media | Исправить метаданные/файл; тело validation_error использует details |
| 503 | processing_unavailable | Ограниченный повтор с задержкой, состояние не «готово» |

Конкретные коды/схемы реализованных ошибок фиксируются в OpenAPI и документации #9;
сырой stderr декодера никогда не возвращается клиенту.

DELETE recording удаляет исходник, части, playback-медиа и принадлежащие записи
задания/версии/экспорты. Meeting и другие его записи сохраняются. DELETE meeting
каскадно удаляет участников, записи и производные результаты. Owner ACL проверяется
до операций с файлами. После удаления новый media request возвращает 404;
уже переданные браузеру байты отозвать невозможно. Отсутствующие файлы не мешают
повторить cleanup, ошибка файловой системы не маскируется успешным удалением.

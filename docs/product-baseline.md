# Начальное состояние продукта

Этот документ описывает основу для совместной разработки. Требования к
обработке совещаний и исходные материалы — в [кейсе](case.md), запуск
на личном сервере — в [инструкции](dev-server.md).

## Что уже есть

Вход, регистрация и выход с настоящими сессиями, серверная проверка прав,
рабочее пространство RU/KK/EN, светлая и тёмная темы, настройки доступности,
PostgreSQL с миграциями и генерируемый TypeScript-клиент FastAPI.
Первый backend-срез #9 добавляет хранение совещаний/участников, загрузку файла и
live-частей, приватное воспроизведение с перемоткой и удаление. UI этих операций
развивается отдельно; контракт не означает наличие готового пользовательского пути.

| Сценарий | Начальное состояние |
| --- | --- |
| Регистрация и вход | Работают; регистрация создаёт обычного пользователя |
| Доступ к рабочему пространству | Требует сессию; API отдельно проверяет права |
| Страница совещаний | Сообщает, что обработка записей ещё не подключена |
| Загрузка файла и приём частей | API готов; пользовательский экран и браузерный захват ещё не подключены |
| Хранение и воспроизведение | Приватный volume, WAV с общей шкалой, cookie media proxy и Range; интеграция плеера отдельно |
| STT, диаризация и извлечение поручений | Не реализованы |
| Саммари, протокол и экспорт | Не реализованы |
| Напоминания и интеграции встреч | Не реализованы |

Запуск основы на production не меняет этот список готовности.
Экран не должен выдавать статические примеры за результат обработки,
показывать фиктивные счётчики или предлагать действие без реализации.

## Брендинг и интерфейс

[Issue #2](https://github.com/BAITC-Hacks/hack-a58598e0-saint-tibo/issues/2)
закрыт без поставки брендинга. В последнем комментарии Иван указал,
что незавершённые изменения сняты, а брендинг и UI/UX переданы Артёму.
Актуальная задача —
[issue #16](https://github.com/BAITC-Hacks/hack-a58598e0-saint-tibo/issues/16),
назначенная Артёму. Повторно импортировать шаблон и возвращать удалённый
Notes не требуется.

Saint Tibo — название проекта команды. Контекст кейса — Samruk-Kazyna Ondeu.
При подборе материалов не смешивать визуальную идентичность Ondeu
и материнского фонда: это разные организации, что отражено на
[официальном сайте Ondeu](https://o-sk.kz/about-company/about-us/).
В образцах кейса и на официальном сайте различается юридическая форма;
для интерфейса достаточно названия без самостоятельно выбранной формы.

Точки изменения единой визуальной системы:

- `frontend/src/app/styles/globals.css` — общие токены и темы;
- `frontend/src/app/layouts/app-shell.tsx` — навигация и оболочка;
- `frontend/src/pages/login/ui/login-page.tsx` — вход и регистрация;
- `frontend/src/pages/home/ui/home-page.tsx` — стартовое состояние совещаний;
- `frontend/messages/{ru,kk,en}.json` — весь пользовательский текст;
- `frontend/public/` — локальные ресурсы бренда и favicon.

Использовать текущие компоненты из `shared/ui`, сохранять мобильное меню,
клавиатурный фокус, доступность, все три локали и работу авторизации.
Шрифты и изображения, нужные приложению, должны загружаться с нашего
сервера: внешний CDN не должен быть обязательным условием работы.
Для брендовых ресурсов фиксировать источник; в шаблонах экспортируемых
протоколов использовать ту же согласованную идентичность.

## Первый продуктовый срез

Создание встречи с датой и участниками → загрузка записи → видимый прогресс
фоновой обработки → реплики с таймкодами и говорящими → проверка поручений
и саммари → сохранение исправлений → скачивание протокола.

В интерфейсе различать отсутствие записей, обработку, ошибку и готовый
результат. Поручение показывает исполнителя, исходный срок и источник;
неизвестное имя или дата требуют проверки, а не догадки. Исполнитель
не обязан совпадать с говорящим или участником встречи.

Проверка среза выполняется на личном dev-сервере по реальному сценарию,
затем по интегрированному `dev`. Изменения UI не должны вводить отдельную
авторизацию, другую UI-библиотеку или ручную копию API-контракта.
Production разворачивается из согласованного `main` вручную.

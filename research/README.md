# Meeting-system research

This directory preserves the **14 complete texts supplied by the project owner** on 23 September 2026. The files in [`sources/`](sources/) are byte-for-byte copies of the supplied Russian text, including citations, examples, caveats, and original links. They are source material, not a claim that the proposals are implemented or tested. Some `sandbox:/` links in the originals refer to artifacts outside this repository and may not resolve for other readers.

This English index turns the research into decisions for Saint Tibo. The live product contract and verified setup remain in [`docs/`](../docs/); issue comments record integration and deployment evidence. Check current GitHub and the deployed commit before treating any status below as current.

## Decision for the hackathon

**Finish and demonstrate the narrow, real path first:** private recording upload → local transcription with timed segments → human review of summary and action items with audio evidence → saved revision → authenticated PDF/DOCX. This path is being integrated in [#107](https://github.com/BAITC-Hacks/hack-a58598e0-saint-tibo/issues/107) and [PR #109](https://github.com/BAITC-Hacks/hack-a58598e0-saint-tibo/pull/109). A real browser walkthrough and exact deployed SHA are still the release gate; source code or a synthetic screen alone is insufficient.

The present stack is React/TypeScript with TanStack Start and Better Auth, FastAPI/Python with SQLAlchemy, PostgreSQL, a generated OpenAPI client, and a separate local transcription worker. `dev` already contains recording, persisted jobs, STT, review persistence, and export code. A completed RU transcription and backend review/export checks have been reported in [#94](https://github.com/BAITC-Hacks/hack-a58598e0-saint-tibo/issues/94) and [#13](https://github.com/BAITC-Hacks/hack-a58598e0-saint-tibo/issues/13). This does **not** establish automatic action extraction, integrated diarization, or acceptable quality on human KK/mixed meetings.

## Findings across the fourteen texts

1. **Capture and existing projects.** Backchannel, Recall's extension, WXT, Electron, SoundCard, Mediabunny, WhisperLiveKit, and WhisperX wrappers are implementation references or candidates, not drop-in proof that capture works on the target operating systems. File upload already provides the shortest verifiable route. Live/platform capture belongs to separate acceptance work. See [01](sources/01-github-capture-audit.md), [02](sources/02-transcription-projects.md), and [#21–25](https://github.com/BAITC-Hacks/hack-a58598e0-saint-tibo/issues/21).
2. **Speech and meeting quality.** Measure transcription, speaker assignment, action detection, assignee, final deadline, and provenance independently. Use separate RU, KK, and mixed scorecards. Written example minutes are not verbatim references for their audio; the [case notes](../docs/case.md) identify disputed passages that need a human listening decision. A speaker label does not establish a person's identity. See [06](sources/06-quality-evaluation.md), [#70](https://github.com/BAITC-Hacks/hack-a58598e0-saint-tibo/issues/70), and [#89](https://github.com/BAITC-Hacks/hack-a58598e0-saint-tibo/issues/89).
3. **Private processing.** Run audio/text inference locally, from pinned prepared assets, with no hidden cloud fallback or runtime download. Keep the processing worker without external egress; route only explicitly approved integration fields through a separate gateway. A recording imported from a cloud meeting platform was already outside the local boundary before ingestion. See [07](sources/07-closed-processing.md) and [#31](https://github.com/BAITC-Hacks/hack-a58598e0-saint-tibo/issues/31).
4. **Evidence and revisions.** An action may be created, repeated, reassigned, or given a corrected deadline later in the same meeting. Its evidence may span several segments. Preserve the wording and source of each field and require review when resolution is ambiguous. Approval belongs to one frozen revision; a later action-card deadline must not rewrite the approved PDF/DOCX. Keep protocol approval and current action execution as separate life cycles, without a generic workflow engine. See [06](sources/06-quality-evaluation.md), [14](sources/14-minutes-and-actions-lifecycle.md), [#90](https://github.com/BAITC-Hacks/hack-a58598e0-saint-tibo/issues/90), and [#91](https://github.com/BAITC-Hacks/hack-a58598e0-saint-tibo/issues/91).
5. **Identity and object permissions.** Better Auth sessions and a corporate IdP establish identity, while the backend decides access to each organization's meeting, audio, transcript, action, and export. An account administrator is not automatically a meeting reader. The same business authorization must apply to REST, media Range requests, bots, and MCP. RLS is a possible extra tenant barrier, not a substitute for operation-level authorization. See [09](sources/09-sso-and-device-trust.md), [10](sources/10-object-permissions.md), and [#86](https://github.com/BAITC-Hacks/hack-a58598e0-saint-tibo/issues/86).
6. **Audit, deletion, and keys.** Record the actor, action, object version, result, and file digest without copying meeting content into logs. Test that restoration does not resurrect deleted meetings or revoked access. Choose a closed-site key service or AWS IAM/KMS profile according to the deployment; neither justifies writing custom cryptography or keeping static AWS keys. See [04](sources/04-audit-retention-recovery.md), [08](sources/08-secrets-and-encryption.md), [#87](https://github.com/BAITC-Hacks/hack-a58598e0-saint-tibo/issues/87), and [#92](https://github.com/BAITC-Hacks/hack-a58598e0-saint-tibo/issues/92).
7. **Redaction and security testing.** A safe-to-share copy needs policy, deterministic handling of identifiers, local RU/KK entity detection, human review, and links to precise original spans. A pseudonymized copy is still sensitive. Security evaluation should attack actual API/tool effects, including authorization bypass, malicious transcript instructions, file/resource abuse, and leakage; the research supplies test plans, not findings of existing vulnerabilities. See [11](sources/11-pii-redaction.md), [12](sources/12-security-verification.md), [#36](https://github.com/BAITC-Hacks/hack-a58598e0-saint-tibo/issues/36), and [#71–72](https://github.com/BAITC-Hacks/hack-a58598e0-saint-tibo/issues/71).
8. **Bots, calendar, and MCP.** Keep PostgreSQL authoritative for actions, consent, and reminder intent. A calendar provides schedule changes; webhooks trigger a sync and do not themselves contain the new event. Recheck authorization and consent before sending. A lost provider response needs an `unknown` delivery outcome rather than an unsafe automatic retry. Telegram inline controls are the smallest bot pilot; Teams/Slack depend on customer usage, WhatsApp has more operational limits. MCP should expose a small explicit tool set through the same business operations and needs real client/IdP compatibility testing. See [03](sources/03-remote-mcp.md), [05](sources/05-chat-bots.md), [13](sources/13-calendar-and-reminders.md), and [#53–67](https://github.com/BAITC-Hacks/hack-a58598e0-saint-tibo/issues/53).

## Evidence limits and corrections

- The repository audits compare code and documentation; they did not build every candidate on every operating system. Model-card scores and published benchmarks do not prove quality or speed on our hardware and meetings.
- The STT work on `dev` has a real RU functional run. The small and turbo comparison reported in [the transcription notes](../docs/transcription.md) used short synthetic samples; it does not establish human KK/mixed acceptance. Diarization has a standalone synthetic smoke; extraction still has a failed bounded real-case run recorded in [#69](https://github.com/BAITC-Hacks/hack-a58598e0-saint-tibo/issues/69).
- The remote MCP text says `server/discover` is mandatory for the server. The [official 2026-07-28 specification announcement](https://blog.modelcontextprotocol.io/posts/2026-07-28/) describes discovery as optional for clients before another request. Verify exact client/server behavior in a live interoperability test rather than copying that claim into an implementation requirement.
- None of the supplied architecture or security texts is a completed audit of this repository or proof that a third-party integration has been accepted by a real organization.

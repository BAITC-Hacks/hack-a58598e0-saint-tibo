# GitHub-аудит: из чего собрать аналог Granola на Python и TypeScript

**Для твоего проекта я бы первым проверил связку: WXT + пример расширения Recall → Mediabunny → WhisperLiveKit. Для настольного захвата — TypeScript-приложение на electron-vite, а для отдельного Python-агента на Windows/Linux — SoundCard. Backchannel стоит разобрать как пример уже собранного продукта.**

Ниже — **15 репозиториев**, разделённых на готовые приложения, непосредственно встраиваемые библиотеки и дополнительные компоненты.

Проверял README, лицензии, зависимости и отдельные исходные файлы. **Сборку и испытания на всех ОС не проводил**: это аудит пригодности к интеграции, а не подтверждение безотказной работы.

Важная граница: отбирал решения, в которых прикладной код пишется на **Python или TypeScript**. У некоторых остаются нативные зависимости: браузер/Electron, аудиосистема ОС, ONNX, CTranslate2. Отдельно писать и поддерживать Swift, Rust или C++ в предлагаемой схеме не требуется.

## Что смотреть первым

Это мой порядок изучения **под твою задачу**, а не рейтинг популярности.

| Задача                                                  | Первый кандидат                       | Как использовать                                                    |
| ------------------------------------------------------- | ------------------------------------- | ------------------------------------------------------------------- |
| Посмотреть уже собранный продукт на Python + TypeScript | **Backchannel**                       | Разобрать аудиозахват, протокол передачи, запись и обработку        |
| Быстро получить работающую запись вкладки               | **Recall Chrome Recording Extension** | Взять как пример реализации, не как готовую промышленную библиотеку |
| Сделать собственное поддерживаемое расширение           | **WXT**                               | Каркас расширения на TypeScript                                     |
| Сделать настольное приложение на TypeScript             | **electron-vite**                     | Каркас приложения; захват реализовать через API Electron            |
| Получать системный звук из Python на Windows/Linux      | **SoundCard**                         | Встроить в локальный процесс захвата                                |
| Записывать длинные аудиопотоки                          | **Mediabunny**                        | Отдельный слой кодирования и формирования файлов                    |
| Получать расшифровку во время разговора                 | **WhisperLiveKit**                    | Отдельный Python-сервис рядом с FastAPI                             |

Функциональные основания этого выбора разобраны ниже с источниками.

# 1. Backchannel — наиболее интересный пример целого продукта

**GitHub:** [talberthoule/backchannel](https://github.com/talberthoule/backchannel)
**Стек:** Python + TypeScript. **Лицензия:** MIT. **Тип:** готовое приложение, не библиотека. ([GitHub][1])

### Что уже есть

React-интерфейс, FastAPI, PostgreSQL, захват микрофона и дополнительного аудиопотока, передача через WebSocket, расшифровка, разделение говорящих и сохранение записи. Предусмотрены локальные и внешние обработчики; полностью локальная работа требует соответствующей конфигурации моделей и адресов сервисов. ([Backchannel][2])

В исходнике захвата действительно есть **два независимых источника**: микрофон и звук через `getDisplayMedia`. Аудио преобразуется в PCM16 и отправляется с идентификатором дорожки. Документация описывает сохранение смешанной записи и отдельных согласованных по времени файлов микрофона и системного звука. 

### Как встроил бы

Не переносил бы приложение целиком. Разобрал бы три участка:

```text
frontend/src/hooks/useAudioCapture.ts
backend/app/ws/audio_handler.py
backend/app/services/audio_store.py
```

Первый — получение аудиоблоков; второй — приём и распределение между обработчиками; третий — запись. Эти модули и их назначение перечислены в документации проекта. ([Backchannel][2])

Для существующего Angular-фронтенда я бы перенёс логику захвата в Angular-сервис, а не менял интерфейс на React.

### Ограничение

**Это не универсальный нативный рекордер.** Даже настольная поставка использует браузерный захват: упаковка через PyInstaller сама по себе не снимает ограничений `getDisplayMedia`. ([Backchannel][2])

**Мой вывод:** лучший из найденных примеров для изучения всей цепочки, но основу своего продукта я бы собирал из отдельных компонентов.

# 2. Recall Chrome Recording Extension — конкретный пример захвата вкладки на TypeScript

**GitHub:** [recallai/chrome-recording-transcription-extension](https://github.com/recallai/chrome-recording-transcription-extension)
**Язык прикладного кода:** TypeScript. **Лицензия:** ISC указана в `package.json`; отдельный LICENSE перед заимствованием стоит уточнить. **Тип:** демонстрационное расширение. ([GitHub][3])

### Что уже есть

Захват вкладки, запись через `MediaRecorder`, offscreen-документ, возможность добавить микрофон и сохранить WebM. Пример ориентирован на Google Meet. Для самой локальной записи подключение к коммерческому Recall API не требуется. ([github.com][4])

**Ключевая находка аудита:** функция транскрипции здесь **читает субтитры из интерфейса Meet**, а не распознаёт записываемое аудио собственной моделью. Её нельзя считать универсальным распознавателем для Teams, Zoom и Slack. ([GitHub][4])

### Как встроил бы

Использовал бы как исходный пример для своего адаптера:

```text
Действие пользователя
    → захват вкладки
    → отдельный микрофон
    → аудиоблоки
        → локальная запись
        → Python-сервис распознавания
```

Чтение субтитров оставил бы необязательным источником метаданных. Вместо необратимого смешивания источников сохранял бы отдельные дорожки.

### Ограничение

Это небольшой пример, а не готовое ядро для многочасовой записи с восстановлением после сбоя. Сохранение промежуточных фрагментов, повторная отправка, контроль источников и обработка обрывов — отдельная работа.

**Мой вывод:** первый репозиторий, который стоит открыть разработчику именно для браузерного захвата.

# 3. WXT — каркас собственного расширения

**GitHub:** [wxt-dev/wxt](https://github.com/wxt-dev/wxt)
**Язык:** TypeScript. **Лицензия:** MIT. **Тип:** фреймворк расширений. ([GitHub][5])

WXT организует разработку и сборку расширения: точки входа, фоновые компоненты, скрипты страниц, интерфейс и конфигурацию. **Аудиозахват он сам не реализует** — это основа, в которую помещается собственная логика. ([GitHub][5])

### Как встроил бы

Создал бы отдельный пакет расширения на WXT. Из примера Recall взял бы механику захвата, но не его структуру продукта целиком.

Внутри разделил бы:

```text
Управление записью
Аудиозахват
Передачу аудиоблоков
Локальное сохранение
Адаптеры метаданных Meet / Teams / Zoom
```

Существующее веб-приложение при этом остаётся отдельным: расширение не должно тянуть в себя весь основной фронтенд.

**Мой вывод:** брать как зависимость для собственного расширения, а не искать огромный готовый форк с чужим интерфейсом.

# 4. electron-vite — основа настольного агента на TypeScript

**GitHub:** [alex8088/electron-vite](https://github.com/alex8088/electron-vite)
**Язык:** TypeScript. **Лицензия:** MIT. **Тип:** инструменты разработки настольного приложения. ([GitHub][6])

Это не рекордер, а инфраструктура сборки Electron-приложения: основной процесс, preload, интерфейс, перезагрузка при разработке. Есть шаблон `vanilla-ts`, поэтому React для небольшого агента необязателен. ([GitHub][6])

### Как встроил бы

Сделал бы минимальное настольное приложение: выбор источника, индикаторы двух дорожек, начало/остановка, состояние записи и передачи. Захват — через API Electron; формат аудиоблоков — тот же, что у расширения.

На современной macOS Electron использует Core Audio Tap через Chromium. При этом важны разрешения и `NSAudioCaptureUsageDescription`: документация предупреждает, что неправильная конфигурация может дать **неработающий поток без явной ошибки**. ([Electron][7])

### Ограничение

**electron-vite не превращает системное аудио всех ОС в одинаковый API без проблем.** Это способ держать свой код на TypeScript, а не доказательство одинакового поведения Windows, macOS и Linux.

**Мой вывод:** основной путь для настольной части без собственного Swift/C++-модуля. Но проверять захват нужно отдельно на каждой ОС.

# 5. SoundCard — Python-библиотека для устройств и системного аудиовыхода

**GitHub:** [bastibe/SoundCard](https://github.com/bastibe/SoundCard)
**Язык:** Python. **Лицензия:** BSD-3-Clause. **Зависимости:** CFFI, NumPy и аудиоинтерфейсы ОС. ([GitHub][8])

### Что уже есть

Перечисление устройств, запись и воспроизведение аудио. Используются WASAPI на Windows, PulseAudio на Linux и CoreAudio на macOS. Для Windows/Linux предусмотрен захват воспроизводимого звука — loopback. ([GitHub][8])

**Важное ограничение, подтверждённое исходником:** в Mac-адаптере SoundCard системный loopback не реализован. Параметр `include_loopback` приводит к предупреждению, а не к получению системного аудио. Это ограничение библиотеки, не современных API самой macOS. ([github.com][9])

### Как встроил бы

В отдельный локальный Python-процесс:

```text
SoundCard: микрофон + loopback
              → очередь аудиоблоков
                   → запись
                   → распознавание
```

На Windows я бы отдельно проверил многоканальный захват с последующим сведением: README описывает проблему некорректных данных при записи одного канала в некоторых WASAPI-сценариях. ([GitHub][8])

### Ограничение

Не следует трактовать библиотеку как готовый механизм изоляции конкретного Teams-процесса. Базовая модель здесь — устройства и их аудиопотоки.

**Мой вывод:** хороший первый кандидат для Python-агента на Windows/Linux. **Не универсальный ответ для Mac.**

# 6. Mediabunny — запись и формирование медиафайлов на TypeScript

**GitHub:** [Vanilagy/mediabunny](https://github.com/Vanilagy/mediabunny)
**Язык:** TypeScript. **Лицензия:** MPL-2.0. **Тип:** библиотека обработки медиа. ([GitHub][10])

### Что уже есть

Чтение, запись и преобразование медиа, работа с контейнерами и временными метками, потоковый ввод-вывод. Ядро написано на TypeScript; браузерные возможности кодирования зависят от доступных API и кодеков. ([GitHub][10])

**Она не получает звук из Teams или Chrome сама.** Ей передают уже захваченный поток или аудиоданные.

### Как встроил бы

Сделал бы отдельную ветку записи:

```text
Захваченные аудиоблоки
        ├── передача распознавателю
        └── Mediabunny → сохраняемые медиафайлы
```

Здесь я бы проверял потоковую запись без удержания всей встречи в памяти, сохранение временной шкалы и возможность восстановить уже записанную часть после аварийного завершения.

### Ограничение

Библиотека формирования файлов **не заменяет** собственную логику восстановления, индекса фрагментов и подтверждения сохранения.

**Мой вывод:** сильный кандидат для требования «расшифровывать и одновременно нормально записывать», особенно если обычный `MediaRecorder` становится слишком непрозрачным.

# 7. WhisperLiveKit — первый кандидат на Python-сервис потоковой расшифровки

**GitHub:** [QuentinFuxa/WhisperLiveKit](https://github.com/QuentinFuxa/WhisperLiveKit)
**Язык выбираемого компонента:** Python. **Лицензия:** Apache-2.0. **Тип:** библиотека и сервер обработки аудио. ([GitHub][11])

### Что уже есть

Потоковая обработка, управление аудиобуфером, несколько движков распознавания, разделение говорящих и WebSocket API. Сервер поддерживает несколько одновременных сессий. Это **не библиотека захвата системного звука**: аудио нужно подать извне. ([GitHub][11])

В Python-интеграции выделены `TranscriptionEngine` и `AudioProcessor`: общий движок и обработчик конкретной сессии. Это полезное разделение для собственного FastAPI-приложения. ([GitHub][11])

### Как встроил бы

Не загружал бы модель в каждый обычный веб-воркер. Выделил бы самостоятельный процесс или сервис распознавания:

```text
Расширение / настольный агент
             → приём аудио
             → WhisperLiveKit
             → промежуточный и окончательный текст
             → существующий backend
```

Собственную запись аудио оставил бы независимой: остановка распознавателя не должна прекращать архивирование.

### Ограничение

Ресурсы и поддержка языков зависят от выбранного движка и модели. Само наличие потокового API не доказывает качество русского, казахского или смешанной речи.

**Мой вывод:** первый кандидат на сравнительные испытания серверного конвейера. Встроенные клиенты на других языках из репозитория для твоей схемы не нужны.

# 8. RealtimeSTT — альтернатива для встраивания непосредственно в Python

**GitHub:** [KoljaB/RealtimeSTT](https://github.com/KoljaB/RealtimeSTT)
**Язык:** Python. **Лицензия:** MIT. **Тип:** библиотека и сервер. ([GitHub][12])

Есть определение речевой активности, промежуточная и окончательная расшифровка, обработчики событий и несколько движков. Помимо микрофона, библиотека принимает внешние аудиоблоки. В текущей документации также присутствует отдельный FastAPI-сервер с аутентификацией и управлением сессиями — это уже не только микрофонный демонстрационный скрипт. ([GitHub][12])

### Как встроил бы

Для твоей задачи важен режим:

`AudioToTextRecorder(use_microphone=False)` → `feed_audio(...)`.

Так библиотека получает звук от расширения или SoundCard, а не пытается сама открыть микрофон на сервере. ([GitHub][12])

Я бы сравнил её с WhisperLiveKit на одинаковом потоке и выбрал одну основную систему.

### Ограничение

Нужны зависимости выбранного движка и аудиостека. Например, документация установки отдельно указывает PortAudio для ряда окружений. **«Python-библиотека» не означает отсутствие системных зависимостей.** ([GitHub][12])

**Мой вывод:** особенно интересна, когда хочется управлять обработкой через Python-объект и события, а не только через внешний сервис.

# 9. Meet2Notes — готовый Python-помощник как источник реализации

**GitHub:** [estebanstifli/Meet2Notes](https://github.com/estebanstifli/Meet2Notes)
**Язык основного приложения:** Python. **Лицензия:** MIT. **Статус по README:** активная альфа. ([GitHub][13])

### Что уже есть

Одновременная запись микрофона и системного звука, выбор устройств и индикаторы, локальная WAV-запись, отдельные движки предварительной и окончательной расшифровки, разделение говорящих и история встреч. ([GitHub][14])

Для Windows описан WASAPI loopback. На Mac и Linux используются доступные системе виртуальные или monitor-входы — это не собственная универсальная реализация нативного захвата на всех ОС. ([GitHub][14])

### Как встроил бы

Изучил бы управление записью: состояния, выбор двух источников, остановку, отмену обработки, окончательную расшифровку. В существующий проект переносил бы отдельные механизмы, а не всё приложение с его базой и интерфейсом.

### Ограничение

По описанию текущей реализации микрофон и системный звук смешиваются для общей WAV-записи. В твоём варианте я бы дополнительно сохранял оригинальные источники раздельно. ([GitHub][14])

**Мой вывод:** хороший Python-пример близкого продукта, но из-за альфа-статуса не стал бы без проверки делать его фундаментом.

## Что из найденного не стал бы добавлять в новый проект

**`electron-audio-loopback` — не основная рекомендация для актуального Electron.** Репозиторий действительно написан на TypeScript, но автор позиционирует его как обход ограничений Electron 31–38 и прямо пишет, что начиная с 39 эти обходы не нужны. Ставить старую версию Electron ради этой библиотеки я бы не стал. ([GitHub][21])

**Репозитории на обычном JavaScript не включал как замену TypeScript.** Например, близкие по задаче `mic-speaker-streamer` и `electron-mic-speaker-loop` полезны концептуально, но не соответствуют твоему фильтру исходного прикладного кода. ([GitHub][22])

**Готовое приложение не считал автоматически готовым SDK.** Backchannel и Meet2Notes полезнее как источники проверяемых решений, чем как зависимости, которые нужно целиком втащить в существующий продукт.

# Как я встроил бы это в твой проект

Я бы сохранил существующее веб-приложение и добавил **два источника аудио с единым контрактом**, а не создавал четыре независимых рекордера для Meet, Zoom, Teams и Slack.

```text
TypeScript: расширение Chrome
WXT + собственный адаптер по примеру Recall
                         │
                         │ одинаковые аудиоблоки
                         ▼
                Приём аудиосессии
                         ▲
                         │
TypeScript: настольный агент
electron-vite + API захвата Electron

Резервный источник Windows/Linux:
Python-агент на SoundCard
                         │
                         ▼
                Две независимые ветки
              ┌──────────┴──────────┐
              ▼                     ▼
       Сохранение записи     Потоковая расшифровка
       и её фрагментов       WhisperLiveKit
                             ИЛИ RealtimeSTT
                                    │
                                    ▼
                         Существующий FastAPI:
                         встречи, текст, поручения
```

Это **предлагаемая мной композиция**, а не готовый комплект, который все перечисленные авторы уже протестировали совместно.

### Что сделал бы общим

Контракт аудиоблока: сессия, источник, порядковый номер, время захвата, частота, число каналов и данные. Тогда браузерный и настольный захват можно менять, не переписывая распознавание и хранение.

Сохранение отделил бы от обработки. Если модель перегружена, запись должна продолжаться; если пропала сеть — локальные фрагменты должны оставаться доступными для повторной передачи.

### Что не стал бы усложнять

**Не подключал бы одновременно WhisperLiveKit, RealtimeSTT и WhisperLive.** Это кандидаты на одну роль. `faster-whisper` при этом может быть внутренним движком выбранной системы, а не ещё одним сервисом сверху.

**Не переносил бы React-интерфейсы донорских приложений в существующий Angular-проект.** Переносить стоит аудиологику и протоколы, а не чужую архитектуру фронтенда.

**Не начинал бы с WebRTC только потому, что речь об аудио.** Сначала проверил бы более простой обмен аудиоблоками через WebSocket; `aiortc` оставил бы для конкретной транспортной потребности.

## Итоговый выбор

**Для браузерной первой версии:** WXT + механика захвата из Recall + независимая запись через Mediabunny + WhisperLiveKit.

**Для настольного варианта:** electron-vite и собственный небольшой TypeScript-адаптер захвата. SoundCard — отдельный Python-путь для Windows/Linux, но не обещание универсального Mac-loopback.

**Для изучения уже собранного продукта:** Backchannel первым, Meet2Notes вторым.

**Самый существенный результат аудита:** среди проверенных решений я не нашёл одной готовой Python/TypeScript-библиотеки, которая одновременно закрывает захват вкладок, нативные приложения всех ОС, раздельные дорожки, устойчивую запись и распознавание. Практичный путь — собрать несколько узких компонентов с общим аудиоконтрактом, а не выбирать один «аналог Granola» и наследовать все его ограничения.

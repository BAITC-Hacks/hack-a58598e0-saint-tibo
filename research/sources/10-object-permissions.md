## Вывод

Для этой системы я рекомендую **роли с ограниченной областью действия + объектные разрешения + единый серверный модуль авторизации**, а PostgreSQL RLS использовать как дополнительный барьер между организациями.

Не должно существовать правила «пользователь — секретарь, значит может читать встречи». Должно существовать правило: **«пользователь назначен секретарём встречи X в организации A и может выполнить действие Y над конкретным материалом этой встречи»**.

Веб-приложение, REST API, боты и MCP должны обращаться к одним прикладным операциям. Канал может дополнительно ограничивать доступ, но не расширять его. Проверять разрешения нужно при каждом обращении к защищённому объекту, а не только при входе или открытии страницы. Это соответствует рекомендациям OWASP по запрету по умолчанию и проверке каждого запроса. ([OWASP Cheat Sheet Series][1])

**Для пилота отдельный сервер авторизации не обязателен.** Общего модуля в FastAPI, таблиц назначений в PostgreSQL, RLS и защищённой выдачи файлов достаточно, чтобы реализовать требуемую модель без лишней инфраструктуры.

## 1. Какие модели подходят

Здесь нужны три разных механизма:

**RBAC — права через роли.** Например, секретарь может редактировать черновик протокола.

**Объектная авторизация — права на конкретный объект.** Этот пользователь является секретарём именно этой встречи, а не всех встреч организации.

**Проверка условий — ограничения поверх разрешений.** Например, утверждать можно только назначенную версию протокола, а заблокированный пользователь не может воспользоваться ранее выданными правами.

### Практичные варианты реализации

| Вариант                                                 | Что даёт                                                                                                             | Ограничения и применимость                                                                                                                                                                                                                                               |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Общий модуль Python + таблицы назначений PostgreSQL** | Фиксированные роли, связи «пользователь → встреча/поручение», дополнительные разрешения на материалы                 | **Мой выбор для пилота.** Права и бизнес-данные можно менять в одной транзакции. Нужны общие проверки, а не разрозненные `if role == ...`                                                                                                                                |
| **PyCasbin**                                            | Готовая библиотека для ACL, RBAC, ABAC; роли могут различаться между организациями                                   | Подходит, если команда предпочитает описывать правила отдельной моделью. При хранении загруженной политики в памяти необходимо отдельно обеспечить актуальность разрешений во всех процессах. Поддержка нужных моделей подтверждена документацией проекта. ([GitHub][2]) |
| **OpenFGA**                                             | Роли и разрешения через связи между пользователями и объектами; проверяется разрешение на объект, а не название роли | Хороший кандидат при усложнении связей и появлении нескольких независимых сервисов. Потребуется согласовать изменения бизнес-данных и разрешений. ([OpenFGA][3])                                                                                                         |
| **SpiceDB**                                             | Объектные отношения и явное управление свежестью проверок через уровни согласованности и ZedToken                    | Полезен, когда общая авторизация становится отдельной инфраструктурной задачей. Для небольшого пилота, на мой взгляд, избыточен. ([AuthZed][4])                                                                                                                          |

**RLS не заменяет эту модель.** Он ограничивает доступ к строкам PostgreSQL, но сам по себе не решает, какие поля вернуть исполнителю, можно ли утвердить протокол или выдать файл из объектного хранилища. ([PostgreSQL][5])

У внешних движков отдельно важен отзыв доступа. OpenFGA при включённом кэшировании может возвращать результат из кэша; `HIGHER_CONSISTENCY` обращается непосредственно к базе. В SpiceDB для свежести используются соответствующие режимы проверки и ZedToken. Нельзя подключить движок и считать немедленный отзыв автоматически обеспеченным. ([OpenFGA][6])

## 2. Предлагаемая модель ролей и объектов

Ниже — проект политики именно для вашей системы.

### Область действия роли

| Роль                          | Где назначается                                      | Что не следует из назначения                                      |
| ----------------------------- | ---------------------------------------------------- | ----------------------------------------------------------------- |
| Владелец                      | На конкретную встречу                                | Владение всеми встречами организации                              |
| Секретарь                     | На конкретную встречу                                | Право управлять учётными записями или читать другие встречи       |
| Исполнитель                   | На конкретное поручение                              | Доступ ко всей встрече, транскрипту и другим поручениям           |
| Куратор                       | На явно заданные поручения или область контроля      | Доступ ко всем материалам контролируемых встреч                   |
| Утверждающий                  | На конкретный процесс утверждения и версию протокола | Доступ ко всем черновикам, оригиналам и будущим версиям           |
| Администратор учётных записей | В пределах организации                               | Доступ к содержанию встреч и назначение себе содержательных ролей |

Один человек может иметь несколько назначений. Например, быть владельцем встречи A1 и исполнителем поручения из A2. Эти назначения не должны превращаться в общую роль «владелец» на уровне пользователя.

### Материалы встречи — разные защищаемые объекты

Не стоит ограничиваться единственным флагом `can_read_meeting`. Нужны отдельные разрешения на оригинальное аудио, обезличенную копию, транскрипт, поручение, выписку, версию протокола и экспорт.

Принцип наследования предлагаю такой:

> **Доступ к встрече может давать доступ к определённым дочерним материалам по явному правилу. Доступ к поручению никогда автоматически не даёт доступ вверх — ко всей встрече.**

Обезличенная копия не становится публичной. У неё остаются организация, собственный идентификатор, версия и разрешённая аудитория. Расширять аудиторию производного материала следует только через отдельную процедуру выпуска разрешённой копии или выписки.

Исполнителю лучше отдавать отдельное представление поручения: текст, срок, разрешённые комментарии, его отчёт и специально опубликованный контекст. Не полный объект встречи с полями, которые интерфейс «просто не показывает»: OWASP отдельно выделяет избыточную выдачу и изменение свойств объектов как класс ошибок авторизации. ([OWASP API Security Top 10][7])

### Матрица прав

**«Да» означает только назначенный объект. «Отдельно» означает дополнительное объектное разрешение.** Таблица описывает базовую роль без дополнительных совмещений.

| Данные или действие                | Владелец                          | Секретарь             | Исполнитель             | Куратор                  | Утверждающий                      | Администратор |
| ---------------------------------- | --------------------------------- | --------------------- | ----------------------- | ------------------------ | --------------------------------- | ------------- |
| Оригинальное аудио                 | Отдельно                          | Отдельно              | Нет                     | Нет                      | Отдельно                          | Нет           |
| Обезличенная запись                | Да                                | Да                    | Выданная копия          | Выданная копия           | Выданная копия                    | Нет           |
| Полный транскрипт                  | Да                                | Да                    | Нет                     | Нет                      | Отдельно                          | Нет           |
| Просмотр поручений                 | Все во встрече                    | Все во встрече        | Свои                    | Назначенные для контроля | В составе утверждаемого протокола | Нет           |
| Изменение поручений                | В пределах процесса               | В пределах процесса   | Статус и отчёт по своим | Контроль и комментарии   | Нет                               | Нет           |
| Просмотр протокола                 | Да                                | Да                    | Своя выписка            | Выданная выписка         | Назначенная версия                | Нет           |
| Редактирование черновика протокола | Да                                | Да                    | Нет                     | Нет                      | Нет                               | Нет           |
| Утверждение протокола              | Нет                               | Нет                   | Нет                     | Нет                      | Да                                | Нет           |
| Выдача доступа к встрече           | В пределах разрешённых полномочий | Нет                   | Нет                     | Нет                      | Нет                               | Нет           |
| Управление учётными записями       | Нет                               | Нет                   | Нет                     | Нет                      | Нет                               | Да            |
| Экспорт                            | Разрешённые материалы             | Разрешённые материалы | Выписка своих поручений | Отчёт по своей области   | Назначенный протокол              | Нет           |

Для экспорта нужны отдельные действия `export.create` и `export.download`, а также проверка разрешённого состава. Наличие права читать один материал не должно разрешать выгрузку всего комплекта.

**Выдача разрешений тоже является защищённой операцией.** Владелец не должен назначать произвольные роли или выдавать полномочия, которых сам не вправе делегировать. Межорганизационное предоставление доступа в пилоте лучше запретить.

Для утверждения предлагаю фиксировать версию и содержимое документа. После изменения создаётся новая версия, а не незаметно меняется уже утверждённая. Если требуется разделение обязанностей, автор версии не может утвердить её сам, даже имея обе роли.

### Администратор учётных записей: важная оговорка

Недостаточно убрать ему кнопку «Открыть встречу». Нужно также исключить обход через смену владельца, выдачу себе роли секретаря, создание токена от имени другого пользователя или подмену его внешней идентичности.

Если администратор может установить другому пользователю известный пароль и войти за него, разделение прав фактически разрушено. В предлагаемой модели администратор управляет членством и состоянием учётной записи в своей организации, но не получает возможность незаметного входа от чужого имени.

Это ограничение относится к **прикладному администратору**. Защита от администратора сервера или PostgreSQL superuser — отдельная граница доверия: superuser обходит RLS. ([PostgreSQL][5])

## 3. Где должны применяться проверки

### Общий путь для всех каналов

```text
Веб / REST / бот / MCP
    -> проверка подлинности пользователя и вызывающего приложения
    -> доверенный контекст запроса
    -> общая прикладная операция
    -> объектная проверка разрешений
    -> разрешённая выборка или изменение
    -> PostgreSQL с RLS / защищённая выдача файла
```

Общая точка применения — **прикладной слой FastAPI**, который выполняет операции над встречами, поручениями и материалами. Не React, не API-шлюз и не отдельно написанные проверки в каждом боте.

Условный интерфейс:

```text
authorize(context, action, resource, representation)
```

Решение должно учитывать:

```text
РАЗРЕШИТЬ =
    пользователь и его полномочия активны
    AND членство в выбранной организации активно
    AND организация запроса совпадает с организацией объекта
    AND вызывающему приложению разрешена операция
    AND есть объектное разрешение на действие и представление
    AND выполнены ограничения процесса и политики
```

### Что делает FastAPI

Через `Depends`/`Security` удобно получать проверенную сессию, пользователя, приложение и ограничения токена. Но `scope=meetings:read` не означает доступ к любой встрече: после него всё равно нужна проверка конкретного объекта. Документация FastAPI прямо оставляет фактическое применение требований авторизации коду приложения. ([FastAPI][8])

В пилоте я бы сделал так:

**Обработчики каналов не читают бизнес-таблицы напрямую.** Они вызывают операции вроде `read_task`, `update_task_progress`, `read_protocol_version`, `request_export`.

**Проверка и чтение связаны.** Объект выбирается по организации и ID, после чего проверяются актуальные назначения; по возможности ограничение включается непосредственно в SQL-запрос.

**Списки используют ту же семантику прав, что и единичное чтение.** Ограничения применяются до подсчёта количества, пагинации и формирования поисковых фрагментов. Нельзя получить все встречи, а потом отфильтровать их в браузере.

**Поля изменений перечислены явно.** Исполнитель может отправить отчёт, но не изменить через общий `PATCH` поля `organization_id`, `assignee_id`, `owner_id`, `classification`, `approved_by`.

Подмена ID остаётся опасной даже при UUID. OWASP относит к объектной авторизации проверки идентификаторов в пути, параметрах, заголовках и теле запроса — тип идентификатора сам по себе проблему не решает. ([owasp.org][9])

Отдельная тонкость: при чтении поручения нужно проверить принадлежность его встречи нужной организации, **но не требовать от исполнителя права читать всю встречу**. Иначе правильное разделение доступа перестанет работать.

## 4. Минимальные данные для решения о доступе

Для пилота достаточно следующего набора.

| Категория             | Минимальные данные                                                                                                                            |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| **Субъект**           | Внутренний `principal_id`, тип «человек/сервис», активность; идентификатор и актуальное состояние сессии или API-полномочия                   |
| **Организация**       | `organization_id`, членство субъекта, состояние членства; организационные административные роли                                               |
| **Объект**            | ID, организация, тип, родительская связь, вариант материала, версия, состояние процесса                                                       |
| **Назначения**        | Субъект, объект, роль или разрешённое действие; срок действия и состояние отзыва                                                              |
| **Контекст операции** | Действие, вызывающее приложение, ограничения делегирования, запрошенное представление; при необходимости доверенные признаки MFA и устройства |
| **Экспорт и задание** | Организация, инициатор, исполнитель-сервис, состав источников и их версий, профиль результата, состояние задания                              |

Текст транскрипта и содержимое аудио для решения о доступе не нужны. Достаточно метаданных и назначений.

Организацию, роль, автора запроса и признак «я администратор» нельзя брать из тела запроса как доказательство. Клиент может выбрать организацию, но сервер должен проверить членство в ней. Атрибуты объекта берутся из базы.

### Структура PostgreSQL

Я бы использовал отдельные таблицы членства, назначений на встречи, назначений на поручения и дополнительных разрешений на материалы. У всех принадлежащих организации сущностей должен быть обязательный `organization_id`.

Связи нужно защищать составными внешними ключами:

```text
tasks(organization_id, meeting_id)
    -> meetings(organization_id, id)

assets(organization_id, meeting_id)
    -> meetings(organization_id, id)

meeting_roles(organization_id, principal_id)
    -> organization_memberships(organization_id, principal_id)
```

Так база не позволит привязать поручение организации A к встрече организации B. PostgreSQL поддерживает составные внешние ключи; в документации есть и пример с принадлежностью пользователей и записей одному tenant. ([PostgreSQL][10])

### RLS как межорганизационный барьер

Пример **только изоляции организаций**, не полной объектной политики:

```sql
ALTER TABLE app.tasks ENABLE ROW LEVEL SECURITY;
ALTER TABLE app.tasks FORCE ROW LEVEL SECURITY;

CREATE POLICY tasks_organization_isolation
ON app.tasks
FOR ALL
TO app_runtime
USING (
    organization_id =
    NULLIF(current_setting('app.organization_id', true), '')::uuid
)
WITH CHECK (
    organization_id =
    NULLIF(current_setting('app.organization_id', true), '')::uuid
);
```

Для каждой транзакции сервер устанавливает проверенный контекст через параметризованный `set_config(..., true)`. Последний аргумент ограничивает настройку текущей транзакцией — это важно при повторном использовании соединений. ([PostgreSQL][11])

Рабочая роль приложения не должна быть superuser, иметь `BYPASSRLS`, владеть таблицами или иметь возможность переключиться на обходящую RLS роль. Политики нужно проверять и на чтение, и на запись. При добавлении новых политик учитывать, что разрешающие политики по умолчанию объединяются через `OR`. ([PostgreSQL][5])

**Ограничение:** этот RLS остановит доступ к другой организации при забытом SQL-фильтре, но не остановит исполнителя от чтения чужого поручения внутри своей организации, если забыта объектная проверка. За это отвечает общий прикладной слой.

И ещё: контекст, устанавливаемый приложением, не является защитой от полностью скомпрометированного приложения, способного выполнять произвольный SQL.

## 5. Отзыв доступа, медиа и Range-запросы

### Сначала зафиксировать гарантию

Предлагаю такое проверяемое требование:

> **После успешной фиксации отзыва любой новый запрос должен принимать решение по обновлённым правам, включая запросы со старой сессией, API-токеном, адресом файла или идентификатором экспорта.**

Для этого в пилоте стоит проверять актуальное членство и назначения в основном PostgreSQL при каждом защищённом обращении. Не хранить положительные решения между запросами.

Проверки подписи и срока JWT недостаточно для отражения последующего изменения прав. OWASP отдельно рассматривает расхождение между состоянием JWT и актуальным состоянием пользовательской сессии. ([OWASP Cheat Sheet Series][12])

Для проверки прав нужны свежие запросы, а не долго живущий снимок транзакции: PostgreSQL `READ COMMITTED` получает снимок на начало каждого запроса, а `REPEATABLE READ` сохраняет прежний снимок в рамках транзакции. ([PostgreSQL][13])

Нужно различать три операции отзыва:

**Снять назначение.** Например, убрать роль секретаря. Другие независимо выданные права могут остаться.

**Полностью закрыть встречу человеку.** Удалить все действующие пути доступа к ней и соответствующим материалам либо применить явный объектный запрет с приоритетом над разрешениями.

**Отключить членство в организации.** Прекратить весь доступ к её объектам, не затрагивая независимое членство в другой организации.

### Почему прямые подписанные ссылки не подходят

Подписанная ссылка S3 работает с полномочиями подписавшего её субъекта, может использоваться повторно и фактически является bearer-полномочием. Удаление пользовательского назначения в вашей базе само по себе не отзывает такую ссылку. Короткий срок только ограничивает окно доступа. ([docs.aws.amazon.com][14])

Поэтому для заявленной гарантии рекомендую:

```text
GET /organizations/{org}/assets/{asset}/content
    -> актуальная объектная проверка
    -> поиск точного объекта хранения на сервере
    -> чтение из закрытого хранилища
    -> передача разрешённых байтов клиенту
```

Клиент не получает прямой адрес, позволяющий обойти проверку. Внутреннее перенаправление на файловый сервер допустимо, если его внутренний маршрут недоступен извне и каждый новый внешний запрос снова авторизуется.

### Как обрабатывать Range

Каждый новый `GET` с `Range` проходит ту же проверку, что и скачивание целиком. Нельзя авторизовать только первое нажатие Play.

Порядок: **аутентификация → авторизация объекта и варианта → обработка HTTP-условий и диапазона → выдача**. Это касается также `HEAD`, `If-Range` и `If-None-Match`. Условный запрос не должен превратить отказ в `304` или раскрыть размер недоступного файла через `416`. Правила HTTP предусматривают выполнение обычных проверок до оценки условий запроса. ([IETF HTTP Working Group][15])

Starlette `FileResponse` поддерживает Range и ответы `206`/`416`, но эту поддержку нужно использовать уже после своей проверки разрешений. ([Starlette][16])

### Кэш и уже начатая передача

Для закрытых материалов в пилоте я бы отключил общий HTTP-кэш и возвращал `Cache-Control: no-store`. Прикладной кэш допустим только после авторизации; пользовательские выборки должны учитывать организацию, субъекта и остальные параметры, меняющие результат. Разделение ключей не заменяет проверку доступа. ([OWASP Cheat Sheet Series][17])

**Новый запрос после отзыва и уже начатый поток — разные случаи.** Остановка текущего потока требует периодической перепроверки и закрытия соединения. Уже отправленные или находящиеся в буфере байты отозвать нельзя.

Также нельзя обещать «можно слушать оригинал, но невозможно его сохранить»: для воспроизведения клиент уже получает аудиоданные. Запрет кнопки скачивания — не защита от копирования. Даже `no-store` не является гарантией против недобросовестного клиента или кэша. ([IETF HTTP Working Group][18])

## 6. Фоновые задания и экспорт

### В очередь передаётся поручение выполнить работу, а не вечное разрешение

В сообщении достаточно идентификатора задания. Организацию, инициатора, объекты и разрешённый профиль worker должен восстанавливать из доверенной записи задания.

Для пользовательского экспорта предлагаю проверки в четырёх местах:

1. При постановке — разрешены операция, источники и профиль.
2. При начале выполнения — разрешения ещё действуют.
3. Перед публикацией — результат соответствует разрешённому составу, доступ не отозван.
4. При каждом скачивании — получатель сейчас вправе получить этот результат.

Повторная проверка отложенных операций соответствует рекомендациям OWASP для многопользовательских очередей; общая очередь сама по себе не обеспечивает изоляцию организаций. ([OWASP Cheat Sheet Series][17])

**Не все задания должны зависеть от сессии инициатора.** Распознавание записи для организации может быть самостоятельной системной операцией и продолжаться после увольнения загрузившего её человека. Но такой worker действует по явно разрешённому заданию организации, а не под универсальным флагом `is_system=true`.

Боту, MCP-серверу и worker нельзя выдавать одинаковую неограниченную учётную запись «для удобства интеграций».

### Экспорт — самостоятельный защищённый объект

У экспорта предлагаю сохранять:

```text
организацию
инициатора и разрешённого получателя
профиль экспорта
список источников, версий и представлений
состояние и расположение результата
```

Условие скачивания:

```text
разрешено читать объект экспорта
AND разрешена операция export.download
AND сейчас разрешены все материалы, включённые в файл
```

Проверки только `export.created_by == current_user` недостаточно.

Если пользователь потерял доступ к одному из включённых материалов, старый архив целиком больше не выдаётся. Можно сформировать новый экспорт из актуального разрешённого набора.

Для специально опубликованной выписки источником проверки может быть сама выписка с собственной политикой, а не закрытый оригинал. Иначе исполнитель никогда не сможет получить законно выданную ему часть документа.

**Экспорт строится из серверного разрешённого представления.** Нельзя выгружать полный PDF/DOCX и скрывать запрещённые разделы визуально. Нужно исключать их также из приложений, комментариев, истории изменений и метаданных результата.

## 7. Боты и MCP

### Боты

Для команды боту нужно установить две личности: **какая интеграция вызывает систему и какой пользователь стоит за командой**.

Связку внешней учётной записи с внутренним пользователем следует хранить по устойчивым идентификаторам платформы и рабочей области, а не по отображаемому имени. Подлинность входящего события проверяется механизмом платформы. Например, Slack предусматривает подпись запроса и проверку временной метки против повторного воспроизведения. ([Slack Developer Docs][19])

Далее действуют обычные объектные права пользователя плюс ограничения интеграции.

**Право пользователя читать материал не означает право отправить его в групповой чат.** Получатели сообщения могут не иметь этого права. Для пилота я рекомендую уведомления без содержимого и ссылки в веб-приложение; выдачу выписок — только в явно разрешённые назначения.

### MCP

MCP-авторизация на транспортном уровне не заменяет ваши объектные проверки. Для HTTP-транспорта спецификация требует авторизацию каждого запроса и проверку того, что токен предназначен этому MCP-серверу. ([Model Context Protocol][20])

Практическая схема:

```text
MCP-клиент
    -> MCP-сервер проверяет своё входящее полномочие
    -> устанавливает пользователя и ограничения делегирования
    -> вызывает общую прикладную операцию
    -> получает только разрешённое представление
```

`user_id` в аргументах инструмента не может определять, от чьего имени выполняется запрос. Пользователь устанавливается из проверенного контекста.

Если MCP вынесен в отдельный сервис, для внутреннего API нужно отдельное предназначенное ему полномочие с сохранением проверенной делегации. Текущая спецификация прямо запрещает просто передавать полученный MCP-токен в другой API. ([Model Context Protocol][21])

Проверки нужны не только для `tools/call`, но и для чтения ресурсов, списков, поиска и возвращаемых ссылок. Знание `Mcp-Session-Id` не должно заменять аутентификацию. ([Model Context Protocol][22])

Для пилота не стоит предоставлять агентам универсальный SQL-инструмент или чтение файлов по произвольному пути. Лучше узкие операции: «получить моё поручение», «записать отчёт», «получить разрешённую выписку».

Отдельная граница: **ответ MCP и сообщение бота уже являются копией данных у получателя**. Отзыв остановит последующие обращения к серверу, но не удалит ранее выданный текст из переписки или контекста модели. Поэтому допустимость конкретного клиента и места передачи данных должна проверяться отдельно от права пользователя читать встречу.

## 8. План отрицательных тестов

Это план испытаний, а не утверждение, что конкретная реализация уже проверена.

### Тестовые данные

Создать организации **A и B**, минимум по две встречи в каждой, все перечисленные типы материалов и пользователей каждой роли. Добавить пользователя, который состоит в обеих организациях, но имеет разные роли.

В аудио, транскрипты, поручения и экспорт поместить различимые контрольные данные. У исполнителя должно быть доступно одно поручение, но недоступны соседнее поручение и полный транскрипт той же встречи.

Тесты выполнять через реальные внешние маршруты и адаптеры, с настоящим PostgreSQL и рабочими ролями БД. Проверки политики нельзя подменять заглушкой «всегда разрешено».

### A. Организации, роли и поля

| Проверка                                                                                                      | Ожидаемый результат                                                                  |
| ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Пользователь A подставляет ID встречи, поручения, аудио, протокола или экспорта B                             | Нет данных и изменений независимо от того, откуда взят ID: путь, параметры, тело     |
| Подмена организации или пользователя в заголовках и теле                                                      | Не меняет установленную сервером личность и разрешённую область                      |
| Пользователь — владелец в A и исполнитель в B                                                                 | Права владельца не применяются к B                                                   |
| Вложенный URL содержит встречу A1 и поручение из A2 либо B1                                                   | Несогласованные родительские связи отклоняются                                       |
| Создание поручения A со ссылкой на встречу или исполнителя B                                                  | Операция отклоняется; межорганизационная связь не появляется в БД                    |
| Администратор учётных записей запрашивает содержимое, поиск по транскриптам или экспорт                       | Содержимое недоступно                                                                |
| Администратор пытается назначить себя владельцем, выдать токен от чужого имени или перепривязать идентичность | Повышение полномочий отклоняется                                                     |
| Исполнитель читает поручение с расширением связанных объектов                                                 | Нет полного транскрипта, других поручений, скрытых комментариев и ссылок на оригинал |
| Исполнитель отправляет `PATCH` с заменой организации, ответственного, срока или утверждающего                 | Разрешены только предусмотренные для исполнителя поля и переходы                     |
| Автор версии пытается её утвердить; утверждающий подставляет другую версию                                    | Нарушение разделения обязанностей или области назначения отклоняется                 |
| Поиск, количество результатов, пагинация, автодополнение и пакетный запрос содержат недоступные объекты       | Недоступное не появляется в выдаче, фрагментах и счётчиках                           |

Для REST можно возвращать одинаковый `404` для отсутствующего и недоступного объекта, не раскрывая его существование. Для недостаточного права на действие над уже видимым объектом допустим `403`. В MCP важна эквивалентная семантика отказа, а не буквальное совпадение HTTP-кода.

### B. Медиа, Range и старые ссылки

| Проверка                                                                                                     | Ожидаемый результат                                                                          |
| ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| Чужое аудио запрашивается обычным `GET` и `HEAD`                                                             | Нет аудиобайтов, имени исходника, его размера и других защищённых метаданных                 |
| Чужое аудио запрашивается с `Range: bytes=0-1023`, `bytes=0-`, `bytes=-1024`                                 | Отказ, а не частичный или полный файл                                                        |
| Для чужого аудио передаётся некорректный или выходящий за границы диапазон                                   | Ошибка диапазона не раскрывает настоящий размер файла                                        |
| После разрешённого `206` отзывается доступ, затем запрашивается следующий диапазон                           | Следующий запрос отклоняется                                                                 |
| После отзыва используются прежние `If-Range`, `If-None-Match`, `ETag`                                        | Нет обхода через `200`, `206` или `304`                                                      |
| ID обезличенной копии заменяется на ID оригинала; запрашивается предыдущая версия                            | Проверяются точный вариант и версия материала                                                |
| Повторяется адрес из истории браузера, экспорта или ответа MCP; вызывается внутренний путь файлового сервера | Нет обхода общей авторизации                                                                 |
| Отзыв происходит во время уже открытого потока                                                               | Поведение соответствует отдельно принятой политике остановки потока; новые запросы запрещены |

### C. Задания, боты и MCP

| Проверка                                                                                           | Ожидаемый результат                                                       |
| -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Экспорт поставлен в очередь, доступ отозван до начала выполнения                                   | Пользовательский результат не создаётся или не публикуется                |
| Доступ отозван во время формирования либо после готовности экспорта                                | Результат не выдаётся инициатору                                          |
| В задании подменены организация, инициатор, источники или путь результата                          | Worker сверяется с доверенной записью; подмена не расширяет права         |
| Повторяется отменённое задание или совпадающий ключ повторного запроса другой организации          | Не возвращается чужой результат и не восстанавливается отменённая выдача  |
| Исполнитель просит экспортировать встречу целиком вместо своего поручения                          | Отказ до чтения и упаковки запрещённых материалов                         |
| Боту передаётся чужой ID, неподписанное событие, повтор события или неверная внешняя привязка      | Нет выдачи или изменения данных                                           |
| Разрешённый пользователю документ запрашивается для отправки в посторонний чат                     | Отправка отклоняется либо заменяется безопасной ссылкой согласно политике |
| MCP вызывается с токеном другой аудитории, без токена, только с ID сессии или поддельным `user_id` | Запрос не получает пользовательских полномочий                            |
| Через MCP выполняется прямой вызов инструмента, отсутствующего в интерфейсе клиента                | Проверка всё равно выполняется; видимость инструмента не является защитой |
| В тексте поручения находится инструкция агенту прочитать чужую встречу                             | Серверная авторизация не позволяет исполнить такой вызов                  |

### D. Отзыв и инфраструктура

| Проверка                                                                                              | Ожидаемый результат                                                                        |
| ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| После фиксации отзыва повторяется запрос со старым JWT, cookie или делегацией                         | Новый запрос учитывает отзыв без ожидания истечения токена                                 |
| Запросы идут в разные процессы FastAPI/MCP и после перезапуска worker                                 | Отзыв действует одинаково во всех процессах                                                |
| Соединение PostgreSQL используется последовательно для A, B и запроса без контекста, включая rollback | Контекст A не переносится в B; отсутствие контекста не открывает строки                    |
| Запрос намеренно выполнен без фильтра организации под рабочей ролью                                   | RLS не возвращает строки другой организации                                                |
| База или механизм проверки прав недоступны                                                            | Ошибка доступности, например `503`, без выдачи содержимого и без разрешения «по умолчанию» |
| Отключено членство пользователя только в A                                                            | Доступ к A прекращается; независимые права в B не изменяются                               |

**Обязательно нужны и положительные контрольные тесты.** Система, которая запрещает всё, отрицательные проверки пройдёт, но рабочей не будет.

Для проверки одинаковости каналов использовать общий набор сценариев: один субъект, одно действие, один объект, одинаковые ограничения делегирования. Результат должен совпадать; дополнительные ограничения конкретного канала могут только сузить доступ.

## 9. Что реализовать уже в пилоте

| Обязательно до работы с реальными закрытыми данными | Минимальный объём                                                                                          |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| **Общая объектная авторизация**                     | Один прикладной слой для REST, веба, ботов, MCP и пользовательских заданий                                 |
| **Изоляция организаций**                            | Обязательный `organization_id`, составные связи, RLS, отдельная рабочая роль БД                            |
| **Разделение содержимого**                          | Оригинал, обезличенная копия, транскрипт, поручение, выписка, версия протокола и экспорт                   |
| **Отделение администрирования**                     | Администратор учётных записей без прав на содержимое и без скрытого входа от чужого имени                  |
| **Защищённая выдача файлов**                        | Повторная проверка каждого скачивания и Range-запроса; отсутствие прямого обходного URL                    |
| **Актуальный отзыв**                                | Проверки текущего состояния в PostgreSQL; без положительного кэша между запросами                          |
| **Безопасные задания и интеграции**                 | Сохранённый инициатор, организация, состав источников; повторная проверка перед выдачей                    |
| **Проверки и аудит**                                | Две организации в автоматических тестах; журнал выдачи прав, отзыва, чтения оригиналов, экспорта и отказов |

В журнале достаточно фиксировать субъекта, вызывающий сервис, организацию, объект, действие, результат, причину и версию политики. Не нужно записывать содержимое транскриптов, токены или подписанные ссылки. Администратору учётных записей следует показывать только разрешённую административную часть журнала.

**Можно отложить:** отдельный OpenFGA/SpiceDB, произвольный конструктор ролей, сложное наследование через подразделения, межорганизационный обмен и распределённый кэш разрешений.

**Итоговый критерий готовности пилота:** подмена любого идентификатора не расширяет доступ; исполнитель получает только разрешённое представление своего поручения; администратор учётных записей не читает содержимое; после отзыва следующий запрос — через любой канал, к медиа или экспорту — проверяется по новым правам.

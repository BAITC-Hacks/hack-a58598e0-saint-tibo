# Удалённый MCP для системы протоколирования совещаний

**Рекомендация: отдельный, узкий MCP-адаптер на FastMCP, внешний корпоративный OAuth-сервер и общий с REST слой бизнес-операций.** Не превращать OpenAPI-схему в каталог инструментов автоматически и не пересылать пользовательский MCP-токен в REST.

Главный результат исследования: **поддержка «Streamable HTTP + OAuth» ещё не означает совместимость всего подключения**. Отдельно проверяются версия MCP, discovery, регистрация клиента, выдаваемый `audience`, обновление токена, обработка `401/403` и поведение после потерянного ответа.

Ниже — срез на **23 сентября 2026 года**, подтверждённые документацией и кодом возможности клиентов, рекомендуемая архитектура и прототип. **В прототипе выполнены 39 локальных тестов бизнес-логики, JWT, REST и защиты от повторов. Сквозной OAuth/MCP-прогон с настоящим IdP и настольными клиентами не выполнен** — для него подготовлены код и сценарии.

## 1. Важное изменение: актуальный MCP уже не такой, как в руководствах 2025 года

Актуальная опубликованная редакция — **2026-07-28**. Она существенно меняет жизненный цикл удалённого подключения. ([Model Context Protocol][1])

| Аспект                   | Предыдущая схема Streamable HTTP                | Редакция 2026-07-28                                                        |
| ------------------------ | ----------------------------------------------- | -------------------------------------------------------------------------- |
| Инициализация            | `initialize` → `notifications/initialized`      | Этот обмен удалён; версия и возможности передаются с запросами             |
| Сессия                   | Возможен `Mcp-Session-Id`                       | Протокольные сессии удалены                                                |
| Обнаружение возможностей | Через инициализацию                             | Добавлен обязательный для сервера `server/discover`                        |
| Длительные уведомления   | GET/SSE и подписки прежней модели               | `subscriptions/listen` через POST                                          |
| Восстановление потока    | Возможна доставка событий через `Last-Event-ID` | Возобновление SSE и повторная доставка удалены; запрос отправляется заново |

Это изменения протокола, а не просто настройки сервера. ([Model Context Protocol][1])

Современный Streamable HTTP также использует заголовки `MCP-Protocol-Version`, `Mcp-Method` и, для именованных операций, `Mcp-Name`. Значения заголовков и тела запроса должны согласовываться. Прокси перед сервером не должен их удалять или подменять. ([Model Context Protocol][2])

**Практическое решение:** поддерживать современную редакцию и прежний режим через библиотеку, а не писать собственную совместимость. FastMCP 4 заявляет обслуживание обеих схем; его клиент автоматически выбирает протокол и позволяет принудительно проверить прежний режим через `mode="legacy"`. ([FastMCP][3])

Для воспроизводимого стенда я зафиксировал:

```text
fastmcp==4.0.5
mcp==2.2.0
```

Это версии из проверенных релизов: FastMCP 4.0.5 опубликован 17 сентября, Python MCP SDK 2.2.0 — 7 сентября 2026 года. ([GitHub][4])

## 2. Рекомендуемая схема компонентов

```text
Одобренный MCP-клиент
    │
    ├── браузерный вход + authorization code / PKCE ──> Корпоративный IdP
    │
    └── HTTPS + access token
                │
        Reverse proxy / ограничения нагрузки
                │
        FastMCP: только явно объявленные инструменты
                │
        Проверка токена → внутренняя личность пользователя
                │
        Общий слой бизнес-операций и объектных прав
                │
             PostgreSQL

Существующий FastAPI REST ──> тот же слой бизнес-операций и прав
```

### Что должно быть общим с REST

Предлагаю вынести в версионируемый Python-пакет операции примерно такого уровня:

```python
meeting_service.get_meeting(principal, meeting_id)
meeting_service.get_transcript(principal, meeting_id, page)
meeting_service.get_summary(principal, meeting_id)
meeting_service.list_action_items(principal, meeting_id)
meeting_service.create_action_item(principal, command)
```

И REST, и MCP вызывают их напрямую. Внутри находятся проверки организации, объектных прав, допустимости операции, версии объекта и транзакционные изменения.

**Нельзя оставлять проверки только в FastAPI dependencies.** При прямом вызове из MCP такой обработчик можно обойти. Транспортная проверка токена и предметная проверка прав — разные уровни.

Предлагаемая последовательность:

```text
Проверить access token
→ сопоставить (issuer, subject) с внутренним пользователем
→ проверить действующее членство в организации
→ проверить право на конкретный объект и действие
→ выполнить общую бизнес-операцию
```

`user_id`, организация и полномочия не должны приниматься на веру из аргументов, сформированных моделью. Для транскрипта, саммари и поручений нужны собственные проверки: доступ к карточке встречи не обязан давать доступ ко всему содержимому.

### Минимальный каталог

Для первого выпуска достаточно пяти инструментов:

```text
list_my_meetings
get_meeting
get_transcript
get_summary
list_action_items
```

Предлагаю не включать оригинальное аудио, произвольные выгрузки, SQL, HTTP-запросы, поиск по всей организации и универсальный `call_api(method, path, body)`.

Для транскриптов обязательны ограничение размера ответа и постраничное чтение. Иначе разрешение на просмотр одной встречи легко превращается в неограниченную передачу текста в контекст агента.

### Почему лучше отдельный процесс

В исходниках FastMCP 4.0.5 указана зависимость **Starlette ≥ 1.0.1**. Это может конфликтовать с окружением существующего FastAPI-приложения. Поэтому для пилота безопаснее два процесса и два окружения зависимостей, но один пакет бизнес-логики. ([GitHub][5])

Совместное ASGI-развёртывание допустимо после проверки зависимостей. При этом нужно монтировать **полное приложение** с middleware и lifespan, а не переносить только его маршруты: иначе можно потерять защиту или корректный жизненный цикл. Также необходимо сохранить доступность discovery по правильному внешнему адресу. ([FastMCP][6])

## 3. Как должен работать OAuth

### Discovery: закрытые инструменты, открытые метаданные входа

**Анонимный доступ к данным запрещается. Но метаданные, необходимые для начала OAuth-входа, должны быть доступны без токена.** Это не доступ к встречам.

Запрос к защищённому MCP endpoint без bearer должен возвращать `401` с указанием Protected Resource Metadata:

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://minutes.corp.example/.well-known/oauth-protected-resource/mcp"
```

Пример метаданных для предлагаемого профиля:

```json
{
  "resource": "https://minutes.corp.example/mcp",
  "authorization_servers": [
    "https://id.corp.example/issuer"
  ],
  "scopes_supported": ["minutes:read"],
  "bearer_methods_supported": ["header"]
}
```

Текущая спецификация предусматривает обнаружение через `WWW-Authenticate`, а также стандартные адреса `.well-known`. В метаданных ресурса должен быть указан как минимум один authorization server. Для пилота рекомендую **один issuer**, чтобы не добавлять различия клиентского выбора между несколькими IdP. ([Model Context Protocol][7])

Прокси не должен заменять `401` перенаправлением на корпоративную страницу cookie-входа. MCP-клиенту нужен OAuth challenge, а не HTML-страница.

### Регистрация клиента: открытый DCR не нужен

Для закрытой корпоративной системы рекомендую **предварительную регистрацию одобренных клиентов**:

```text
grant_types: authorization_code, refresh_token
PKCE: S256
public native client: без client_secret
redirect_uri: точное значение конкретного клиента
```

Это соответствует текущей спецификации. Она предпочитает заранее известную регистрацию; далее рассматривает Client ID Metadata Documents, а Dynamic Client Registration оставляет для совместимости и помечает устаревающим механизмом. **Требования обязательно открыть DCR нет.** ([Model Context Protocol][8])

В документации FastMCP Remote OAuth встречается более категоричное утверждение о необходимости DCR. Его нельзя использовать как универсальное ограничение: актуальная спецификация допускает предварительную регистрацию, а `RemoteAuthProvider` отвечает за проверку токенов и метаданные ресурса, а не требует единственного способа регистрации клиента. ([FastMCP][9])

Отдельное ограничение: разрешённый `client_id` идентифицирует регистрацию приложения, но сам по себе не доказывает, что запрос пришёл от доверенного бинарного файла или безопасного устройства. Поэтому это дополнительное ограничение, а не замена аутентификации пользователя.

### PKCE, issuer и audience — три отдельных проверки

**PKCE.** Требуется `S256`. Клиент должен проверять поддержку PKCE через метаданные authorization server; отсутствие необходимого объявления нельзя исправлять отключением PKCE. Также нужны проверка `state` и точное соответствие callback URI. ([Model Context Protocol][10])

**Issuer.** Клиент сохраняет ожидаемый issuer до перехода в браузер. Если ответ авторизации содержит `iss`, его нужно сверить **до обмена кода на токен**. Если IdP объявляет поддержку соответствующего параметра, его отсутствие также является ошибкой. ([Model Context Protocol][11])

**Audience.** Токен должен быть предназначен для MCP-ресурса. Клиент передаёт `resource` при авторизации и обмене кода; сервер проверяет соответствующее назначение токена. В предлагаемом профиле:

```text
MCP resource / ожидаемый aud:
https://minutes.corp.example/mcp
```

Токен входа в веб-приложение, ID token и access token для другого API не должны автоматически приниматься MCP-сервером. ([Model Context Protocol][11])

### Проверка JWT: явно задать корпоративный профиль

У стандартного `JWTVerifier` FastMCP параметры issuer и audience необязательны, а срок проверяется при наличии `exp`. Поэтому «подключили JWTVerifier» недостаточно: нужно явно определить обязательные поля и проверки. Это видно в исходниках зафиксированной версии. 

Для прототипа я использовал проверку библиотекой PyJWT: фиксированный алгоритм, доверенный ключ/JWKS, ожидаемые issuer и audience, обязательные `exp/sub/iat/jti`, разрешённый `client_id` либо `azp`. Это **профиль данного прототипа**, не утверждение, что MCP требует именно такой набор claims.

Адрес ключей берётся из доверенной конфигурации, а не из произвольной ссылки внутри полученного токена.

### Scopes: не путать с доступом к встречам

Для первого выпуска предлагаю один scope `minutes:read`, а конкретные права проверять в бизнес-слое. Для записи позднее добавить `minutes:write` или более узкие разрешения, соответствующие операциям.

Важная особенность FastMCP: **отказ на уровне отдельного инструмента — не обязательно HTTP `403`**. Декоратор может скрывать инструмент и возвращать not-found; `AuthMiddleware` может сообщать о недостающих scopes внутри JSON-RPC/HTTP `200`. Стандартный HTTP `403` с `WWW-Authenticate` относится к транспортному уровню проверки scopes. Поэтому автоматическое получение дополнительных разрешений нельзя считать работающим только потому, что установлен `require_scopes`. ([FastMCP][12])

Для пилота лучше заранее согласовать небольшой набор read-scopes, чем зависеть от автоматического расширения разрешений посреди вызова.

### Особая проверка для authentik

authentik документирует OAuth/PKCE и refresh tokens. Для выдачи refresh token требуется корректная настройка и запрос `offline_access`. ([authentik][13])

Но **наличие этих функций не доказывает корректный MCP audience**. В просмотренном исходном коде исходный `aud` устанавливается в `provider.client_id`, а access token строится на этой основе; сопоставление claims может изменить результат. ([GitHub][14])

Значит, для выбранной конфигурации authentik необходимо проверить фактический токен и профиль ресурса. **Нельзя просто разрешить любой `aud`, чтобы подключение заработало**, или глобально заменить audience у ID tokens. Готовый проверенный authentik blueprint в прототип не включён.

### Несколько обнаруженных несовместимостей

**Claude Code: callback реально менялся между версиями.** Документация отмечает переключение с `localhost` на `127.0.0.1` в 2.1.229 и исправление в 2.1.231. Для OAuth это разные redirect URI. Кроме того, выбор SDK v2 и протокола 2026 года зависит от сборки и настроек; в закрытом окружении нельзя полагаться на получение удалённых feature flags. ([Claude][16])

**FastMCP: scopes из конфигурации клиента не гарантируют выданных прав.** В коде Python SDK первоначальный набор может определяться challenge/metadata сервера. Поэтому нужно проверять запрос авторизации и полученный токен, а не только `scopes=[...]` в Python. Также известное клиенту истечение токена и неожиданный `401` могут запускать разные ветки: обновление либо повторную авторизацию. ([GitHub][19])

**FastMCP: хранение токенов по умолчанию не обязательно переживает перезапуск.** В просмотренной реализации используется хранилище в памяти; для эксплуатации требуется настроить безопасное постоянное хранение. 

**Мой порядок внедрения:** сначала эталонный Python-клиент, затем один одобренный пользовательский клиент. Остальные добавлять только после такого же прогона. Не переносить результаты Claude Code на Claude Desktop или результаты CLI на облачный коннектор.

И отдельно: техническая совместимость клиента не означает разрешение передавать закрытые протоколы используемой им модели. Путь данных после получения tool result нужно согласовывать отдельно.

## 5. Обновление, отзыв токена и переподключение

### Предлагаемая политика токенов

Для пилота я бы задал access token на **5–10 минут**, а для теста — **30 секунд**. Это параметры предлагаемой политики, не требования MCP.

Refresh token хранится только там, где выполняется OAuth-клиент. Обновление должно сохранять новый токен атомарно и не запускаться одновременно несколькими процессами без координации. При ротации refresh token такая гонка может испортить авторизованное состояние.

Для публичных клиентов текущий профиль безопасности MCP предусматривает ротацию refresh tokens. ([Model Context Protocol][10])

### Отзыв refresh token не равен немедленному отзыву JWT

Самостоятельная проверка подписи JWT не обращается к IdP на каждом запросе. Поэтому для быстрого отзыва уже выданных полномочий предлагаю выбрать один механизм:

| Вариант                                  | Практический смысл                                                                                           |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **Introspection**                        | Сервер проверяет активность токена через защищённый endpoint IdP; кэш задаёт допустимое запаздывание         |
| **События отзыва + локальное состояние** | MCP проверяет блокировку пользователя, `revoke_before` или отозванный `jti`; нужна надёжная доставка событий |
| **Только короткий срок JWT**             | Самый простой вариант, но доступ сохраняется до истечения; не подходит для требования немедленного отзыва    |

Стандартные механизмы описаны в RFC 7009 и RFC 7662. Сам endpoint отзыва не решает автоматически, как каждый сервер узнаёт об отзыве автономно проверяемого токена. ([RFC Editor][20])

Нужно также различать выход из браузерной сессии и отзыв OAuth credentials. Например, в просмотренной модели authentik refresh token может сохраняться после завершения связанной сессии. ([GitHub][21])

**Предлагаемый критерий:** блокировка пользователя или изменение его прав действует на следующем серверном запросе с учётом явно установленного времени доставки и кэширования. Уже переданные клиенту данные отозвать невозможно.

### Переподключение

В редакции 2026-07-28 восстановление означает новый запрос, а не продолжение старой MCP-сессии. Потеря соединения не доказывает, что операция не выполнилась. В прежнем режиме дополнительно возможны повторная инициализация и обработка исчезнувшей серверной сессии. ([Model Context Protocol][2])

Для первого выпуска предлагаю короткие запросы с JSON-ответами и постраничным чтением. Подписки и длительные SSE-потоки здесь не нужны.

## 6. Безопасные ошибки

Предлагаемый контракт должен различать неисправный токен, недостаточные OAuth-полномочия и запрет на конкретную встречу:

| Ситуация                                                | Ответ и поведение                                                                  |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Нет токена, токен недействителен или истёк              | HTTP `401`, корректный Bearer challenge и `resource_metadata`                      |
| Валидному токену не хватает обязательного scope сервера | HTTP `403`, `insufficient_scope`, требуемые scopes                                 |
| Чужая или несуществующая встреча                        | Одинаковая безопасная ошибка инструмента, например `NOT_FOUND_OR_FORBIDDEN`        |
| Недоступна инфраструктура проверки токена               | HTTP `503`, а не ложный `invalid_token`                                            |
| Превышен лимит                                          | HTTP `429`, ограниченные повторы с учётом `Retry-After`                            |
| Повтор operation ID с другим содержимым                 | Прикладной конфликт; для REST — `409`, для MCP — безопасный код ошибки инструмента |

Разделение `401` и `403` соответствует OAuth-профилю MCP. Различие между транспортным отказом и ошибкой отдельного инструмента особенно важно для FastMCP: иначе клиент может пытаться «получить ещё scopes» при обычном запрете на чужую встречу. ([Model Context Protocol][11])

В ответах и обычных логах предлагаю оставлять код ошибки, корреляционный идентификатор, имя операции и решение проверки доступа. Не возвращать SQL, трассировки, токены, внутренние адреса и фрагменты транскрипта.

На HTTP-границе нужно явно включить проверку Host/Origin. В FastMCP соответствующая защита настраивается отдельно; CORS не заменяет аутентификацию. Отсутствующий Origin у нативного клиента нельзя автоматически считать атакой, но присутствующий должен проверяться. ([FastMCP][6])

Для закрытых данных дополнительно предлагаю запретить общий HTTP-кэш и не разрешать повторное использование содержимого в обход актуальной проверки прав.

## 7. Как повторять изменение без дубля

**Защита должна находиться в общей бизнес-операции, а не в конкретном MCP-клиенте.** Разные клиенты по-разному обновляют credentials, переподключаются и повторяют запросы; транспортного идентификатора JSON-RPC недостаточно.

Предлагаемый контракт будущего инструмента:

```json
{
  "meeting_id": "own-meeting",
  "title": "Подготовить согласованный документ",
  "operation_id": "72e1fbb3-804a-474d-8a81-3a1e3f6f6b56"
}
```

`operation_id` создаёт и сохраняет вызывающая программа **до первой отправки**. После обрыва используется тот же идентификатор. Модель не должна самостоятельно придумывать новый UUID при каждом повторе.

В PostgreSQL предлагаю уникальность:

```text
tenant_id + internal_actor_id + operation_kind + operation_id
```

В одной транзакции выполняются проверка текущих прав, регистрация операции, изменение данных, запись исходящего события в outbox и сохранение результата. Дополнительно сохраняется хеш нормализованных параметров.

```text
Тот же operation_id + те же параметры
    → вернуть прежний результат

Тот же operation_id + другие параметры
    → конфликт, ничего не менять

Нет записи операции
    → выполнить изменение и сохранить результат
```

Критический сценарий:

```text
Создали поручение
→ COMMIT
→ соединение оборвалось до получения ответа
→ клиент переподключился
→ повторил ту же команду с тем же operation_id
→ получил прежний task_id
```

**Права проверяются и перед возвратом сохранённого результата.** Иначе журнал повторов станет способом читать данные после отзыва доступа.

Для обновлений нужно включать ожидаемую версию объекта. Для внешних уведомлений нужна отдельная защита от повторов у обработчика outbox: одна транзакция PostgreSQL сама по себе не гарантирует однократную доставку в другую систему.

Смена JSON-RPC request ID, refresh token или соединения не должна менять `operation_id`. Без такого контракта автоматический повтор изменяющих операций после неоднозначного сетевого сбоя я бы запретил.

| `security.py`                   | Проверка JWT, внутренней личности, локального отзыва                               |

| Блокировка пользователя и локальный отзыв токена                               | Следующий запрос отклоняется                           |
| Восемь конкурентных вызовов с одинаковым operation ID                          | Одна операция                                          |
| Откат транзакции                                                               | Нет частично записанного изменения                     |

Последний сетевой тест выполнен через **REST и общий бизнес-слой**. Это доказательство защиты операции от дублей, **не доказательство работы MCP-транспорта**.

### Что подготовлено, но не запускалось

В среде не было пакетов FastMCP/MCP и не работало разрешение внешних адресов для установки. Интерфейсы адаптера сверены с исходниками; код проверен синтаксически.

Также локальные таблицы отзыва **не подключены автоматически к IdP**, а SQLite и демонстрационные ACL нужно заменить существующей моделью PostgreSQL.

### Сквозной сценарий

После настройки `.env.example`, HTTPS и тестового IdP:

```bash
# Сервер: отдельное окружение MCP
python -m pip install -r requirements-mcp.txt
python seed.py
uvicorn mcp_server:app --host 127.0.0.1 --port 8001

# Клиент: обычный и прежний режим протокола
python client_demo.py
python client_demo.py --legacy
```

Для приложенного клиента регистрируется точный callback:

```text
http://127.0.0.1:8765/callback
```

Сценарий проверяет:

```text
Вход через браузер
→ чтение own-meeting
→ одинаковый отказ для чужой и несуществующей встречи
→ ожидание истечения 30-секундного access token
→ старый bearer получает 401
→ клиент обновляет токен без нового открытия браузера
→ новое соединение снова читает разрешённую встречу
```

Для искусственного изменения:

```bash
# Только на тестовом сервере, перед MCP-процессом
python fault_proxy.py --upstream-port 8001 --listen-port 8000

# Сохранить идентификатор до вызова и использовать его при повторе
python client_demo.py --write --operation-file one-operation.txt
```

Тестовый прокси предназначен только для локального стенда. Он не является частью рекомендуемой промышленной архитектуры.

## 9. Условия допуска клиента и сервера в пилот

В протоколе приёмки нужно фиксировать **название и версию клиента, версию MCP, версию сервера, конфигурацию IdP и наблюдаемые результаты**, а не отметку «OAuth поддерживается».

Минимальная матрица:

| Сценарий                             | Критерий                                                                            |
| ------------------------------------ | ----------------------------------------------------------------------------------- |
| Подключение без credentials          | `401`, данные и инструменты недоступны                                              |
| PKCE и callback                      | Неверный verifier, state или redirect отклоняются; код нельзя использовать повторно |
| Назначение токена                    | Чужой issuer/audience и ID token не принимаются                                     |
| Чужая организация и дочерние объекты | Ни содержимого, ни обхода через ID транскрипта/поручения                            |
| Истечение access token               | Старый токен отклонён; разрешённое обновление проходит без повторного входа         |
| Отзыв refresh token                  | Следующее обновление отклонено; нет перехода к анонимному доступу                   |
| Отзыв объектного права               | Последующий запрос и возврат сохранённого результата запрещены                      |
| Перезапуск клиента/сервера           | Предсказуемое восстановление без потери привязки пользователя                       |
| Потеря ответа после изменения        | Повтор с прежним operation ID не создаёт дубль                                      |
| Сбой IdP/JWKS                        | Нет разрешения «по умолчанию» и бесконечного цикла входа                            |

**Итоговое решение:** FastMCP подходит как транспортный адаптер. Для этого проекта основная работа — не объявить пять инструментов, а зафиксировать OAuth-профиль, сохранить единые объектные права с REST и проверить конкретные клиентские сборки. В первый пилот я бы выпускал только чтение; запись — после сквозного теста потери ответа, актуальной проверки прав и подтверждённой защиты от дублей.

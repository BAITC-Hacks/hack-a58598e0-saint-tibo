**Для твоего стека я бы оставил два основных кандидата: `pavelzbornik/whisperX-FastAPI` — для интеграции в существующий Python-бэкенд, `Nyralei/whisperx-api-server` — для быстрого запуска сервера с готовым TypeScript-интерфейсом. Для обработки прямо во время встречи — отдельно `QuentinFuxa/WhisperLiveKit`.** Это моя рекомендация по устройству проектов и их интерфейсам, а не рейтинг качества распознавания. ([GitHub][1])

Ниже — **статический аудит GitHub на 23 сентября 2026 года**: документация, зависимости, API и отдельные исходные файлы. Модели на одинаковом железе я не запускал, поэтому подтверждённые возможности отделяю от того, что потребуется проверить.

Под Python здесь подразумевается серверная и прикладная логика. PyTorch, ONNX Runtime, FFmpeg и другие нативные зависимости от этого не исчезают. Готовый TypeScript-интерфейс есть не у всех: Python-сервис без интерфейса также подходит для подключения к твоему React/TypeScript-приложению.

## 2. `pavelzbornik/whisperX-FastAPI`: наиболее прямое встраивание в твой backend

### Что полезного уже сделано

Здесь этапы обработки представлены **отдельными операциями**, а не только одной кнопкой «расшифровать»:

| Операция                       | Интерфейс                |
| ------------------------------ | ------------------------ |
| Обработка загруженной записи   | `POST /speech-to-text`   |
| Распознавание текста           | `/service/transcribe`    |
| Привязка текста к времени      | `/service/align`         |
| Определение говорящих          | `/service/diarize`       |
| Объединение текста и говорящих | `/service/combine`       |
| Получение состояния задания    | `GET /task/{identifier}` |

Статусы и результаты сохраняются через SQLAlchemy; предусмотрены SQLite и PostgreSQL. ([GitHub][1])

**Почему стоит использовать:** такая декомпозиция позволяет проектировать повторную обработку отдельных этапов. Например, после изменения предполагаемого числа участников повторять диаризацию и объединение, а не обязательно всё распознавание.

**Как интегрировать:** я бы запускал его отдельным внутренним сервисом. Твой FastAPI передаёт файл, сохраняет идентификатор задания, забирает результат и связывает его со встречей. Пользователи и права остаются в твоей системе.

### Что обнаружилось при проверке

По умолчанию авторизация и ограничение частоты запросов выключены, размер загрузки не ограничен. Проверка размера опирается на `Content-Length`, поэтому для потоковых загрузок без этого заголовка нужна дополнительная защита. CPU допускается настройками, но стандартная Linux-установка зависимостей ориентирована на CUDA. ([GitHub][1])

В `app/main.py` есть глобальная подмена `torch.load`, возвращающая `weights_only=False`, если явно не передано `True`. Она добавлена для совместимости загрузки моделей. **Перед корпоративным внедрением я бы пересмотрел этот патч и разрешал только заранее проверенные файлы моделей.** Это найденный участок для проверки, не доказательство уже существующей атаки. 

Также я бы отдельно испытал восстановление после аварии: запись статуса в БД сама по себе ещё не доказывает, что прерванная обработка корректно продолжится.

**Вывод:** мой первый кандидат для твоего существующего приложения, но не в конфигурации по умолчанию и не напрямую в интернет.

## 3. `Nyralei/whisperx-api-server`: готовый API и TypeScript-экран загрузки

Здесь предусмотрены **отдельные CPU- и CUDA-профили**, а Kafka и MinIO нужны только для расширенного распределённого режима. Для небольшого сервера можно начать без них. Основной API — `POST /v1/audio/transcriptions`; диаризация включается через `diarize=true` и требует `align=true`. ([GitHub][2])

TypeScript-интерфейс — отдельный тонкий клиент: загрузка файла, отображение этапов, переход по расшифровке к моменту записи, подсветка слов и говорящих, экспорт. Его необходимо явно собрать и включить. ([GitHub][2])

**Почему стоит использовать:** меньше работы до первого пользовательского теста. Можно проверить и сервер, и сценарий загрузки, не создавая свой экран с нуля.

**Как интегрировать:** либо использовать готовый интерфейс для пилота, либо обращаться к тому же API из твоего приложения. Логику встреч я бы не переносил внутрь этого проекта.

### Существенное ограничение

В обычном режиме запрос обработки **синхронный**: соединение остаётся открытым до завершения. `async=true` с немедленным ответом `202` работает только в Kafka-режиме. Отдельный API статуса не превращает обычный запуск в устойчивую очередь заданий; завершённые статусы по умолчанию хранятся 300 секунд. ([GitHub][2])

Поэтому мой вариант — внешнее задание в твоём приложении, которое вызывает этот сервис и сохраняет окончательный результат в твою БД.

**Вывод:** лучший из найденных кандидатов для быстрого пилота **Python + готовый TypeScript UI**, особенно когда нужен понятный CPU-профиль.

## 4. `WhisperLiveKit`: когда расшифровка нужна во время встречи

Это не просто повторный запуск Whisper на каждом маленьком фрагменте. Проект уже реализует буферизацию аудио, работу с промежуточными результатами и постепенное подтверждение текста. Есть Python-интерфейс с `TranscriptionEngine` и `AudioProcessor`, а также готовый сервер. ([GitHub][3])

**Что закрывает:** получение поступающего аудио, потоковую расшифровку и подключаемую диаризацию.

**Как интегрировать:** TypeScript-клиент отправляет аудиофрагменты по WebSocket `/asr`, получает обновления и отображает их. Альтернатива — встроить Python-компоненты в собственный сервис. Для файлов также есть `POST /v1/audio/transcriptions`. Формат `diarized_json` требует запуска с включённой диаризацией, иначе возвращается ошибка. ([GitHub][3])

### На что обратить внимание

При выборе **Streaming Sortformer 4spk v2.1** действует ограничение модели — до четырёх говорящих. Это ограничение конкретной конфигурации, а не универсальная характеристика всех возможных движков WhisperLiveKit. Для большой переговорной такой вариант нельзя назначать без проверки. ([Hugging Face][7])

Кроме того, совместимые API — именно подмножества: например, параметр `model` файлового API принимается, но используется модель, настроенная на сервере. ([GitHub][8])

**Моя рекомендация:** использовать для предварительной расшифровки во время встречи, а после завершения запускать отдельный окончательный проход по полной записи. Черновой поток не должен автоматически становиться утверждённым протоколом.

## 5. `TranscriptionSuite`: наиболее законченный пользовательский продукт

Проект объединяет Python-сервер и настольный интерфейс на Electron/React/TypeScript. Сервер можно вынести на другую машину. Есть загрузка файлов, хранение расшифровок, поиск, воспроизведение и подключение локальной языковой модели для последующей работы с текстом. ([GitHub][4])

**Почему стоит использовать:** позволяет оценить целый пользовательский процесс, а не только качество JSON после обработки.

**Как интегрировать:** использовать серверную часть через API. Для твоего уже существующего веб-приложения я не вижу причины переносить весь Electron-интерфейс.

### Два важных ограничения

**Возможности зависят от движка.** Например, наличие whisper.cpp в списке поддерживаемых вариантов не означает наличие диаризации в этом режиме. Нужно проверять выбранную комбинацию, а не общий список функций продукта. ([GitHub][4])

**Успешный HTTP-ответ не гарантирует успешную диаризацию.** Документация прямо описывает поведение: при некоторых сбоях этого этапа сервер возвращает `200` с обычной расшифровкой, `num_speakers=0` и без полей `speaker`, записав предупреждение в журнал. 

Я бы трактовал такой результат как **«распознавание завершено, диаризация не выполнена»**, а не как полностью успешное задание.

**Вывод:** сильный кандидат для готового рабочего места и проверки сценариев; для твоего продукта — скорее подключаемый сервис, чем основа всей системы.

## 6. `transcribee`: когда главное — исправить и проверить расшифровку

Это наиболее интересный вариант именно для этапа **«машина подготовила → человек исправил → результат экспортирован»**. Проект позволяет редактировать текст, назначать имена говорящим и синхронизировать изменения между пользователями. ([GitHub][5])

Стек соответствует направлению: Python/FastAPI на сервере и React/TypeScript в интерфейсе. Редактор использует Slate, совместную работу — через Automerge. 

**Почему стоит использовать:** редактор с привязкой к расшифровке — отдельная большая часть продукта. Готовое решение здесь может быть полезнее ещё одной обёртки над моделью.

**Как интегрировать:** рассматривать как отдельное приложение проверки либо изучать его интерфейсы и структуру редактора для собственного решения. При переносе кода учитывать AGPL-3.0.

**Ограничение:** в README прямо предупреждают о серьёзных проблемах производительности при одновременном редактировании. Поэтому именно совместную работу нельзя считать готовой к нагрузке без испытаний. ([GitHub][5])

**Вывод:** хороший кандидат для редакторского этапа, но не мой первый выбор вычислительного сервера.

## 7. `etalab-ia/whisperx-openai-api`: компактная альтернатива

Это меньшая по продуктовым амбициям Python/FastAPI-обёртка: поднять локальные модели и предоставить API. В опубликованной конфигурации используются `large-v3-turbo` и диаризация Community-1; инструкция запуска ориентирована на GPU. Готовый CPU-профиль я здесь не подтвердил. ([GitHub][6])

**Почему стоит использовать:** когда интерфейс, очередь, пользователи и хранение у тебя уже есть, лишняя собственная платформа внутри обработчика не нужна.

**Как интегрировать:** отдельный контейнер, вызов из твоего обработчика заданий, сохранение результата в основной системе.

Важная деталь для закрытого контура: исходный список предварительно загружаемых моделей выравнивания включает несколько европейских языков, но не русский. Русскую конфигурацию нужно подготовить до отключения интернета. ([GitHub][6])

**Вывод:** разумная минимальная альтернатива на GPU; для CPU-пилота я предпочёл бы Nyralei.

## 8. Ещё два проекта, но не основные кандидаты

### `estebanstifli/Meet2Notes`

Функционально близок к твоей идее: локальная запись, импорт файлов, предварительная и окончательная расшифровки, диаризация, профили голосов и заметки встречи. Лицензия MIT, проект находится в альфа-стадии. ([GitHub][9])

Архитектурно интересен: Python-логика отделена от FastAPI, есть адаптеры обработки и фоновые исполнители. Но **штатный интерфейс написан на обычном JavaScript, не TypeScript**, поэтому в строгий список готовых Python/TypeScript-приложений я его не включаю. 

Я бы изучал **Python-ядро и расширения**, а не принимал весь проект как готовую корпоративную систему.

### `jhj0517/Whisper-WebUI`

Python-приложение с Gradio, загрузкой файлов, распознаванием, диаризацией и экспортом субтитров. Помимо интерфейса, в репозитории действительно есть отдельный FastAPI-бэкенд — это не только демонстрационная форма. ([GitHub][10])

Полезен для экспериментов и сравнения параметров. Но основной сценарий — расшифровки и субтитры, а не управляемый жизненный цикл встречи.

**Я бы использовал как испытательный инструмент, не как основу продукта.**

## 9. Какие из твоих проблем всё равно остаются отдельными

### Предложения — частично уже закрыты; законченные мысли — нет

WhisperX уже использует разбиение на предложения. Поэтому неверно считать, что во всех перечисленных обёртках получаются только произвольные куски аудио. Однако предложение и законченный смысловой блок — разные сущности. ([GitHub][11])

Для дополнительной обработки есть два подходящих Python-проекта:

| Компонент                       | Что добавляет                                                                                                         | Как подключать                                                                            |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| **`segment-any-text/wtpsplit`** | Специализированное разбиение текста на предложения, в том числе при проблемной пунктуации; доступны компактные модели | После распознавания, с переносом границ обратно на временные метки слов. ([GitHub][12])   |
| **`feyninc/chonkie`**           | Разбиение текста на фрагменты по предложениям и семантической близости                                                | После формирования реплик; выбирать локальные модели представления текста. ([GitHub][13]) |

Я бы не обещал, что семантическая нарезка автоматически выделит все законченные решения. Например, решение может состоять из вопроса одного человека, уточнения второго и подтверждения третьего.

**Практическое решение:** хранить реплики отдельно от смысловых блоков. Один смысловой блок может объединять нескольких говорящих.

### Метки говорящих — не отдельные чистые аудиодорожки

Результат диаризации вида `SPEAKER_01, 12.4–18.2` не означает, что из наложения голосов восстановлен чистый голос этого человека. Для настоящего разделения источников существует отдельный Python-инструментарий — например, **`modelscope/ClearerVoice-Studio`**, с моделями разделения и улучшения речи. ([GitHub][14])

Я бы подключал такое разделение **только для проблемных участков**, а не включал тяжёлую дополнительную обработку всей встречи по умолчанию.

### Русский, казахский и смешанная речь требуют проверки по этапам

В текущем коде WhisperX есть стандартное соответствие модели выравнивания для русского, но нет такого соответствия для `kk`. Это **не доказательство отсутствия казахского распознавания**: ограничение касается стандартного пути получения точных временных меток. 

Для твоей системы это означает отдельную проверку трёх результатов: текста, времени слов и привязки к говорящим. Особенно на переключениях RU → KK внутри реплики.

### Загрузка записи — не подключение к самой встрече

В описанных API основным входом служит файл или поток аудио. Поддержка загруженного MP4 из Teams не означает, что сервис сам входит в Teams, получает разрешение на запись и забирает звук с ноутбука пользователя. ([GitHub][1])

Поэтому я бы разделял **клиентский захват звука** и **серверную обработку**, а первый пилот строил вокруг загрузки уже готовой записи.

## 10. Как я бы интегрировал это в твою систему

**Не переносил бы корпоративную логику внутрь проекта распознавания.** Моя рекомендуемая граница:

```text
Твой React / TypeScript
        ↓
Твой FastAPI
Пользователи, организации, права, встречи
        ↓
Задание на обработку
        ↓
Один внутренний сервис:
whisperX-FastAPI ИЛИ whisperx-api-server
        ↓
Проверка полноты результата
        ↓
Твои PostgreSQL и файловое хранилище
        ↓
Редактор расшифровки → смысловые блоки → протокол
```

WhisperLiveKit добавлял бы отдельным путём только для поступающего аудио.

### Что должно остаться на твоей стороне

**Управление заданием.** Внешний `meeting_id`, версия обработки, параметры моделей, состояния каждого этапа, повтор после ошибки, отмена и защита от дублирующего запуска.

**Единый формат результата.** Независимо от выбранной обёртки: слова с временем, реплики с говорящими, смысловые блоки и предупреждения. Отсутствующий говорящий — неизвестное значение, а не автоматически «участник 1».

**Права и хранение.** API-ключ вычислительного сервиса не заменяет права пользователя на конкретную встречу. Оригиналы, версии расшифровки и исправления должны оставаться под контролем твоего приложения.

Это позволяет заменить обработчик позднее, не переделывая всю систему.

## 11. Что ожидать по ресурсам и доработкам

**Наличие CPU-профиля означает возможность такого запуска, но не обещает быструю обработку часовой встречи.** У Nyralei есть отдельные CPU-сборки; у pavelzbornik CPU задаётся конфигурацией. Производительность полного конвейера на твоём сервере всё равно нужно измерить. ([GitHub][2])

Для первого испытания я бы выбрал одну одновременно обрабатываемую запись, небольшую многоязычную модель, INT8 там, где поддерживается, и последовательное выполнение тяжёлых этапов. Это **предлагаемая стартовая конфигурация**, не результат замера.

| Проверка приёмки                                 | Что она должна показать                                                  |
| ------------------------------------------------ | ------------------------------------------------------------------------ |
| **Запуск без исходящего интернета**              | Все необходимые модели и зависимости действительно подготовлены локально |
| **Одинаковые записи с 2, 4 и 6+ участниками**    | Ошибки числа говорящих, перебиваний и коротких реплик                    |
| **RU, KK и смешанная речь отдельно**             | Какие этапы работают, а где нужны другая модель или запасной режим       |
| **Перезапуск в середине обработки**              | Задание не пропало и не отмечено успешно без результата                  |
| **Ошибка диаризации при успешном распознавании** | Пользователь видит частичный результат, а не ложное «готово»             |
| **Время обработки и ручной правки**              | Реальная стоимость часа записи: CPU/GPU, память и труд редактора         |

### Мой окончательный выбор

**Для твоего существующего продукта — сначала `pavelzbornik/whisperX-FastAPI`, с исправлением настроек безопасности и проверкой восстановления заданий. Для самого быстрого пилота с готовым TypeScript-экраном и CPU-сборкой — `Nyralei/whisperx-api-server`. Для живой расшифровки — WhisperLiveKit отдельным компонентом.**

TranscriptionSuite полезен как законченный пользовательский инструмент, transcribee — как редактор. **Я бы не объединял несколько крупных приложений между собой: взял один вычислительный сервис, оставил управление встречами в твоём FastAPI и добавлял только недостающие этапы.**

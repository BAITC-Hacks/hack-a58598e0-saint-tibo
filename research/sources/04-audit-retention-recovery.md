# Вывод

**Для такой системы нужен не просто журнал действий, а проверяемая связь между действием, версией данных и результатом операции.** Отдельно нужна управляемая процедура удаления, которая учитывает резервные копии и не позволяет восстановлению вернуть удалённые встречи или отозванные права.

Рекомендую следующую конструкцию:

**Бизнес-операция → событие аудита в той же транзакции → независимое защищённое хранилище → поисковый индекс и контролируемая выгрузка.**

Содержание встреч и история их версий остаются в основном защищённом хранилище. Аудит хранит идентификаторы, действия, результаты, ссылки на версии и контрольные суммы — не копии транскриптов.

Ниже — предлагаемая архитектура и программа проверки, основанная на документации, доступной на **23 сентября 2026 года**. Указанные сроки и показатели восстановления — **параметры для согласования на пилоте, а не требования SOC 2**. Реальное развёртывание системы в рамках этого ресерча не проверялось.

## 1. Что именно должен доказывать аудит

Сразу стоит ограничить смысл доказательств.

Журнал может подтвердить, что определённая учётная запись получила разрешение на оригинал и сервер начал или завершил передачу данных. **Он не доказывает, что конкретный человек действительно прослушал запись.** Аналогично контрольная сумма подтверждает соответствие файла зафиксированной версии, но сама по себе не подтверждает достоверность произнесённого на встрече.

Поэтому в интерфейсе лучше писать «оригинал выдан пользователю», а не «пользователь прослушал встречу».

Источником бизнес-аудита должно быть приложение: именно оно знает пользователя, объект, операцию и её результат. Журналы веб-сервера, БД и операционной системы дополняют эту картину, но не заменяют её. OWASP также различает аудит операций и журналы событий безопасности по назначению. ([OWASP Cheat Sheet Series][1])

### Предлагаемый состав события

| Группа               | Поля и назначение                                                                                          |
| -------------------- | ---------------------------------------------------------------------------------------------------------- |
| Идентичность события | `event_id`, `schema_version`, `event_type`. Идентификатор сохраняется при повторной доставке               |
| Время                | `occurred_at`, `recorded_at` в UTC. Отдельно — контроль рассинхронизации часов                             |
| Область действия     | `organization_id`, окружение, сервис и версия приложения                                                   |
| Инициатор            | Внутренний `actor_id`, тип: человек или сервис; при делегировании — `on_behalf_of`                         |
| Объект               | Тип объекта, его ID, `meeting_id`; без названия встречи и исходного имени файла                            |
| Версия               | Версии до и после, ID утверждённой версии, контрольная сумма документа или артефакта                       |
| Операция             | Действие, результат, ограниченный набор `reason_code`; HTTP-код — дополнительное поле                      |
| Основание доступа    | ID и версия политики, применённое разрешение; для выдачи доступа — получатель, область и срок              |
| Связность            | `operation_id` для логической операции, `request_id` для конкретного запроса, `correlation_id` для цепочки |
| Изменённые поля      | Например, `["assignee_id", "due_at"]`, но не полный текст старых и новых значений                          |
| Целостность          | Номер приёма коллектором, ID блока архива, контрольная сумма блока и сведения о подписи                    |

`actor_id` сервер получает из проверенной сессии или сервисной аутентификации, а не из переданного клиентом JSON. Для фонового экспорта фиксируются и сервис-исполнитель, и пользователь-заказчик.

Связь внутреннего ID с человеком нужно сохранять в отдельном ограниченно доступном справочнике идентичностей. Иначе после удаления аккаунта в журнале останется технический номер, который невозможно надёжно отнести к сотруднику.

### Минимальный словарь событий

| Действие                   | Что фиксировать                                                                                        |
| -------------------------- | ------------------------------------------------------------------------------------------------------ |
| Выдача оригинала           | Разрешение, начало передачи, завершение либо обрыв; ID оригинала и версии                              |
| Редактирование транскрипта | Создание новой версии, автор, предыдущая версия, перечень изменённых полей                             |
| Изменение поручения        | ID поручения, версии, изменённые поля; принятие, выполнение и подтверждение закрытия — разные действия |
| Утверждение                | Кто утвердил, какую неизменяемую версию, с какими связанными артефактами                               |
| Выдача и отзыв доступа     | Кто, кому, на что, до какого срока и на каком основании                                                |
| Экспорт                    | Запрос, разрешение, создание файла, скачивание или отказ; формат, версия, хеш файла                    |
| Удаление                   | Запрос, блокировка доступа, удаление рабочих копий, ожидание очистки backup, завершение либо ошибка    |
| Отказ в доступе            | Инициатор, запрошенное действие и объект, безопасная категория причины                                 |
| Работа с аудитом           | Просмотр, выгрузка, изменение политики хранения, аварийный доступ                                      |

OWASP Logging Vocabulary полезен как основа для согласованных категорий отказов аутентификации, авторизации, изменения полномочий и привилегированных действий. Конкретные события протоколирования выше — предлагаемое расширение под эту систему. ([OWASP Cheat Sheet Series][2])

**Старое и новое содержание — в истории версий, не в журнале.** После уничтожения истории аудит сможет доказать факт изменения срока, но не восстановить его прежнее значение. Если прежние значения требуется сохранять дольше, это отдельная категория служебных записей с собственной политикой хранения.

Для утверждённых документов рекомендую сохранять готовые PDF/DOCX как неизменяемые артефакты. Утверждение связывается с конкретной версией и этими файлами; скачивание возвращает их, а не заново сформированный документ из «текущих» данных.

### Что исключить

Не записывать аудио, транскрипты, текст поручений, запросы и ответы модели, пароли, токены, cookie, ключи, подписанные ссылки и тела HTTP-запросов. OWASP отдельно предупреждает об исключении секретов, идентификаторов сессий и чувствительных данных из журналов. ([OWASP Cheat Sheet Series][1])

Для этой системы предпочтительна **схема разрешённых полей**, а не попытка удалить секреты из произвольной строки постфактум. Ограничение должно действовать до первой записи на диск — включая ошибки, трассировки и сообщения фоновых заданий.

## 2. Как не потерять событие и не записать действие дважды

### Изменения: одна транзакция с бизнес-данными

Предлагаю использовать **transactional outbox**: изменение объекта и запись подготовленного события выполняются в одной транзакции PostgreSQL. Отдельный процесс передаёт событие в хранилище аудита.

Это устраняет разрыв «поручение изменилось, но процесс упал до записи события». Повторная доставка остаётся возможной, поэтому получатель должен обрабатывать событие идемпотентно — по стабильному `event_id`. Это стандартная особенность данного шаблона, а не гарантия доставки «ровно один раз». ([AWS Documentation][3])

Для API различаются:

* **Повтор запроса:** новый `request_id`, тот же ключ идемпотентности и `operation_id`.
* **Результат бизнес-операции:** одна новая версия объекта и одно событие изменения.
* **Доставка аудита:** сколько угодно повторов одного `event_id`, но одна запись в логическом журнале.

### Отказы: отдельно от отменённой транзакции

Неуспешную попытку доступа нельзя записывать только внутри транзакции, которая затем откатывается.

Предлагаемое правило: **событие отказа создаёт тот компонент, который принял окончательное решение о запрете**. Например, сервис авторизации фиксирует `access.denied`; обработчик поручения не добавляет второе событие «изменение поручения не удалось», если до изменения дело не дошло.

Инфраструктурный HTTP-журнал при этом может содержать свой факт запроса. Это другой класс записи, связанный через `request_id`, а не второе бизнес-событие.

Каждая новая запрещённая попытка — отдельное событие. При атакующем потоке допустима только явно обозначенная агрегация с количеством, первым и последним временем; нельзя молча отбросить события и продолжать заявлять полноту аудита.

### Чтение и скачивание: результат не всегда известен

Перед выдачей первого байта оригинала предлагаю надёжно сохранять факт разрешённой выдачи. Затем записывать завершение или обрыв.

Если процесс аварийно завершился, корректный результат — «передача началась, завершение неизвестно», а не выдуманный `success`.

Range-запросы медиаплеера можно объединять в одну сессию выдачи с общим идентификатором. Отдельные диапазоны остаются техническими событиями, иначе одно прослушивание создаст сотни записей «пользователь открыл оригинал».

### Поведение при отказе аудита

Для пилота предлагаю согласовать строгий режим:

**Если событие нельзя надёжно сохранить ни в outbox, ни в другом предусмотренном устойчивом буфере, выдача оригинала, экспорт и изменение данных запрещаются.**

Недоступность удалённого коллектора сама по себе не останавливает работу, пока события надёжно сохраняются локально и не превышены согласованные пределы задержки и объёма. Переполнение, потеря связи и остановка поступления событий должны вызывать отдельные оповещения.

Это именно выбранная политика чувствительных операций, а не требование о полной остановке всего приложения при любом сбое журналирования.

## 3. Защита от незаметного изменения

**Таблица «только на добавление» в той же БД защищает от обычного приложения, но не от администратора этой БД. Хеш-цепочку в ней он также может пересчитать.**

Практичная защита требует разделения полномочий и независимой контрольной копии.

### Рекомендуемая конструкция

Сервис приложения имеет право передавать события, но не изменять уже принятый архив. Отдельный коллектор формирует закрываемые блоки событий: диапазон номеров, количество записей, контрольная сумма предыдущего блока, контрольная сумма текущего блока и подпись.

Контрольные точки передаются в независимую систему заказчика или отдельному хранителю. Подпись и архив не должны полностью контролироваться тем же администратором, что управляет приложением.

Порядок событий, обнаружение пропусков, защита от повторов и проверка происхождения — задачи, которые отдельно рассматривает стандарт Signed Syslog. Он полезен как ориентир требований, даже если конкретный формат архива будет другим. ([RFC Editor][4])

Предлагаю разделить три слоя:

| Слой                          | Назначение                                                                           |
| ----------------------------- | ------------------------------------------------------------------------------------ |
| Защищённый архив              | Источник доказательств; закрытые блоки не перезаписываются в пределах срока хранения |
| Поисковый индекс              | Удобство запросов; допускает восстановление из архива                                |
| Независимые контрольные точки | Обнаружение удаления блоков, подмены архива и исчезновения его конца                 |

Одна подпись файла CSV не доказывает полноту выгрузки. Для этого нужно дополнительно сопоставить запрос с проверенным архивом, его диапазонами и контрольными точками.

### WORM — с проверкой реальных полномочий

В AWS S3 Object Lock режим **governance** допускает обход пользователем с соответствующим разрешением. Режим **compliance** существенно строже: защищённую версию нельзя удалить или перезаписать в течение установленного срока даже обычным действием root-пользователя аккаунта. Эти режимы нельзя считать эквивалентными. ([AWS Documentation][5])

Для закрытого контура нужен аналогичный проверенный механизм хранения. Например, `rest-server --append-only` ограничивает удаление через интерфейс сервера, но это не означает защиту от администратора, имеющего прямой доступ к файловой системе репозитория. ([GitHub][6])

**Обязательно указать границы защиты:** от администратора приложения, БД, хранилища или от их сговора? Какое окно остаётся до независимой фиксации? Подпись не исправляет ложное событие, которое скомпрометированное приложение сформировало изначально.

Поэтому аудит приложения следует сопоставлять с отдельными событиями IdP, объектного хранилища, управления ключами и администрирования БД.

### Роль pgAudit

pgAudit полезен как дополнительный источник сведений о действиях в PostgreSQL, но не заменяет бизнес-аудит. В нём предусмотрена запись SQL и параметров, поэтому конфигурацию нужно проверять на утечки содержимого. Для данного профиля стоит отдельно рассмотреть отключение `pgaudit.log_statement` и `pgaudit.log_parameter`, а также проверить обычные журналы ошибок и медленных запросов PostgreSQL. ([GitHub][7])

## 4. Права на поиск и контролируемую выгрузку CSV

Предлагаю не связывать автоматически право читать встречи с правом читать весь журнал организации.

| Роль                              | Доступ к аудиту                                                                                 |
| --------------------------------- | ----------------------------------------------------------------------------------------------- |
| Пользователь или владелец встречи | Ограниченная история разрешённых ему объектов                                                   |
| Аудитор безопасности              | Поиск по согласованным организациям и категориям событий                                        |
| Оператор выгрузки                 | Отдельное разрешение на экспорт; без права изменять журнал                                      |
| Администратор инфраструктуры      | Состояние сервисов и технические метрики; не автоматический доступ к содержимому аудита         |
| Хранитель архива                  | Управление сроками и процедурами удаления, с независимым согласованием чувствительных изменений |

Поиск: организация, пользователь, объект, действие, результат, время, версия, идентификатор операции. Фильтр организации применяется сервером. Сам поисковый запрос аудитируется через нормализованные параметры без произвольного чувствительного текста.

### Предлагаемая процедура CSV

Запрос фиксирует область, период, поля, основание и получателя. Для широких выгрузок — MFA и согласование другим уполномоченным сотрудником.

Права повторно проверяются **перед формированием и перед скачиванием**. Отзыв роли после постановки задания должен остановить выдачу.

Рядом с CSV формируется манифест: ID выгрузки, версия схемы, параметры отбора, граница снимка журнала, количество строк, контрольная сумма файла, инициатор и согласующий. Временный файл зашифрован, доступен через авторизованное скачивание и удаляется по короткому сроку.

CSV также требует защиты от формул. Простого заключения значения в кавычки недостаточно; опасны, в частности, значения с начальными `=`, `+`, `-`, `@`. OWASP отдельно отмечает отсутствие универсального способа, безопасного одновременно для всех табличных приложений и программных обработчиков. Поэтому преобразование нужно проверять в конкретных поддерживаемых версиях Excel или другого клиента. ([OWASP Foundation][8])

**Скачанную на неуправляемый компьютер копию система уже не сможет гарантированно отозвать.** Это следует указывать как границу контроля, а не обещать «удаление всех экспортов».

## 5. Политика хранения: отдельно для каждого класса данных

OWASP рекомендует учитывать сроки для самих журналов, временных журналов, копий и выгрузок: не удалять раньше необходимого и не хранить дольше установленного срока. Конкретный период зависит от обязательств организации. ([OWASP Cheat Sheet Series][1])

Для пилота предлагаю следующую отправную точку:

| Класс                                          | Предлагаемая политика                                                                                         |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Оригинальное аудио                             | Отдельный срок `R_original`; например, 90 дней после утверждения, если это разрешено правилами заказчика      |
| Транскрипты, поручения, утверждённые протоколы | Срок `R_record` по категории документа; не обязательно совпадает со сроком аудио                              |
| История версий                                 | Явно включается в класс документа; старые версии не становятся бессрочными                                    |
| Временные файлы обработки                      | Удаление после задания; страховочный срок — не более 24 часов                                                 |
| Временные CSV                                  | Короткий срок, например 24 часа; отдельно от сохранённых утверждённых PDF/DOCX                                |
| Аудит                                          | Для обсуждения: 90 дней в быстром поиске, 365 дней суммарно; не «90 + 365»                                    |
| Резервные копии                                | Для обсуждения: окно восстановления 35 дней; реальное исчезновение данных требует дополнительных условий ниже |

До загрузки реальных закрытых данных заказчик должен утвердить сроки, основания продления и ответственных. Для незавершённых встреч нужен предельный срок от создания: правило «90 дней после утверждения» иначе оставит неутверждённую встречу навсегда.

Нужно инвентаризировать не только очевидные файлы: сегменты аудио, промежуточный WAV, результаты распознавания, поисковые индексы, векторные представления, предпросмотры, временные каталоги PDF/DOCX-генератора, незавершённые загрузки, старые версии объектов и аварийные дампы.

Для очередей и сообщений об ошибках предлагаю хранить ID объектов, а не содержание встречи. Временные каталоги обработки не должны попадать в обычные резервные копии.

## 6. Удаление: процедура с проверяемыми промежуточными состояниями

Одного `deleted_at` недостаточно. Предлагаю следующие состояния:

**`active → deletion_requested → access_blocked → active_copies_purged → backup_pending → deletion_completed`**

Дополнительные состояния: `held` — удаление приостановлено на согласованном основании; `deletion_failed` — есть неустранённая ошибка.

### Что должно происходить

**Сразу после принятия запроса** блокируется обычный доступ. Фоновым заданиям запрещается публиковать новые результаты этой встречи. Незавершённые обработки отменяются либо их результаты отбрасываются по версии состояния удаления.

**Затем удаляются рабочие копии** по реестру связанных объектов: оригиналы, производные файлы, версии, индексы, кэши, временные экспорты. Для каждой операции сохраняются ID объекта, результат, время и число повторов.

**После этого система показывает ожидание очистки backup**, а не финальное «данные уничтожены». В карточке удаления должны быть оставшиеся классы копий, ожидаемый срок и ошибки.

Если протокол или поручение требуется сохранить по самостоятельному основанию, это отражается явно. Нельзя назвать встречу полностью удалённой, оставив её текст в «независимом» документе без объяснения.

### Реестр удалений не должен откатываться вместе с БД

Нужен небольшой отдельный журнал окончательных удалений и отзывов доступа: ID объекта, время, область, основание и состояние исполнения — без содержания встречи.

При восстановлении старой резервной копии этот реестр применяется **до открытия пользовательского доступа**. Иначе возвращаются и удалённые встречи, и прежние права.

Хранить его следует как минимум дольше максимального горизонта доступного восстановления с согласованным запасом.

### Почему «backup хранится 35 дней» недостаточно

В restic команда `forget` удаляет ссылки на снимки, а освобождение невостребованных данных выполняет `prune`. Общие блоки сохраняются, пока на них ссылаются другие снимки. Поэтому удалённый из списка backup ещё не означает удалённые данные. ([Restic Documentation][9])

В PostgreSQL `DELETE` не удаляет старую версию строки немедленно. Обычный `VACUUM` освобождает пространство для повторного использования; это не процедура гарантированного уничтожения информации на носителе. ([PostgreSQL][10])

**Практический вывод:** срок backup нельзя автоматически превратить в обещание «через 35 дней нигде не останется фрагментов текста». Нужно учитывать физические остатки, последующие снимки, WAL, реплики, версии объектов и реальные процедуры очистки.

Для срока окончательного удаления следует рассчитывать не просто дату запроса плюс период, а **самую позднюю дату окончания хранения всех содержащих данные копий плюс подтверждённую задержку очистки**. Удержания, зависимые цепочки backup и ошибки очистки изменяют эту дату.

## 7. Отзыв доступа, отключение ключа и уничтожение ключа — разные результаты

Для интерфейса и доказательств стоит различать:

| Действие                      | Что оно подтверждает                                                                                                                    |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Отзыв права                   | Пользователь больше не должен получать данные через предусмотренные интерфейсы                                                          |
| Отключение ключа              | Система управления ключами временно не разрешает его использование                                                                      |
| Ротация                       | Новые операции используют новую версию ключа; старые данные могут оставаться расшифровываемыми                                          |
| Криптографическое уничтожение | Защищённые данные становятся недоступны благодаря необратимому уничтожению необходимого ключевого материала при выполнении всех условий |

Например, AWS KMS различает отключение и окончательное удаление ключа; запланированное удаление имеет обязательное ожидание от 7 до 30 дней. Это хороший пример того, почему нельзя считать нажатие «удалить ключ» мгновенным уничтожением данных. ([AWS Documentation][11])

Актуальная NIST SP 800-88 Rev. 2 отдельно рассматривает проверку уничтожения, пригодность результата и прослеживаемость операций с ключами, включая их копирование и хранение. ([NIST Computer Security Resource Center][12])

Для данной системы из этого следует важное архитектурное ограничение:

**Удалить зашифрованный ключ встречи из рабочей БД недостаточно, если он есть в backup и существующий мастер-ключ способен его расшифровать.**

Для избирательного криптографического уничтожения нужны соответствующая гранулярность ключей, учёт их резервных копий и отсутствие обходного восстановления. Отдельно учитываются открытые производные файлы и экспорты. Общий ключ шифрования диска не позволяет уничтожить только одну встречу.

На небольшом пилоте разумнее обещать **отзыв доступа, удаление рабочих копий и контролируемое истечение backup**, чем заявлять криптографическое уничтожение без доказанной схемы управления всеми копиями ключей.

## 8. RPO/RTO и проверка восстановления

RPO определяет допустимую точку потери данных относительно сбоя. RTO — допустимую продолжительность восстановления. Для этой системы показатели должны относиться к работоспособной услуге, а не только к поднятому процессу PostgreSQL. ([NIST Computer Security Resource Center][13])

### Предлагаемые цели пилота

| Показатель                  | Отправная точка для согласования                                                         |
| --------------------------- | ---------------------------------------------------------------------------------------- |
| RPO рабочих данных          | Не более 15 минут                                                                        |
| RTO основного сервиса       | Не более 4 часов на заранее зафиксированном объёме данных                                |
| Независимая фиксация аудита | Целевая задержка до 60 секунд в штатном режиме; отдельно измеряется поведение при отказе |
| Проверка восстановления     | До приёмки пилота, после существенных изменений; далее, например, ежеквартально          |
| Область восстановления      | БД, файлы, необходимые ключи, конфигурация, актуальные запреты доступа и удаления        |

**Задержка доставки аудита — не его RPO.** Outbox в той же БД предотвращает расхождение при откате транзакции, но не гарантирует нулевую потерю при уничтожении всего узла до репликации. Если заказчик требует нулевую потерю уже подтверждённых утверждений или событий, это отдельное требование к синхронной устойчивой записи и инфраструктуре.

### Что резервировать

Для PostgreSQL нужны согласованные базовые копии и WAL для восстановления на момент времени. Но WAL не восстанавливает конфигурационные файлы вроде `postgresql.conf` и `pg_hba.conf`; их нужно сохранять отдельно. Сам WAL также является чувствительными данными. ([PostgreSQL][14])

Файловое хранилище должно восстанавливаться согласованно с БД. Ситуация «версия протокола в таблице есть, соответствующего PDF нет» не считается успешным восстановлением.

### Проверяемый сценарий

На изолированном стенде поднимается система из резервной копии без использования рабочих дисков. Фиксируются начало аварии, доступная точка восстановления и момент прохождения приёмочных проверок.

Проверяются контрольные суммы оригиналов и утверждённых файлов, связи версий, поручения, доступ пользователей и целостность аудита. До открытия доступа применяются актуальные удаления и отзывы прав, старые сессии аннулируются.

Обязательные отрицательные проверки: удалённая встреча не возвращается пользователю; отозванный пользователь не входит; чужая организация недоступна; намеренно уничтоженный ключ не появляется из старого backup.

Успешная проверка backup-файлов не заменяет такой запуск. PostgreSQL прямо предупреждает, что `pg_verifybackup` не способен проверить всё, что потребуется при реальном восстановлении. В restic обычный `check` также не равнозначен чтению всего содержимого; для этого предусмотрен `--read-data`. ([PostgreSQL][15])

Результат испытания — измеренные RPO/RTO, объём данных, конфигурация, команды, ошибки и повторные проверки. Не только скриншот «backup completed».

## 9. Минимальная эксплуатационная архитектура

Для пилота достаточно следующего разделения, без обязательного внедрения большого SIEM или брокера сообщений:

```text
Пользователь / бот / MCP
        → общий сервис проверки прав и бизнес-операций
        → PostgreSQL: данные, версии, outbox
        → защищённое файловое хранилище

Outbox + события безопасности
        → отдельный коллектор
        → защищённый архив аудита
        → поисковый индекс
        → контролируемая выгрузка

БД + файлы + конфигурация
        → отдельный резервный репозиторий

Актуальный реестр удалений и отзывов
        → обязательный этап процедуры восстановления
```

Принципиальны **разные полномочия и независимость отказов**, а не количество контейнеров. Backup на том же диске и архив аудита под тем же полным административным доступом не обеспечивают нужной независимости.

Отдельно должны быть назначены владельцы мониторинга: задержка аудита, пропуски контрольных точек, неуспешное архивирование WAL, возраст последней пригодной копии, просроченные удаления, ошибки очистки и незавершённые восстановления.

## 10. Пакет доказательств пилота

Каждое доказательство предлагаю привязывать к версии системы, конфигурации, окружению, дате испытания и конкретному требованию.

| Раздел                             | Что включить                                                                                                          |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| **Периметр и ответственность**     | Какие организации, площадки и компоненты проверяются; владельцы доступа, ключей, backup и удаления; что вне периметра |
| **Потоки данных**                  | Источники, преобразования, места хранения, производные копии, границы доверия, протоколы и шифрование                 |
| **Внешние соединения**             | Разрешённые назначения, назначение соединения, передаваемые категории данных, владелец и результаты проверки          |
| **Компоненты и лицензии**          | Зафиксированные версии, образы и хеши, зависимости, лицензии кода и моделей, обязательства при поставке               |
| **Политики**                       | Роли, экспорт, сроки хранения, удержания, ключи, RPO/RTO, действия при отказе аудита                                  |
| **Протоколы испытаний**            | Предусловия, команды или сценарий, ожидаемый и фактический результат, ссылки на доказательства                        |
| **Эксплуатационные подтверждения** | Результаты восстановления, очистки, проверки целостности, оповещений и разбора ошибок                                 |
| **Реестр несоответствий**          | Ограничение, риск, ответственный, срок исправления, решение заказчика и результат повторной проверки                  |

У пакета — собственный манифест файлов и контрольных сумм. Секреты и реальные закрытые записи в него не включаются: тесты предпочтительно выполнять на синтетических данных с уникальными контрольными маркерами.

### Реестр внешних соединений

Для каждого соединения нужны: процесс-источник, зона, адрес назначения, направление, порт, протокол, цель, категории данных, способ аутентификации без секрета, обязательность и правило сетевого доступа.

Проверять следует не только AI API и мессенджеры, но и IdP, DNS/NTP, проверку сертификатов, обновления, загрузку моделей, телеметрию, аварийные отчёты, внешние шрифты, генератор документов, поддержку и резервные копии.

Предлагаемое испытание: запретить все несогласованные исходящие соединения и пройти полный цикл встречи. Затем сопоставить фактически наблюдавшиеся соединения с реестром. Проверять нужно и серверы, и браузерную часть.

### Лицензии: пример для эксплуатационных компонентов

| Компонент            | Что подтверждено в upstream                                                                                      |
| -------------------- | ---------------------------------------------------------------------------------------------------------------- |
| PostgreSQL и pgAudit | PostgreSQL License. ([PostgreSQL][16])                                                                           |
| pgBackRest           | MIT.                                                                                                             |
| restic               | BSD-2-Clause.                                                                                                    |
| FFmpeg               | Базово LGPL; итоговые условия зависят от включённых компонентов и параметров сборки, включая GPL. ([FFmpeg][17]) |

Это **не лицензионная проверка будущей поставки**. Нужна ведомость именно поставляемых версий и сборок. SBOM в формате CycloneDX позволяет описывать компоненты, зависимости и лицензии. ([CycloneDX][18])

Отдельными строками учитываются веса ASR/LLM, токенизаторы, GPU-компоненты, базовые образы, библиотеки экспорта и шрифты. Лицензия репозитория модели не должна автоматически считаться лицензией её весов.

### Обязательные испытания

| Проверка                       | Критерий приёмки                                                                                                                |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| Изоляция организаций           | Подмена ID не даёт доступ к оригиналам, версиям, поиску, экспорту и чужому аудиту                                               |
| Отзыв доступа                  | Последующие запросы, старые ссылки и ожидающие выгрузки не обходят отзыв                                                        |
| Полнота событий                | Все согласованные действия дают ожидаемые события; повтор запроса не повторяет бизнес-изменение                                 |
| Отсутствие содержимого в логах | Контрольные тексты и секреты не обнаруживаются в аудитах, трассировках, ошибках БД и очередях                                   |
| Подмена и отказ аудита         | Изменение блока и удаление конца обнаруживаются; сбой хранения не допускает неучтённую чувствительную операцию                  |
| CSV                            | Верная область и количество строк, проверяемый манифест, отсутствие исполняемых формул в поддерживаемом клиенте                 |
| Удаление                       | Проверены рабочие и временные копии, гонки с обработчиками, ожидание backup и отсутствие «воскрешения» после restore            |
| Восстановление                 | Система поднята из backup на отдельной среде, проверены права и файлы, фактические RPO/RTO укладываются в согласованные пределы |
| Изоляция исходящего трафика    | Полный цикл работает без несогласованных внешних соединений                                                                     |

Для доказательств нужны воспроизводимые сценарии и фактические результаты, включая неудачные. Набор исключительно успешных скриншотов не позволяет оценить границы системы.

## 11. SOC 2: где заканчивается внутренняя оценка

AICPA публикует **2017 Trust Services Criteria с пересмотренными Points of Focus 2022**. Критерии охватывают Security, Availability, Processing Integrity, Confidentiality и Privacy. Применимость категорий и периметр оценки должны быть определены явно. ([AICPA & CIMA][19])

Для этой системы предлагаемая связь выглядит так:

| Категория            | Примеры проверяемых мер                                                                   |
| -------------------- | ----------------------------------------------------------------------------------------- |
| Security             | Объектные права, аудит, контроль администраторов, реакция на отказы                       |
| Availability         | Резервирование, наблюдаемость, восстановление и измеренные RPO/RTO                        |
| Processing Integrity | Однократность изменений, связь утверждения с версией, соответствие экспорта               |
| Confidentiality      | Классификация, ограниченная выдача, ключи, сроки хранения и удаление                      |
| Privacy              | Минимизация персональных данных, установленные цели обработки и соответствующие процедуры |

Это сопоставление отдельных мер, **не доказательство выполнения всех критериев**.

### Три разных результата

| Формат                       | Что оценивается                                                                    | Что получается                            |
| ---------------------------- | ---------------------------------------------------------------------------------- | ----------------------------------------- |
| Внутренняя оценка готовности | Выбранные меры, доказательства, пробелы и план исправлений                         | Внутренний отчёт; не SOC 2 report         |
| Независимый SOC 2 Type 1     | Устройство и внедрение средств контроля на определённую дату                       | Отчёт независимой аудиторской организации |
| Независимый SOC 2 Type 2     | Дополнительно — операционная эффективность средств контроля за определённый период | Отчёт по результатам проверки за период   |

Различие Type 1 и Type 2, а также независимый характер проверки описаны в материалах аудиторской организации Schellman, непосредственно оказывающей услуги SOC 2. ([Schellman][20])

Пилот подтверждает ограниченный набор технических свойств в конкретной конфигурации. Полноценная оценка готовности должна также затронуть управление изменениями, инцидентами, поставщиками, персоналом и распределение ответственности.

Для установки у заказчика особенно важно разделить обязанности: кто обновляет узлы, управляет ключами, отзывает доступ, хранит backup и выполняет восстановление. Нельзя автоматически распространить оценку разработчика на любую инсталляцию его продукта.

Корректный шаблон формулировки **после выполнения внутренних работ**:

> «Проведена внутренняя оценка готовности системы в указанном периметре по выбранным Trust Services Criteria. Зафиксированы выполненные проверки, ограничения и план устранения несоответствий. Независимая проверка SOC 2 не проводилась; отчёт SOC 2 не выпускался».

**Называть это “сертификацией SOC 2” нельзя.**

## Что закрепить в критериях приёмки

Заказчику стоит принимать пилот не по наличию кнопок «Журнал» и «Удалить», а по доказанным обязательствам:

**какие действия фиксируются; к какой версии они относятся; кто способен изменить доказательства; какое окно потери остаётся; какие копии ещё существуют после удаления; и за какое фактически измеренное время система восстанавливается без возврата удалённых данных и отозванных прав.**

Именно эти параметры превращают эксплуатацию из декларации в проверяемую процедуру.

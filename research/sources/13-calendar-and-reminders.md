## Вывод

**Для пилота рекомендую Google Calendar API + PostgreSQL + один фоновый процесс.** Календарь отвечает за расписание связанных встреч, корпоративная система — за поручения, получателей, согласия и правила уведомлений. Напоминания планируются и отменяются в вашей БД, а мессенджеры используются только для отправки.

Основная цепочка:

```text
Google Calendar: изменение расписания
    -> webhook или периодическая сверка
    -> чтение актуального состояния Calendar API
    -> обновление встречи в PostgreSQL
    -> пересчёт напоминаний

Корпоративная система: изменение поручения или согласия
    -> бизнес-операция и запись изменения в одной транзакции
    -> пересчёт напоминаний

Наступило время отправки
    -> повторная проверка актуальности, согласия, прав и привязки
    -> формирование разрешённого сообщения
    -> отправка через адаптер канала
    -> фиксация результата
```

**Главное ограничение:** можно исключить повторное создание задания и повторную обработку webhook. Но нельзя обещать универсальную доставку «ровно один раз» через любой мессенджер: если провайдер принял сообщение, а ответ потерялся, автоматический повтор может создать дубль. Для этого нужен отдельный статус «результат неизвестен», а не обычный retry.

Ниже — результат проверки официальной документации на **23 сентября 2026 года**, рекомендуемая архитектура и программа PoC. Реальные подключения к аккаунтам и отправки в рамках этого исследования не выполнялись.

## 1. Что считать источником истины

### Расписание — из одного выбранного события Calendar

Для каждой корпоративной встречи нужна **одна основная связь**:

```text
tenant_id
internal_meeting_id
google_connection_id
calendar_id
event_id
```

Рекомендую связывать встречу с событием в календаре организатора. Копии приглашения в личных календарях участников не должны создавать отдельные корпоративные встречи и отдельные напоминания.

Это важно и для отмены: удаление участником своей копии приглашения не следует трактовать как отмену совещания для всей организации. У Google отменённые события, удалённые копии и исключения повторяющихся событий представлены через `status=cancelled`, поэтому нужно учитывать, **какую именно копию вы наблюдаете**. ([Google for Developers][1])

Если доступ есть только к календарю участника, возможен более узкий режим: «следить за встречей для этого пользователя». Глобальную отмену корпоративной встречи из такого источника я бы не разрешал.

### Поручения, права и согласия — из корпоративной БД

В PostgreSQL должны оставаться авторитетными:

* исполнитель, срок и состояние поручения;
* права пользователя на встречу и поручение;
* согласие на конкретные категории уведомлений и каналы;
* проверенная привязка аккаунта мессенджера;
* разрешённый состав сообщения.

**Наличие пользователя в Google `attendees` не должно автоматически выдавать ему права на корпоративный протокол. Подключение календаря не должно автоматически включать рассылку.** Это рекомендуемое разделение полномочий.

### Создание события — отдельная идемпотентная операция

При создании встречи сохраняйте собственный ключ операции и заранее сформированный Google `event.id`. Если запрос оборвался, повторяйте операцию с тем же ID либо проверяйте существование события, а не создавайте новое. Google прямо рекомендует пользовательские ID для защиты от повторного создания после неопределённого результата запроса. ([Google for Developers][2])

Для изменения используйте `etag` и `If-Match`. При `412 Precondition Failed` перечитывайте событие и разрешайте конфликт, а не перезаписывайте чужое изменение. ([Google for Developers][3])

При связывании существующей встречи вообще не нужен `insert`: достаточно проверить доступ, сохранить соответствие и начать наблюдение.

## 2. OAuth: какие права действительно нужны

### Минимальные scopes

В таблице сокращены префиксы: например, `calendar.events.owned` означает `https://www.googleapis.com/auth/calendar.events.owned`.

| Сценарий                                                                   | Scope                            | Ограничение                                                                 |
| -------------------------------------------------------------------------- | -------------------------------- | --------------------------------------------------------------------------- |
| Создавать и изменять встречи в собственных календарях пользователя         | `calendar.events.owned`          | Рекомендуемый вариант для пилота                                            |
| Только читать события собственных календарей                               | `calendar.events.owned.readonly` | Для режима «связать и наблюдать»                                            |
| Читать доступные пользователю события, включая чужие расшаренные календари | `calendar.events.readonly`       | Фактический доступ ограничен правами пользователя                           |
| Изменять события также в доступных общих календарях                        | `calendar.events`                | Запрашивать только при такой необходимости                                  |
| Показать пользователю список календарей                                    | `calendar.calendarlist.readonly` | Не требуется при работе только с `primary`                                  |
| Получить свойства календаря, включая его часовой пояс                      | `calendar.calendars.readonly`    | Дополнительный scope для соответствующего API                               |
| Работать только с отдельными календарями, созданными приложением           | `calendar.app.created`           | Это **не** ограничение «только созданные нами события в основном календаре» |

Назначения scopes подтверждены справочником Google. Полный `calendar`, доступ к ACL и Gmail для описанного сценария не нужны. ([Google for Developers][4])

**Мой выбор:** начать с `calendar.events.owned`; добавить `calendar.calendarlist.readonly`, только если нужен выбор календаря. Для `events.watch` отдельного «webhook scope» нет: метод принимает соответствующие Calendar scopes. ([Google for Developers][5])

Выбор одного календаря в интерфейсе дополнительно ограничивайте на стороне приложения: пользовательское разрешение на события собственных календарей само по себе не сужается до выбранного `calendar_id`.

### Привязка личности

Используйте серверный OAuth authorization code flow, защиту `state`, точные разрешённые redirect URI и `access_type=offline`, чтобы получить возможность обновлять доступ без присутствия пользователя. Проверяйте реально выданные scopes: нельзя считать, что пользователь обязательно согласился со всеми запрошенными правами. Токены храните только на сервере, в зашифрованном виде. ([Google for Developers][6])

Для идентификации Google-аккаунта можно дополнительно использовать OIDC. Внешнюю личность связывайте по проверенному `sub`, а не только по email: Google определяет `sub` как стабильный идентификатор аккаунта. Привязку создавайте из уже авторизованной сессии корпоративного пользователя. ([Google for Developers][7])

### Не смешивать сроки доступа

Нужны независимые состояния:

**Истёк access token.** Обновить через refresh token. Это штатная техническая операция.

**Отозван или недействителен refresh token.** Перевести подключение в `reauth_required`, прекратить бесконечные повторы и показать необходимость переподключения. Google перечисляет отзыв пользователем, длительное неиспользование, ограничения администратора и другие причины прекращения действия refresh token. Для внешнего приложения в режиме **Testing** Calendar OAuth refresh token обычно истекает через **7 дней**. ([Google for Developers][8])

**Истекло согласие на уведомления.** Прекратить отправку независимо от работоспособности OAuth. Обновление токена не продлевает согласие.

Рекомендую отдельно хранить `valid_until`, `revoked_at`, категории уведомлений, канал и версию согласия. Уведомление о необходимости переподключить календарь тоже нельзя отправлять через уже запрещённый канал: в таком случае остаётся интерфейс системы.

Для внутреннего приложения одной Workspace-организации и внешнего продукта на несколько организаций различаются требования Google к проверке OAuth-приложения. Для внешней публикации нужно заранее проверить категорию scopes и процедуру verification; внутренние приложения организации имеют исключение из дополнительной проверки чувствительных scopes. ([Google for Developers][9])

## 3. Синхронизация: webhook недостаточно

### Основной механизм: `events.watch` + incremental sync

**Webhook Google Calendar — сигнал «коллекция изменилась», а не готовое изменение встречи.** Уведомление не содержит тела события. Google также предупреждает о возможной потере части уведомлений. Поэтому после сигнала нужно читать Calendar API, а отсутствие сигналов нельзя считать отсутствием изменений. ([developers.google.com][10])

Рекомендую такой порядок.

**Первичная загрузка.** Прочитать все страницы `events.list`, применить результат и сохранить `nextSyncToken`, полученный на последней странице.

**Дальнейшие обновления.** Вызывать `events.list(syncToken=...)`, обработать все страницы, включая удалённые события, и только после успешного применения результата заменить sync token.

**Сброс курсора.** При `410 Gone` выполнить полную синхронизацию заново. Это сброс локальной календарной проекции, а не повод удалять поручения, согласия и журнал отправок. Google документирует полный пересбор состояния после недействительного sync token. ([Google for Developers][11])

При пересборке я бы использовал временное поколение данных: загрузить новую проекцию, проверить завершённость, затем активировать её. Пока источник не восстановлен, связанные напоминания о встречах приостанавливать.

### Важное ограничение фильтров

С `syncToken` нельзя произвольно совмещать `timeMin`, `timeMax`, `updatedMin`, `q`, `iCalUID` и некоторые другие фильтры. Параметры синхронизации должны сохранять согласованность между запросами. Поэтому схема «каждый раз синхронизируем следующие 30 дней с новым `timeMin` и старым токеном» неправильна. ([Google for Developers][12])

Практичный вариант: синхронизировать метаданные выбранного календаря, а горизонт планирования и отбор связанных встреч выполнять локально. Ненужные описания личных событий не сохранять.

### Приём и продление webhook

Для каждого наблюдаемого календаря сохраняйте `channel_id`, `resource_id`, секретный `channel_token` и срок окончания подписки.

Google передаёт собственный токен приложения в `X-Goog-Channel-Token`; его нужно проверять вместе с идентификаторами канала и ресурса. Это не HMAC-подпись тела. `X-Goog-Message-Number` не является непрерывной последовательностью. Первое уведомление `sync` может прийти до завершения ответа на создание подписки. ([developers.google.com][10])

Поэтому запись ожидаемой подписки лучше создавать **до** вызова `watch`. Обработчик должен быстро сохранить сигнал в БД и вернуть успешный ответ; тяжёлая синхронизация выполняется фоновым процессом.

У `events.watch` указан TTL по умолчанию **604 800 секунд, то есть 7 дней**. Ориентироваться нужно на фактически возвращённое `expiration`, а не считать семь дней вечной константой или гарантированным максимумом. Новую подписку создавайте заранее, допуская короткое пересечение двух каналов. ([Google for Developers][5])

### Страховочная сверка

Для пилота предлагаю:

**Периодическую incremental sync**, например раз в пять минут с небольшим случайным сдвигом. Это параметр проекта, а не требование Google.

**Проверку конкретной встречи через `events.get` перед отправкой**, один раз на встречу и пакет получателей, а не отдельно на каждого человека.

Второй шаг сокращает вероятность отправить напоминание по ещё не синхронизированной отмене. Если достоверность расписания подтвердить нельзя, строгий режим должен отложить отправку, а после окончания полезного интервала — пропустить её.

Полностью устранить гонку «Google изменился сразу после проверки» это не может. Гарантия всегда ограничена последним подтверждённым состоянием внешнего источника.

## 4. Часовые пояса и повторяющиеся встречи

В модели нужны **UTC-момент и исходная временная семантика**.

Для встречи храните `start_at_utc`, `end_at_utc` и IANA-зону, например `Asia/Almaty`. Для поручения — срок, его зону и признак «точное время» либо «только дата». Google поддерживает IANA-зоны на уровне календаря и события; для повторяющейся встречи зона определяет раскрытие повторений. ([Google for Developers][13])

Рекомендую следующие правила:

**Дата без времени не превращается молча в полночь UTC.** Для поручения «до 30 сентября» нужно согласованное правило: например, срок в конце рабочего дня исполнителя, а уведомление утром в той же зоне.

**Смена зоны просмотра не меняет момент встречи.** Пользователь может видеть другой локальный час, но очередь продолжает работать с тем же UTC-моментом.

**Повторения не считаются прибавлением 24 часов.** Используйте календарные правила в исходной зоне и отдельно тестируйте переходы летнего времени.

Для отдельного повторения ключ должен учитывать `recurringEventId` и `originalStartTime`: последнее остаётся идентификатором экземпляра даже после переноса. Отмена одного экземпляра не должна отменять всю серию. ([Google for Developers][14])

Для пилота допустимо сначала поддержать разовые встречи, но повторяющиеся нужно явно пометить как неподдерживаемые, а не обрабатывать приблизительно.

## 5. Минимальная архитектура и данные

### Достаточно двух процессов и одной БД

**API приложения** принимает OAuth callback, webhook и пользовательские команды.

**Один фоновый процесс** выполняет синхронизацию, обновление токенов, продление подписок, пересчёт расписания и отправку.

**PostgreSQL** хранит всё необходимое для восстановления после перезапуска. Kafka, Redis, RabbitMQ, Temporal и отдельный планировщик на каждую встречу для этого пилота не требуются.

Логически нужны следующие группы таблиц:

| Данные                          | Что хранить                                                                             |
| ------------------------------- | --------------------------------------------------------------------------------------- |
| Подключения                     | Google identity, выданные scopes, зашифрованные токены, состояние подключения           |
| Синхронизация                   | Календарь, sync token, параметры выборки, подписки, последняя успешная сверка           |
| Встречи и поручения             | Актуальное состояние, основная внешняя связь, версия расписания                         |
| Привязки и согласия             | Пользователь, организация, проверенные ID канала, категории, сроки, отзыв, версии       |
| Входящие и внутренние изменения | Ключ дедупликации, тип события, состояние обработки                                     |
| Напоминания и попытки           | Время отправки, срок полезности, получатель, версия, результат, ID сообщения провайдера |

Это таблицы одной системы, а не предложение построить шесть микросервисов.

### Изменение данных и запись события — в одной транзакции

Например, операция переназначения поручения должна атомарно:

```text
изменить исполнителя
-> увеличить версию данных для напоминаний
-> записать TaskAssigneeChanged
```

Такую запись изменений обычно называют **transactional outbox**. Здесь это обычная таблица в той же PostgreSQL: фоновый процесс читает её и пересчитывает задания.

Webhook не должен непосредственно отправлять сообщение. Он только инициирует обновление источника.

### Задание — кандидат на отправку, а не заранее разрешённое сообщение

В очереди храните ссылки на сущности и версии, а не окончательный приватный текст.

Перед **каждой попыткой** проверяйте:

```text
сущность ещё активна
AND версия задания соответствует текущей версии
AND пользователь всё ещё нужный получатель
AND у него есть объектные права
AND согласие действует
AND привязка канала активна
AND политика разрешает этот состав сообщения
AND напоминание ещё полезно
```

После этого формируйте сообщение из текущих данных.

Так переназначение поручения, закрытие задачи или отзыв согласия остановят даже задание, которое было запланировано несколько дней назад.

## 6. Идемпотентность, отмена и retries

### Три независимых уровня защиты от дублей

**Первый — входящие события.** Сохраняйте ключ провайдера и не обрабатывайте одно событие повторно. Для Calendar подходит сочетание подписки и номера сообщения; дополнительно объединяйте несколько сигналов в одну синхронизацию календаря.

**Второй — бизнес-состояние.** Повторно полученный объект не должен увеличивать версию расписания. Сравнивайте значимые поля: время, отмену, исполнителя, срок, состояние. Изменение описания не должно автоматически создавать новое напоминание.

**Третий — намерение отправить напоминание.** Нужен уникальный ключ примерно такого вида:

```text
tenant_id + entity_id + occurrence_id
+ recipient_id + reminder_rule_id + reminder_generation
```

Повторная попытка использует тот же ключ, а не новый UUID.

Если пользователь выбирает один основной канал, логическое напоминание должно быть **независимым от канала**. Иначе случайная смена Telegram на Slack создаст второе сообщение. Отдельные отправки по нескольким каналам допустимы только как явно выбранная настройка.

### Что делать при изменениях

| Изменение                     | Действие                                                                            |
| ----------------------------- | ----------------------------------------------------------------------------------- |
| Встреча перенесена            | Старые задания пометить `superseded`, создать задания для новой версии              |
| Встреча отменена              | Отменить все ещё не отправленные напоминания соответствующей встречи или экземпляра |
| Поручение переназначено       | Убрать старого получателя, проверить нового и пересчитать расписание                |
| Поручение закрыто             | Отменить напоминания о приближении срока и просрочке                                |
| Согласие истекло или отозвано | Заблокировать новые попытки, даже если задание уже выбрано обработчиком             |
| Аккаунт отвязан               | Остановить отправки по этой привязке                                                |
| Согласие выдано заново        | Планировать будущие уведомления, не оживлять старую очередь автоматически           |

При переносе на более раннее время отдельно задайте правило для уже прошедшего момента напоминания: «отправить сейчас, пока встреча ещё впереди» либо «пропустить». Не оставляйте это случайным следствием реализации.

### Конкурентная обработка

Для выбора готовых заданий подходит `FOR UPDATE SKIP LOCKED`: PostgreSQL прямо отмечает применимость этого механизма к очередям с несколькими обработчиками. Транзакция захвата должна быть короткой; внешний HTTP-запрос не следует выполнять под долгой блокировкой БД. ([PostgreSQL][15])

Добавьте срок аренды задания и идентификатор обработчика. Но **истечение аренды задания в состоянии `sending` не означает, что его можно безопасно отправить заново**: предыдущий процесс мог успеть обратиться к провайдеру.

### Неопределённый результат — отдельный класс

Пример:

```text
провайдер принял сообщение
-> соединение оборвалось
-> приложение не записало ответ
```

В этом случае уникальный индекс в вашей БД не предотвращает дубль при повторном внешнем запросе.

Моя рекомендация для требования «без дублей»:

**Однозначно отклонённые попытки повторять. Неопределённые — переводить в `unknown`, сверять с провайдером, когда это возможно, и не повторять вслепую.**

Цена такой политики — отдельные пропущенные уведомления. Альтернатива «повторять до подтверждения» повышает доставляемость, но допускает дубли. Это продуктовый выбор, который нужно зафиксировать, а не скрывать под словом «идемпотентность».

### Политика ошибок

| Ситуация                                              | Реакция                                                           |
| ----------------------------------------------------- | ----------------------------------------------------------------- |
| Google `401` из-за истечения доступа                  | Один согласованный refresh, затем повтор запроса                  |
| Refresh недействителен                                | `reauth_required`; не повторять бесконечно                        |
| Google `403`                                          | Разбирать причину: квота и запрет доступа требуют разных действий |
| Google `410` при incremental sync                     | Полная пересборка календарной проекции                            |
| Google `409` при создании                             | Проверить событие с ранее заданным ID                             |
| Google `412`                                          | Перечитать событие и обработать конфликт                          |
| Провайдер явно ограничил частоту                      | Учесть время ожидания, применить ограниченный backoff             |
| Бот заблокирован, приложение удалено, шаблон запрещён | Остановить соответствующие отправки до исправления причины        |
| Timeout или сбой после возможного принятия сообщения  | `unknown`, а не слепой повтор                                     |

Коды Calendar и рекомендуемые способы обработки описаны в документации ошибок Google. Slack для `429` возвращает `Retry-After`, Telegram использует поле `retry_after` при ограничении частоты. ([Google for Developers][16])

Все retries ограничивайте не только количеством попыток, но и `valid_until`: напоминание «за пять минут до встречи» не должно внезапно прийти через час после её начала.

Резервный канал допустим только с отдельным действующим согласием. После `unknown` автоматически переключаться на другой канал опасно: первое сообщение уже могло дойти.

### Политика приватности поверх правил платформ

Для пилота рекомендую **только личные сообщения**. Публикация в общий канал или чат осложняет выполнение требования «только пользователи с согласием»: сообщение увидит аудитория канала, а не только выбранный получатель.

Безопасный шаблон по умолчанию:

> В системе есть напоминание о предстоящей встрече. Откройте карточку для подробностей.

Название, точное время, формулировку поручения и имя ответственного добавляйте только согласно политике организации для конкретного канала. Транскрипты, вложения и ссылки с обходом авторизации в уведомления не включайте.

Ссылка должна вести в приложение с повторной проверкой прав. В Slack отдельно отключайте `unfurl_links` и `unfurl_media`, если предпросмотр способен раскрыть сведения; проверяйте также запасной текст уведомления, а не только визуальную карточку. ([Slack Developer Docs][18])

**Встроенные Google reminders — другой механизм.** Они персональны и поддерживают email/popup, а не произвольные мессенджеры. Их нельзя считать вашей очередью отправки. Настройки пользователя не следует молча отключать ради обещания «одно сообщение вообще во всех приложениях». ([Google for Developers][23])

Приглашения и письма Google через `sendUpdates` также отделите от напоминаний. Не добавляйте получателей автоматически без предусмотренного разрешения; использование `sendUpdates=none` как универсального способа подавить письма может иметь нежелательные последствия для синхронизации приглашений. ([Google for Developers][24])

## 8. Наблюдаемость и эксплуатационные ограничения

### Что должно быть видно без чтения логов вручную

В интерфейсе подключений показывайте: `работает`, `синхронизация задерживается`, `нужно переподключить`, `канал недоступен`, `согласие истекло`.

Для оператора достаточно следующих групп показателей:

| Область        | Что измерять                                                                                  |
| -------------- | --------------------------------------------------------------------------------------------- |
| Calendar       | Возраст последней успешной синхронизации, очередь сверки, окончание подписок, ошибки refresh  |
| Планирование   | Просрочка обработки задания, число отменённых и заменённых заданий                            |
| Отправка       | Принято провайдером, явно отклонено, `unknown`, число повторов, возраст необработанных ошибок |
| Инфраструктура | Работа фонового процесса, размер очереди, время выполнения запросов                           |

Нужна сквозная связь:

```text
входящее событие
-> версия встречи/поручения
-> reminder_id
-> attempt_id
-> provider_message_id
```

Согласие, его версию, решение проверки прав и причину подавления фиксируйте в аудите. Токены, содержимое протоколов и приватные тексты сообщений в обычные логи не помещайте.

**«Провайдер принял» не равно «человек прочитал».** Храните эти состояния отдельно и заполняйте доставку/прочтение только там, где канал действительно даёт соответствующее подтверждение. Например, обычный успешный `chat.postMessage` возвращает идентификаторы сообщения и канала — не доказательство прочтения. ([Slack Developer Docs][18])

### Квоты Google: есть изменения 2026 года

В текущей документации для новых проектов указаны **10 000 запросов/мин на проект** и **600 запросов/мин на пользователя проекта**; часть ранее использовавшихся проектов сохраняет прежние квоты. Также указан дневной порог 1 000 000 запросов. При этом Google пишет о планируемой платности превышения позднее в 2026 году с предварительным уведомлением, а не об уже универсально включённой оплате. Проверять нужно фактические квоты своего проекта в Cloud Console. ([Google for Developers][25])

Для небольшого пилота это не повод строить отдельную инфраструктуру, но повод объединять сигналы webhook и не делать полный опрос каждого календаря каждую секунду.

## 9. Сценарий PoC

### Подготовка

Нужны тестовый Google Cloud project с Calendar API и OAuth client, разрешённый HTTPS callback для webhook, тестовые пользователи и хотя бы один рабочий канал отправки.

Для общей логики проще начать с Telegram. Затем выполнить тот же набор проверок через Slack и Teams. Для WhatsApp отдельно проверить одобренный шаблон и отправку **вне** 24-часового окна: успех внутри активного диалога не доказывает пригодность к регулярным напоминаниям.

В тестах используйте управляемые часы и имитатор ошибок провайдеров. Несколько реальных отправок подтверждают интеграцию; сетевые гонки и падения воспроизводятся управляемыми тестами.

### Основная демонстрация

Создайте две встречи: **M1 для переноса и успешной отправки**, **M2 для отмены**. Это разные ветки: отменённая встреча не должна затем давать «одно правильное напоминание».

Для M1:

```text
первоначальный старт: T + 20 минут
правило: напомнить за 5 минут
первоначальная отправка: T + 15 минут

перенос старта: T + 40 минут
новая отправка: T + 35 минут
```

Получатели: B — согласие и привязка действуют; C — согласие истекает в `T+30`; D — нет разрешённой привязки.

| Проверка                                               | Ожидаемый результат                                                                             |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| Создать M1; повторить запрос создания с тем же ключом  | Одно событие Google и одна внутренняя связь                                                     |
| Перенести M1; прислать повторные и запоздавшие webhook | В БД одна актуальная версия расписания; лишних заданий нет                                      |
| Наступает старое время `T+15`                          | Ни одного напоминания                                                                           |
| Наступает новое время `T+35`                           | B получает одно напоминание; C и D не получают ничего                                           |
| Создать M2 и отменить до срока уведомления             | Все неотправленные задания M2 отменены                                                          |
| Переназначить поручение A → B                          | A больше не получатель; B проходит отдельную проверку                                           |
| Закрыть поручение до отправки                          | Напоминание о сроке не отправляется                                                             |
| Истечь access token перед сверкой                      | Успешный refresh, без повторного задания                                                        |
| Отозвать Google-доступ                                 | Подключение требует повторной авторизации; недостоверные календарные уведомления приостановлены |
| Запустить два обработчика                              | Одно задание не отправляется обоими                                                             |
| Получить явный `429`, затем успех                      | Повтор после ожидания; одно принятое сообщение                                                  |
| Потерять ответ после принятия сообщения                | `unknown`, без слепой повторной отправки                                                        |

Локальные поручения не обязательно останавливать при потере Google-доступа: если их состояние хранится в вашей системе и отдельное согласие на канал действует, они не зависят от календарной синхронизации.

### Отдельные испытания перед эксплуатацией

Потерять webhook и убедиться, что периодическая сверка обнаружит перенос. Принудительно получить `410` и восстановить проекцию без удаления журнала отправок. Проверить отменённый экземпляр серии, событие на весь день, разные часовые пояса и переход летнего времени. Отозвать согласие непосредственно перед финальной проверкой отправки.

Для входящих событий каналов проверяется также подлинность: например, Slack использует подпись запроса и timestamp, Telegram поддерживает секрет webhook-заголовка. Повторная доставка не должна повторно менять состояние. ([Slack Developer Docs][26])

### Критерий приёмки

**В штатном сценарии — одно принятое провайдером напоминание на актуальную встречу, получателя и правило. Ноль отправок по старому времени, отменённой встрече, закрытому поручению, истёкшему согласию и отсутствующей привязке.**

Для аварийного сценария с неопределённым результатом критерий другой: **нет слепого дубля, есть видимый статус `unknown` и процедура разбора**. Уже начатую внешнюю отправку нельзя гарантированно отозвать задним числом.

## Итоговая рекомендация

Начинать стоит с **основного календаря организатора, разовых встреч, личных уведомлений и одного выбранного канала на пользователя**. Хранить расписание отправок в PostgreSQL; строить Calendar-синхронизацию на `watch + syncToken + страховочная сверка`; разрешать сообщение только после повторной проверки текущих данных.

Самое важное здесь — не выбор библиотеки планировщика, а четыре явных решения: **кто определяет актуальное расписание, что инвалидирует задание, когда повтор безопасен и что делать при неизвестном результате доставки**.

Правила WhatsApp подтверждены открытыми страницами политики и тарификации Meta. Часть технической документации Cloud API при проверке не открылась, поэтому конкретные лимиты вашего бизнес-аккаунта, допуск шаблонов и обработку статусов доставки необходимо подтвердить в реальном PoC.

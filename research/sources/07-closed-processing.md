## Вывод

**Да. Весь путь — от загрузки записи до транскрипта, разделения говорящих, саммари, поручений и готового протокола — можно реализовать без обращения к внешним AI-сервисам.** Для распознавания и диаризации существуют документированные локальные реализации; языковые модели также можно обслуживать на собственном сервере. Облачный AI для этого не является обязательной зависимостью. ([GitHub][1])

**Рекомендую архитектуру из двух независимых частей: закрытый контур обработки и отдельный шлюз разрешённых интеграций.** Обработчики аудио и текста не имеют выхода в интернет. Шлюз может обращаться к согласованным API календарей и мессенджеров, но не получает произвольный доступ к записям и транскриптам.

Основная неопределённость здесь — не возможность автономного запуска, а **качество на реальных русско-казахских совещаниях и производительность выбранного оборудования**. Это нужно проверять отдельно.

Ниже — рекомендуемая архитектура по публичной документации, проверенной на **23 сентября 2026 года**. Это не аудит приватного репозитория и не результаты собственного нагрузочного испытания.

## 1. Что именно означает «закрытый контур»

Важно разделить три требования.

| Требование                                              | Что оно позволяет                                                                    | Что необходимо ограничить                                                                           |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| **Нельзя передавать данные внешнему AI**                | Локальные модели; разрешённые интеграции с корпоративными или внешними сервисами     | Любые внешние ASR/LLM API, облачные резервные обработчики                                           |
| **Содержание совещаний не должно покидать организацию** | Локальная обработка; наружу — только специально разрешённые уведомления и метаданные | Записи, транскрипты, саммари и тексты поручений нельзя отправлять даже в обычный внешний мессенджер |
| **Полная физическая изоляция — air gap**                | Работа исключительно с внутренними сервисами; контролируемый перенос обновлений      | Постоянные внешние интеграции невозможны: сетевой связи с ними по определению нет                   |

**Первое и второе требования совместимы с интеграциями, третье — только с внутренними интеграциями или офлайновым обменом.**

Для описанного продукта я бы зафиксировал такую политику:

> Содержание совещаний хранится и обрабатывается внутри корпоративного контура. Внешние интеграции работают через отдельный шлюз по белому списку операций и полей. Основной процесс не зависит от доступности этих интеграций.

Например, сообщение «Протокол готов, откройте корпоративную систему» может быть допустимо. Сообщение с полным текстом поручения, фамилиями и сроками — уже отдельная передача корпоративной информации, которую нужно согласовать.

Также стоит определить **границу ответственности за исходную запись**. Когда запись получена из облачной системы совещаний, локальная последующая обработка не делает сам исходный процесс совещания локальным. Для пилота разумнее начать с загрузки готового файла, а автоматическое получение записей и подключение бота к встречам рассматривать отдельным этапом.

## 2. Какие компоненты действительно можно запускать локально

### Распознавание, диаризация и языковая модель

| Задача                                   | Рекомендуемый кандидат                                              | Что подтверждено и что остаётся проверить                                                                                                                                                                                   |
| ---------------------------------------- | ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Распознавание речи**                   | `faster-whisper` + Whisper `large-v3`                               | Локальный запуск на CPU/GPU, квантование, временные метки. В Whisper предусмотрены русский и казахский языки. Наличие языка не доказывает качество на смешанных совещаниях. ([GitHub][1])                                   |
| **Разделение говорящих**                 | `pyannote.audio` + `speaker-diarization-community-1`                | Документирован полностью офлайновый запуск из локального каталога; поддерживаются CPU и GPU. Для первоначального получения весов нужно принять условия доступа. ([Hugging Face][2])                                         |
| **Саммари и поручения: базовый вариант** | Qwen3-14B, с проверенной квантованной сборкой                       | У семейства Qwen3 заявлены русский и казахский. Предлагаю как исходную точку сравнения, а не как доказанного победителя для протоколов. ([Hugging Face][3])                                                                 |
| **Кандидат для усиления казахского**     | `issai/Qwen3.5-9B-Kazakh`                                           | Адаптация ISSAI с расширенным казахским словарём, дополнительным обучением и документированным локальным запуском. Опубликованные оценки не заменяют проверку поручений на русско-казахских совещаниях. ([Hugging Face][4]) |
| **Сервер языковой модели**               | `llama.cpp` для простого пилота; `vLLM` для выделенного GPU-сервиса | Оба подходят для локального обслуживания моделей. vLLM поддерживает структурированный вывод по JSON Schema. Совместимость конкретной модели, квантования и версии движка нужно зафиксировать испытанием. ([GitHub][5])      |

**OpenAI-совместимый API не означает передачу данных в OpenAI.** Например, vLLM может принимать совместимые запросы на локальном адресе. Важно, куда направлен `base_url`, а не как называется клиентская библиотека. Это прямо показано и в документации модели ISSAI. ([Hugging Face][4])

Для эксплуатации лицензии кода и весов нужно учитывать раздельно. Например, у `speaker-diarization-community-1` указана **CC-BY-4.0**, у модели ISSAI — **Apache-2.0**. Само размещение модели на Hugging Face не определяет условия её использования. ([Hugging Face][2])

### Что важно для русского, казахского и смешанной речи

Я бы не строил первую версию на предположении «определили язык файла один раз — дальше всё распознано правильно». В контрольном наборе должны отдельно присутствовать русская, казахская и смешанная речь, включая переключение языка внутри реплики.

Для проекта рекомендую:

* сохранять исходный язык транскрипта; перевод, когда он нужен, делать отдельным локальным этапом;
* проверять имена, названия подразделений, суммы и даты отдельно от общей точности текста;
* сопоставлять реплики с участниками встречи через подтверждение человеком, а не автоматически считать `SPEAKER_02` конкретным сотрудником.

**Диаризация отвечает на вопрос «когда говорил один и тот же голос», а не гарантирует ФИО или восстановление двух одновременно звучащих голосов.** В документации WhisperX прямо отмечены ограничения на перекрывающейся речи и несовершенство диаризации. ([GitHub][6])

Когда источник предоставляет отдельные аудиодорожки участников, я бы сохранял их. Сводить всё в моно до анализа — значит добровольно терять полезную исходную информацию.

### Реальные приложения, на которые можно опереться

**Scriberr** — наиболее близкий из найденных примеров серверного приложения: локальная транскрипция, диаризация, временные метки, работа с аудио/видео и саммари через Ollama либо совместимый API. Есть Docker-развёртывание. При этом приложение использует SQLite и поддерживает внешних провайдеров: наличие такого проекта не доказывает готовность к корпоративной изоляции, разграничению доступа и отказоустойчивости. ([GitHub][7])

**Meetily** полезен как пример локального настольного помощника: запись звука, локальная транскрипция и саммари. Но это другой профиль продукта, не готовый централизованный сервер. Кроме того, функции Community и Pro следует сверять отдельно: README содержит как реализованные возможности, так и планы. ([GitHub][8])

**WhisperX** — полезная реализация связки распознавания, выравнивания временных меток и диаризации. Однако выравнивание требует языковых моделей, которые могут загружаться отдельно; нельзя автоматически предполагать готовую поддержку казахского на каждом этапе. ([GitHub][6])

**Мой выбор:** использовать эти проекты как проверяемые реализации отдельных решений, но корпоративный процесс согласования, хранение, права доступа и изоляцию проектировать самостоятельно.

## 3. Рекомендуемая архитектура

Для старта не нужны десятки микросервисов. Достаточно **одного модульного приложения и нескольких изолированных обработчиков**.

```text
Пользователь: корпоративная сеть / VPN
                    |
          HTTPS + корпоративный вход
                    |
             Веб-интерфейс / API
                    |
       +------------+-------------+
       |                          |
 PostgreSQL                Хранилище файлов
 метаданные, права,         оригиналы, результаты,
 версии, задания           временные артефакты
       |
 Устойчивая очередь заданий
       |
 Подготовка аудио
       |
 ASR + диаризация
       |
 Транскрипт с временными метками
       |
 Локальная LLM:
 поручения, решения, саммари
       |
 Проверки структуры и источников
       |
 Редактирование и утверждение человеком
       |
 DOCX / PDF / реестр поручений
       |
 Очередь разрешённых внешних событий
       |
 Отдельный шлюз интеграций
       |
 Согласованные мессенджеры / календари
```

### Приём записи

Предлагаю принимать файл через API потоково, с ограничениями размера и длительности, не загружая его целиком в оперативную память приложения.

До обработки файл получает идентификатор и контрольную сумму, проходит проверку формата и помещается в карантин. Декодирование — отдельный процесс без сетевого доступа, с лимитами CPU, памяти и времени. В первой версии лучше принимать файлы, а не произвольные URL для скачивания.

В базу записываются владелец, права доступа, дата и часовой пояс совещания, участники, состояние задания. В очередь отправляется идентификатор задания, **не аудио и не весь транскрипт**.

### Фоновая обработка

Рекомендуемый стек — **FastAPI + PostgreSQL + RabbitMQ + Celery**.

Тяжёлое распознавание не стоит выполнять внутри HTTP-запроса или обычного `BackgroundTasks`: сама документация FastAPI предлагает для тяжёлых распределённых вычислений отдельные инструменты вроде Celery. ([FastAPI][9])

Я бы разделил очереди по типу нагрузки: подготовка файлов, распознавание, диаризация, языковая модель, экспорт. Это позволит длинной генерации саммари не блокировать приём новых записей.

### Сборка транскрипта

Рекомендую хранить реплику как структуру, а не только как строку текста:

```text
segment_id
start_ms / end_ms
speaker_id
text
language_hint
pipeline_version
review_status
```

Все этапы должны использовать общую временную шкалу оригинала. При удалении тишины нужно сохранять соответствие исходным меткам.

Для длинных записей отдельно проверить склейку частей: `SPEAKER_00` в первом фрагменте не должен автоматически считаться тем же человеком, что `SPEAKER_00` во втором.

Исправления пользователя лучше хранить отдельной версией. Повторный запуск новой модели не должен незаметно затереть утверждённый текст.

### Извлечение поручений

Я бы не начинал с запроса «сделай красивый протокол всего совещания». Предлагаю двухэтапную обработку:

**Сначала — факты.** Из реплик извлекаются кандидаты в решения и поручения с указанием источников.

**Затем — документ.** Поручения объединяются, проверяются изменения сроков и отменённые решения, после чего формируются саммари и протокол.

Минимальная структура поручения:

```text
action_text
assignee_id | null
assignee_mention | null
deadline_iso | null
deadline_quote | null
source_segment_ids
review_status
```

Ключевые правила проекта:

**Не назван ответственный — оставляем `null`. Не определён срок — оставляем `null`. Говорящий не становится исполнителем автоматически.** Относительные даты рассчитываются относительно даты совещания, а неоднозначность показывается редактору.

Структурированный вывод vLLM помогает соблюдать JSON-схему, но правильная схема сама по себе не доказывает правильность содержания. Поэтому проверка источников и утверждение человеком остаются отдельными этапами. ([vLLM][10])

### Готовый протокол

Предлагаю формировать DOCX из утверждённых данных по корпоративному шаблону, например через `python-docx`, а PDF получать локальным LibreOffice в режиме без интерфейса. Обе операции документированы и не требуют облачного редактора. ([python-docx][11])

В комплект поставки должны входить шаблоны и шрифты с казахскими символами. Утверждённый протокол — отдельная неизменяемая версия с автором утверждения и ссылкой на использованную версию транскрипта.

## 4. Хранение и надёжность фоновых заданий

### Что где хранить

| Данные                                                                       | Предлагаемое размещение                                                      |
| ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Оригинальные записи, производные аудиофайлы, экспорты                        | Файловое или объектное хранилище                                             |
| Пользователи, права, встречи, задания, поручения, версии, журнал утверждения | PostgreSQL                                                                   |
| Временные файлы обработки                                                    | Локальный NVMe обработчика, с квотами и очисткой                             |
| Веса моделей и связанные файлы                                               | Версионированный внутренний каталог, доступный обработчикам только на чтение |
| Резервные копии                                                              | Отдельное хранилище в разрешённом контуре, не тот же рабочий диск            |

Для одноузлового пилота допустим обычный постоянный том, скрытый за интерфейсом хранения. Для корпоративной эксплуатации предпочтительно существующее внутреннее S3-совместимое хранилище. Например, Ceph Object Gateway предоставляет S3-совместимый интерфейс — это не означает использование облака Amazon. ([Ceph Documentation][12])

Рекомендую сразу определить разные сроки хранения для оригиналов, промежуточных файлов, транскриптов и утверждённых протоколов. Удаление встречи должно учитывать также временные фрагменты, поисковые копии, журналы и политику резервного хранения.

### Как не терять задания

**Источником состояния должна быть PostgreSQL, а не память процесса и не только очередь.**

Проектировать обработку следует так, чтобы повторный запуск этапа был безопасен. В Celery позднее подтверждение `acks_late` не решает все случаи аварийного завершения: документация отдельно описывает поведение при потере процесса и параметр `task_reject_on_worker_lost`. ([Celery Documentation][13])

Для проекта предлагаю:

* идентификатор этапа из записи, версии конвейера и названия операции;
* сохранение промежуточного результата перед отметкой об успешном завершении;
* ограниченное число повторов, тайм-ауты и отдельную очередь окончательно неуспешных заданий.

Запись состояния и событие для дальнейшей обработки лучше создавать через **транзакционный outbox**: в одной транзакции фиксируются изменение в базе и запись о том, что необходимо отправить в очередь. Это устраняет промежуток «данные сохранили, событие потеряли».

Для внешних интеграций нужен стабильный идентификатор операции и сверка результата после неоднозначного ответа API. **Гарантировать “ровно один раз” для всех внешних сервисов заранее нельзя.**

Для PostgreSQL предусмотрены резервные копии с архивированием WAL и восстановлением на момент времени. Репликацию я бы использовал для доступности, а независимую копию — для восстановления после удаления или повреждения данных. ([PostgreSQL][14])

## 5. Сегментация, VPN и контролируемые интеграции

### Предлагаемые сетевые зоны

| Зона                               | Разрешённые связи                                             | Что исключить                                                        |
| ---------------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------- |
| **Пользовательский доступ**        | HTTPS к приложению через корпоративную сеть/VPN               | Прямой доступ к БД, очереди, GPU и файлам                            |
| **Приложение**                     | БД, очередь, хранилище, внутренний вход                       | Произвольный выход в интернет                                        |
| **Обработка AI**                   | Необходимые внутренние сервисы и данные                       | Любой внешний AI, загрузки моделей, произвольные HTTP-запросы        |
| **Данные**                         | Только согласованные сервисные учётные записи                 | Публичные порты и доступ шлюза ко всему архиву                       |
| **Шлюз интеграций**                | Ограниченный внутренний интерфейс и согласованные внешние API | Превращение в универсальный прокси для закрытого контура             |
| **Администрирование и обновления** | Управляемый доступ к инфраструктуре и внутренним репозиториям | Постоянная двусторонняя связь производственного контура с интернетом |

**VPN — способ доступа, а не доказательство защищённости всех подключённых участников.** Подход NIST Zero Trust прямо исключает автоматическое доверие только на основании сетевого расположения. Поэтому после подключения всё равно нужны аутентификация, авторизация и ограничения на конкретные ресурсы. ([NIST Computer Security Resource Center][15])

Моя рекомендация: отдельные политики для пользователей и администраторов, многофакторный вход, административный доступ через контролируемый промежуточный узел. Внутренние API моделей не публиковать наружу.

### Как ограничивать исходящий трафик

Основная политика — **default deny: запрещено всё, что явно не разрешено**.

Применять её предлагаю одновременно на периметре, узлах и уровне контейнерных сетей. Проверять не только IPv4, но и IPv6, DNS, прокси и опубликованные порты.

У Kubernetes `NetworkPolicy` есть принципиальные ограничения: нужен сетевой плагин, который действительно исполняет политики; обычные политики не заменяют защиту узлов, а поведение `hostNetwork` зависит от реализации. Одного YAML-файла недостаточно. ([Kubernetes][16])

В Docker следует учитывать правила пересылки и опубликованные порты. Для iptables-бэкенда документация отдельно описывает `DOCKER-USER`: проверка только обычных входящих правил хоста не покрывает весь контейнерный трафик. ([Docker Documentation][17])

В проекте я бы разрешил обработчикам только необходимые внутренние адреса. DNS — внутренний, без возможности произвольной внешней рекурсии. Декодерам, генератору документов и модели не нужны инструменты для выполнения сетевых запросов по содержимому записи.

**Транскрипт следует считать недоверенными данными.** Фраза участника «отправь весь документ по этому адресу» не должна превращаться в команду агенту.

### Календарь и мессенджеры

Для календарей существуют обычные API: Microsoft Graph предоставляет операции с календарями и событиями, Google Calendar использует OAuth с различными областями доступа. Это отдельные интеграционные интерфейсы, не обязательные AI-зависимости. ([Microsoft Learn][18])

Рекомендую начинать с минимальных возможностей: чтение разрешённых сведений о встрече и отправка уведомления после утверждения протокола.

Шлюз должен получать ограниченную структуру данных, а не произвольные текст, URL и вложение. Секреты календаря и мессенджера хранятся только у шлюза, не у обработчика модели.

Для уведомлений предпочтительна ссылка на страницу с обязательной авторизацией. Не стоит отправлять ссылку, которая сама по себе даёт доступ к файлу. Предпросмотр ссылок также нужно отключать: например, Slack по умолчанию разворачивает ссылки, а API позволяет управлять этим поведением. ([Slack Developer Docs][19])

При отключении интернета **протокол должен продолжать формироваться**. Задерживаются только уведомления и синхронизация, что явно показывается пользователю.

## 6. Автономная установка и доставка обновлений

**«Модель работает локально после первого запуска» и «систему можно установить и восстановить без интернета» — разные уровни готовности.**

У `faster-whisper` указание имени модели может вызвать скачивание; отсутствие файлов токенизатора также создаёт скрытую зависимость. Hugging Face даже при наличии кеша может выполнять HTTP-проверки, если не включён офлайновый режим. ([GitHub][1])

### Как я предлагаю поставлять обновления

```text
Отдельная зона загрузки, без корпоративных записей
    ->
Фиксация версий и проверка компонентов
    ->
Подписанный комплект поставки
    ->
Проверка и согласование переноса
    ->
Внутренние репозитории образов, пакетов и моделей
    ->
Испытательный закрытый стенд
    ->
Производственный контур
```

В комплект должны входить не только контейнеры и веса. Я бы включал зависимости Python и ОС, токенизаторы, конфигурации, вспомогательные модели, библиотеки обработки медиа, шрифты, шаблоны, миграции БД и инструкции восстановления.

Для GPU необходима согласованная поставка драйвера, контейнерного инструментария и библиотек. NVIDIA документирует установку Container Toolkit и настройку среды контейнеров; эти зависимости тоже нужно доставлять автономно. ([NVIDIA Docs][20])

Внутренний реестр контейнеров можно организовать, например, на Harbor: у него есть офлайновый установщик с включёнными образами. Подписи артефактов можно проверять локальными доверенными ключами; при этом нельзя оставлять скрытую зависимость проверки от загрузки ключа или другого материала из интернета. ([Harbor][21])

Для каждого выпуска рекомендую хранить перечень компонентов и лицензий, контрольные суммы, подписи, результаты проверки уязвимостей и контрольного корпуса. Версии фиксировать, не использовать `latest`. Предыдущий работоспособный выпуск сохранять вместе с планом отката схемы и данных.

### Настройки автономного исполнения

Для используемых компонентов нужно включить предусмотренные ими режимы, например:

```text
HF_HUB_OFFLINE=1
HF_HUB_DISABLE_TELEMETRY=1
PYANNOTE_METRICS_ENABLED=0
VLLM_NO_USAGE_STATS=1
```

Эти настройки документированы Hugging Face, pyannote и vLLM. У `hf` CLI также есть отдельное отключение проверки обновлений. Но **переменные окружения — дополнительная мера, а не замена сетевому запрету**. ([Hugging Face][22])

Модели следует загружать по локальным путям, с `local_files_only=True` там, где это поддерживается. Отсутствующий компонент должен приводить к понятной ошибке, а не к скачиванию или переходу на облачного провайдера. ([Hugging Face][23])

Отдельный нюанс: у современного Ollama есть облачные функции. При его выборе необходимо явно отключить их, например через `OLLAMA_NO_CLOUD=1`, и проверить фактическое сетевое поведение. ([Ollama][24])

В автономный тест нужно включить также вход пользователей, DNS, время, сертификаты, мониторинг, резервное копирование и ресурсы веб-интерфейса. Иначе AI будет локальным, а приложение остановится из-за недоступного внешнего входа или скрипта интерфейса.

## 7. Пилот и более строгий корпоративный вариант

Ниже — **мои стартовые инженерные оценки**, не минимальные требования производителей и не обещание определённой скорости. Исходное допущение: обработка загруженных записей через очередь, а не обязательная работа в реальном времени.

### Предлагаемый состав

| Компонент                          | Реалистичный пилот                                                                                                 | Корпоративный вариант с повышенной доступностью                                                |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| **Развёртывание**                  | Linux, Docker Compose, один основной сервер                                                                        | Разделённые узлы/ВМ; Kubernetes только при наличии команды эксплуатации                        |
| **Основной вычислительный сервер** | Около 16 современных физических ядер CPU; 64 ГБ RAM как нижняя ориентировочная граница, **128 ГБ предпочтительно** | Два GPU-узла: ориентировочно по 24–32 ядра CPU и 128 ГБ RAM                                    |
| **GPU**                            | Одна NVIDIA с **24–32 ГБ VRAM**                                                                                    | Две GPU с **48 ГБ VRAM**, на разных узлах                                                      |
| **Режим AI-обработки**             | Один GPU-слот, последовательное выполнение тяжёлых этапов                                                          | Отдельные ресурсы для ASR/диаризации и LLM; возможность перераспределения                      |
| **Приложение**                     | Контейнеры на основном сервере                                                                                     | Две ВМ, ориентировочно по 8 vCPU и 16–32 ГБ RAM                                                |
| **PostgreSQL и очередь**           | По одному экземпляру, с резервным копированием                                                                     | Управляемая HA-конфигурация PostgreSQL; RabbitMQ на трёх узлах при использовании quorum queues |
| **Диск обработчика**               | **2 ТБ NVMe**, с контролем свободного места                                                                        | Около 2 ТБ локального NVMe на GPU-узел для моделей и временных файлов                          |
| **Постоянные файлы**               | Постоянный том + отдельное резервное хранилище                                                                     | Корпоративное объектное хранилище; ёмкость рассчитывается по срокам хранения                   |
| **Интеграции**                     | Отдельная небольшая ВМ: 2–4 vCPU, 4–8 ГБ RAM                                                                       | Изолированный шлюз, при необходимости два экземпляра                                           |

Для RabbitMQ три участника — практический минимум quorum-конфигурации, позволяющий пережить потерю одного. Два экземпляра не дают эквивалентной устойчивости к потере узла. ([RabbitMQ][25])

Это **логические роли**, а не требование купить отдельный физический сервер для каждой. Корпоративные БД, хранилище, вход пользователей, резервное копирование и мониторинг лучше использовать существующие.

При этом **строгая конфиденциальность и высокая доступность — разные требования**. Можно построить хорошо изолированный одноузловой контур. И можно построить большой кластер, который ошибочно отправляет данные наружу.

### Почему нельзя просто сложить «веса моделей»

Расчётная нижняя оценка только для параметров:

* 14 млрд параметров × 2 байта ≈ **28 ГБ**;
* 32 млрд × 2 байта ≈ **64 ГБ**;
* при четырёхбитном представлении арифметический минимум — примерно 7 и 16 ГБ соответственно.

Это не фактическая потребность в VRAM: добавляются служебные данные квантования, рабочая память и кеш контекста. vLLM отдельно управляет бюджетом GPU-памяти и длиной контекста. ([vLLM][26])

Поэтому на одной GPU пилота я предлагаю **поочерёдно выполнять ASR, диаризацию и LLM**, а не запускать несколько серверов с настройками памяти по умолчанию.

CPU-only вариант технически реален: `faster-whisper` поддерживает CPU с INT8, а `llama.cpp` — локальное выполнение языковых моделей на CPU. Но скорость всего конвейера нужно измерять; такой режим я бы рассматривал для демонстрации, небольшой нагрузки или ночной обработки. ([GitHub][1])

### Как рассчитать пропускную способность

Для одного последовательного конвейера предлагаю измерять:

```text
RTF = машинное время обработки / длительность записи

Примерная ёмкость =
доступные часы работы × полезная загрузка / RTF
```

**Условный пример, не результат теста:** если измеренный RTF равен 0,25, доступны 8 часов, полезная загрузка составляет 65%, получится около **21 часа записей за рабочий день**.

У разнесённых обработчиков нужно считать узкое место каждого этапа. Среднего числа часов в день недостаточно: необходимо измерять очереди после массового завершения совещаний и время обработки в 95-м процентиле.

### Диск: аудио и видео дают разный порядок затрат

Расчёт для одного часа, в десятичных единицах:

| Представление                        | Приблизительный объём |
| ------------------------------------ | --------------------: |
| Сжатое аудио 64 кбит/с               |               28,8 МБ |
| PCM, 16 кГц, 16 бит, моно            |              115,2 МБ |
| PCM, 48 кГц, 16 бит, стерео          |              691,2 МБ |
| Видео с суммарным битрейтом 2 Мбит/с |                0,9 ГБ |

При **100 часах записей в день и хранении 90 дней** получаются примерно:

**0,26 ТБ** сжатого аудио, **1,04 ТБ** производного моно-PCM или **8,1 ТБ** видео — до реплик и резервных копий.

Формула планирования:

```text
поток записей × срок хранения × объём часа
+ производные файлы
+ модели
+ временное пространство
+ БД и журналы
+ запас свободного места
```

Резервные копии считать отдельно. Исходное видео не следует хранить бессрочно просто потому, что оно было загружено: это должно быть осознанным требованием.

## 8. Какие проверки докажут автономность и работоспособность

**Главная проверка — не “запретили один AI-домен”. Нужны холодный запуск без внешней сети и наблюдение за всем сетевым трафиком.**

Предлагаю такую программу приёмки.

| Проверка                                           | Что должно быть доказано                                                                                                                                        |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Установка на чистом изолированном стенде**    | Только из комплекта поставки устанавливаются приложение, модели и зависимости. Нет скачиваний из пакетных репозиториев, Hugging Face или CDN                    |
| **2. Полный цикл на новой записи без интернета**   | Вход → загрузка → реальная транскрипция → диаризация → поручения → утверждение → DOCX/PDF. Проверяется не заранее подготовленный пример и не кеш                |
| **3. Контроль исходящего трафика**                 | На уровне узлов, контейнеров, DNS, IPv4/IPv6 и прокси нет успешных внешних соединений из закрытого контура. Неожиданные попытки выявлены и устранены            |
| **4. Отсутствующая модель или токенизатор**        | Понятная контролируемая ошибка. Нет скачивания, бесконечного ожидания и облачного резервного обработчика                                                        |
| **5. Падение на каждом этапе**                     | После остановки обработчика, перезагрузки и нехватки VRAM задание восстанавливается либо завершается понятной ошибкой. Нет потери записи и бесконечных повторов |
| **6. Недоступность календаря и мессенджера**       | Формирование протокола работает. Внешнее событие остаётся в очереди; восстановление связи не создаёт неконтролируемые дубликаты                                 |
| **7. Проверка прав доступа**                       | Другой пользователь или подразделение не может получить запись, транскрипт или экспорт подбором идентификатора. Шлюз не может прочитать весь архив              |
| **8. Проверка вредоносных входных данных**         | Повреждённый файл, внешний URL в метаданных и инструкции внутри транскрипта не дают сетевого доступа или выполнения произвольных команд                         |
| **9. Восстановление на другом изолированном узле** | Из резервной копии восстанавливаются БД, файлы, ключи, конфигурация и версии моделей. После восстановления проходит новый полный цикл                           |
| **10. Нагрузка и большие записи**                  | Измерены ожидание очереди, скорость этапов, пиковая RAM/VRAM и временный диск; многочасовая запись не обрывается незаметно                                      |
| **11. Обновление и откат без интернета**           | Новый выпуск устанавливается из подписанного комплекта, проходит проверки и при необходимости заменяется предыдущим                                             |
| **12. Побочные каналы и экспорт**                  | Нет содержимого записей во внешней аналитике, отчётах об ошибках и предпросмотрах; документы корректно отображают казахские символы и длинные таблицы           |

К результатам приёмки я бы приложил версии и контрольные суммы компонентов, правила межсетевого экрана, сетевые журналы, протокол восстановления и отчёт по контрольному корпусу.

### Качество проверяется отдельно от автономности

Рекомендую собрать стартовый закрытый корпус порядка **30–60 часов**, сбалансированный между русской, казахской и смешанной речью. Это предлагаемая величина для пилота, не отраслевой норматив.

Нужны разные помещения, устройства, число участников, перекрытия голосов, терминология, имена, суммы, переносы сроков и отменённые поручения. Разметку должны проверять люди, понимающие оба языка.

Оценивать следует четыре результата:

| Результат      | Что измерять                                                                                          |
| -------------- | ----------------------------------------------------------------------------------------------------- |
| **Транскрипт** | Ошибки слов/символов отдельно по языкам; точность имён, чисел, дат                                    |
| **Говорящие**  | Ошибки назначения реплик, пропуски и смешение участников                                              |
| **Поручения**  | Точность и полнота извлечения; правильность ответственного и срока; наличие подтверждающего источника |
| **Протокол**   | Фактические ошибки, пропущенные решения, время ручной правки                                          |

Как обсуждаемый стартовый критерий можно предложить **не менее 95% точности и 85% полноты извлечения явно сформулированных поручений**, отдельно на каждом языковом поднаборе. **Это целевые показатели для согласования, не подтверждённые характеристики перечисленных моделей.**

Для всех кандидатов в поручения рекомендую обязательную привязку к исходным репликам. Неопределённые поля должны оставаться неопределёнными. Перед созданием официальных задач и публикацией протокола — утверждение человеком.

## Итоговая рекомендация

**Строить пилот целесообразно. Внешний AI-доступ для него не нужен.**

Я бы выбрал **Linux + Docker Compose + FastAPI + PostgreSQL + RabbitMQ/Celery**, постоянное локальное хранилище с возможностью перехода на корпоративное S3, `faster-whisper`, `pyannote community-1` и локальную Qwen. Для первой проверки — одна GPU на 24–32 ГБ с последовательной очередью. Казахскую адаптацию ISSAI сравнить с базовой моделью на том же закрытом корпусе.

**В корпоративную эксплуатацию переходить после четырёх доказательств:** полный цикл проходит без интернета; система восстанавливается из автономной поставки и резервных копий; сеть действительно блокирует неразрешённые передачи; качество на русской, казахской и смешанной речи соответствует согласованным критериям.

Таким образом, фундаментальное ограничение решаемо. Сложность заключается не в отсутствии облачного AI, а в том, чтобы превратить набор локальных моделей в **воспроизводимую, контролируемую и восстанавливаемую систему**, которая не выдумывает ответственных и не теряет задания при сбоях.

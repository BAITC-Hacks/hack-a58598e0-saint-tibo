## Вывод

**Оба профиля реализуемы без постоянных AWS access keys и без собственной криптографии. Но я рекомендую два разных набора компонентов, а не обязательный Vault поверх AWS.**

**Закрытый контур:** локальный **Vault + Transit**, шифрование файлов проверенной библиотекой, PostgreSQL на зашифрованных дисках, независимые зашифрованные резервные копии.

**AWS-профиль:** **IAM roles / STS + KMS + Secrets Manager**, S3 и зашифрованный RDS. Для требования «скопированный файл без ключа не читается» — дополнительно **шифрование в приложении через AWS Encryption SDK**. Vault здесь нужен только при существующем корпоративном стандарте, а не для самого отказа от постоянных AWS-ключей. AWS прямо рекомендует временные полномочия ролей для приложений. ([AWS Documentation][1])

Главное архитектурное решение: **отделить хранение данных от права их расшифровывать**. Сервис хранения и оператор резервного копирования не должны автоматически получать доступ к содержимому совещаний.

Ниже — рекомендуемая схема и ограничения по первичной документации, проверенной **23 сентября 2026 года**.

## 1. Какие задачи решают разные компоненты

| Компонент                         | Его задача                                                                                 | Чего он сам по себе не обеспечивает                                                                 |
| --------------------------------- | ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| **Vault KV**                      | Хранение паролей, токенов интеграций и других секретов                                     | Отзыв уже скопированного пароля у внешней системы                                                   |
| **Vault Database secrets engine** | Выдача ограниченных по времени учётных данных БД, управление их жизненным циклом           | Автоматическую корректность всех настроек SQL-прав и завершение любых существующих соединений       |
| **Vault Transit**                 | Хранение криптографических ключей; операции шифрования, расшифрования, оборачивания ключей | Хранение аудиофайлов и проверку бизнес-права пользователя на конкретное совещание                   |
| **IAM role / STS**                | Временные полномочия приложения на обращения к AWS                                         | Шифрование содержимого файлов                                                                       |
| **AWS KMS**                       | Управление ключами шифрования и криптографическими операциями                              | Управление паролями сторонних интеграций                                                            |
| **AWS Secrets Manager**           | Хранение секретов и организация их ротации                                                 | Модель выдачи отдельной краткоживущей учётной записи БД каждому клиенту, аналогичную Vault Database |

Разделение функций следует из моделей Vault Transit, динамических секретов Vault, IAM и Secrets Manager. В частности, **Transit не сохраняет переданные ему данные**, а ротация секрета в Secrets Manager должна менять и сохранённое значение, и соответствующий секрет целевой системы. ([HashiCorp Developer][2])

### Два уровня шифрования, которые нельзя путать

**Шифрование диска или управляемого хранилища** защищает данные на носителе. Но после монтирования диска или авторизованного чтения через сервис приложение получает открытые данные. Например, PostgreSQL указывает, что шифрование файловой системы не защищает от доступа к уже смонтированному тому. ([PostgreSQL][3])

**Шифрование содержимого в приложении** означает, что в файловом хранилище или столбце БД лежит уже зашифрованный объект. Для чтения нужны отдельно доступ к объекту и разрешение на расшифрование ключа.

Это принципиально для AWS: **S3 SSE-KMS возвращает авторизованному клиенту расшифрованный объект**. Поэтому скачанный через обычный `GetObject` PDF при одном только SSE-KMS не обязан оставаться зашифрованным. Для такого свойства нужен дополнительный клиентский слой шифрования. ([AWS Documentation][4])

## 2. Общая схема: отдельный ключ данных на каждый файл

Для аудио, PDF/DOCX, крупных транскриптов и других самостоятельных объектов рекомендую **envelope encryption — конвертное шифрование**:

```text
Файл
  -> шифрование отдельным ключом данных DEK
  -> зашифрованный файл в хранилище

DEK
  -> шифрование ключом KEK из Vault Transit или AWS KMS
  -> зашифрованный DEK рядом с файлом

Чтение
  -> проверка права на конкретное совещание
  -> получение разрешения на расшифрование DEK
  -> расшифрование файла в памяти / потоком
```

**DEK** шифрует содержимое. **KEK** защищает DEK. В хранилище допустимо держать вместе зашифрованный файл, зашифрованный DEK, идентификатор ключа и версию формата: открытого ключа расшифрования там нет. Такая схема документирована HashiCorp и AWS. ([HashiCorp Developer][5])

Для проекта я бы закрепил следующие правила:

* **Новый DEK на каждую неизменяемую версию объекта.** Перегенерированный протокол — новая версия, а не перезапись содержимого с произвольным повторным использованием криптографических параметров.
* **Открытый DEK существует только в памяти на время операции.** Не хранить его в БД, `.env`, логах, временных файлах; в пилоте не вводить межзапросный кеш DEK.
* **Разделить ключи по назначению:** оригиналы, производные материалы, резервные копии. При необходимости — дополнительно по организациям или подразделениям.

Это предлагаемая политика, а не требование иметь отдельный мастер-ключ на каждый файл.

### Как не создать собственную криптографию

Для больших файлов нужна библиотека **аутентифицированного потокового шифрования**, которая сама управляет сегментами, проверками целостности и криптографическими параметрами. Например, Tink Streaming AEAD защищает сегменты и их положение внутри потока. Самостоятельно нарезать аудио и придумывать схему AES, nonce и тегов не следует. ([Google for Developers][6])

У HashiCorp есть официальный **Vault Envelope Encryption SDK** для больших файлов. Он использует Tink, однако в его документации прямо указано требование **Vault Enterprise**. Это нужно учитывать при оценке пилота. ([GitHub][7])

Без Enterprise возможна связка **Tink Streaming AEAD + небольшой адаптер к базовому Transit API**: библиотечный ключ или набор ключей оборачивается через Transit. Это не разработка собственного алгоритма, но **отдельная интеграционная работа, которую нужно проверить**, а не готовый универсальный коннектор.

Передавать многогигабайтное аудио целиком в Transit не нужно: у Vault по умолчанию ограничение HTTP-запроса **32 МБ**, а кодирование дополнительно увеличивает объём. Transit в этой схеме обрабатывает небольшие ключи, а файл шифруется локально. ([HashiCorp Developer][2])

Для привязки файла к контексту использовать аутентифицируемые метаданные: непрозрачные идентификаторы организации, объекта и версии. **Это не место для ФИО и текста совещания:** AAD и AWS encryption context не являются секретными. Ожидаемые идентификаторы нужно брать из доверенной записи приложения, а не слепо принимать из заголовка загруженного файла. ([Google for Developers][6])

## 3. Где находятся ключи и кто может читать оригиналы

### Размещение ключевого материала

| Материал                               | Закрытый контур                                                              | AWS-профиль                                                                       |
| -------------------------------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| **KEK для содержимого**                | Transit: защищённое хранилище Vault                                          | Customer-managed KMS key                                                          |
| **Зашифрованный DEK**                  | Рядом с зашифрованным объектом или в связанной записи БД                     | В формате зашифрованного объекта либо связанных метаданных                        |
| **Открытый DEK**                       | Только память сервиса шифрования на время операции                           | То же                                                                             |
| **Пароли и токены интеграций**         | Vault KV                                                                     | Secrets Manager                                                                   |
| **Полномочия приложения**              | Краткоживущий Vault service token; отдельная машинная идентичность для входа | Временные credentials IAM role                                                    |
| **Материал аварийного восстановления** | Независимо сохранённые доли unseal и ключи резервных копий                   | Независимый административный доступ, сохранность KMS-ключей и прав восстановления |

Для Transit рекомендую оставлять `exportable=false`, `allow_plaintext_backup=false`, `deletion_allowed=false`. Приложению нужны права на конкретные криптографические операции, а не экспорт или удаление ключа. ([HashiCorp Developer][8])

В AWS ключевой материал KMS защищён HSM и не выдаётся приложению в открытом виде; приложение работает с идентификатором ключа и разрешёнными API-операциями. В обычном Vault Transit модель другая: **подключение HSM для unseal не означает, что все операции Transit автоматически выполняются внутри HSM**. Это разные функции. ([AWS Documentation][9])

### Предлагаемая матрица доступа

| Участник                                                      | Доступ к оригинальному аудио                                                          |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Пользователь с отдельным правом `original:read`               | Через API после проверки доступа к совещанию                                          |
| Пользователь, которому доступен только протокол или поручение | **Нет**                                                                               |
| Сервис приёма записи                                          | Принимает текущую загрузку; не получает право читать весь архив                       |
| Сервис выдачи оригиналов                                      | Может расшифровывать оригиналы, но обязан проверять разрешение на каждый запрос       |
| Воркер распознавания                                          | Получает поток только для назначенного задания; без общего права расшифровывать архив |
| Сервис саммари и экспорта                                     | Получает необходимый транскрипт; без доступа к аудио                                  |
| Сервис уведомлений                                            | Только необходимые поля поручения                                                     |
| Оператор хранилища / копирования файлов                       | Зашифрованные объекты, без ключей содержимого                                         |
| Администратор ключей                                          | Управление жизненным циклом; без штатного права читать совещания                      |
| Аварийная роль восстановления                                 | Временный согласованный доступ для восстановления и проверки                          |

**Vault и KMS не знают, кто секретарь конкретного совещания.** Это проверяет приложение. Поэтому сервис выдачи оригиналов — доверенный компонент, а его компрометация остаётся серьёзным риском.

Разделение администраторов имеет смысл только при разделении возможностей: оператор, который одновременно может изменить приложение, прочитать его память и переписать политики ключей, способен обойти формальную матрицу. Я бы отдельно ограничил изменение политик, аварийное расшифрование и отключение аудита.

## 4. Профиль А: полностью закрытый контур

### Минимальная архитектура пилота

Мой вариант без избыточной инфраструктуры:

| Узел                                    | Состав                                                                    |
| --------------------------------------- | ------------------------------------------------------------------------- |
| **Приложение**                          | API, сервис шифрования, обработчики заданий, локальные модели             |
| **Данные**                              | PostgreSQL, файловое или объектное хранилище, зашифрованные рабочие диски |
| **Vault**                               | Отдельная машина: auth, KV, Database engine, Transit, integrated storage  |
| **Независимая площадка резервирования** | Зашифрованные копии БД, объектов, состояния Vault и конфигурации          |

Это **предлагаемая компоновка**, не минимальные требования производителя. Один Vault допустим в пилоте с осознанно принятой недоступностью при его отказе. Для отказоустойчивого варианта — кластер, например три узла integrated storage/Raft. ([HashiCorp Developer][10])

Vault запускать в штатном режиме, не `dev`; использовать TLS, отдельного непривилегированного пользователя ОС, исключить постоянный root token у приложений. Для узла Vault HashiCorp рекомендует отключить swap. ([HashiCorp Developer][11])

### Как приложение получает полномочия

Предпочтительный вариант при наличии корпоративной PKI — **Vault cert auth**: сервис предъявляет машинный сертификат и получает ограниченный токен. Закрытый ключ сертификата нужно защищать отдельно; он является исходной машинной идентичностью, а не исчезает благодаря краткому TTL токена. ([HashiCorp Developer][12])

Альтернатива для небольшого развёртывания — **AppRole**. Короткоживущий одноразовый SecretID передаёт доверенная система развёртывания через response wrapping. Нельзя превращать AppRole в бессрочный SecretID, зашитый в образ. Также нужно заранее решить повторный запуск после полного отключения: кто и как выдаст новый SecretID. ([HashiCorp Developer][13])

Для пилота я бы использовал **service tokens**, например с TTL 10 минут, ограниченным максимальным сроком и повторной аутентификацией. Значения — проектная настройка. Batch tokens не подходят там, где требуется индивидуальный ручной отзыв: их модель отзыва отличается. ([HashiCorp Developer][14])

### База данных и секреты

Vault Database выдаёт приложению ограниченную учётную запись PostgreSQL. Сам Vault использует отдельного управляющего пользователя с необходимыми правами, а не передаёт его пароль приложению. Сроки аренды, SQL создания и отзыва, права и обновление соединений нужно настроить совместно. ([HashiCorp Developer][15])

**Не считать TTL достаточным доказательством отзыва:** проверить фактическое поведение PostgreSQL, существующих соединений и пула приложения. Vault поддерживает настраиваемые операции отзыва; результат зависит от этой интеграции. ([HashiCorp Developer][16])

### Как открыть Vault после перезапуска

Для небольшого полностью локального пилота я бы выбрал **Shamir unseal**, например схему «2 из 3» с независимыми хранителями долей. Это ручная операция после холодного старта, зато не появляется скрытая зависимость от AWS.

Локальный HSM с auto-unseal — отдельный более сложный вариант. Важное ограничение: **recovery shares при auto-unseal не заменяют потерянный ключ KMS/HSM**. Если он уничтожен, резервная копия Vault сама по себе не спасёт. ([developer.hashicorp.com][17])

Полная автономность также требует локальных IdP/CA, DNS, времени, пакетов, моделей и журналирования. Проверять её нужно холодным запуском и восстановлением без внешней сети, а не только обработкой записи на уже работающем сервере.

## 5. Профиль Б: AWS без постоянных access keys

### Минимальный набор

| Задача                          | Компонент                                                                        |
| ------------------------------- | -------------------------------------------------------------------------------- |
| Идентичность приложения         | EC2 instance profile, ECS task role либо идентичность workload в EKS             |
| Ключи содержимого               | Customer-managed AWS KMS keys                                                    |
| Шифрование файлов до сохранения | AWS Encryption SDK                                                               |
| Объекты                         | S3 с SSE-KMS как дополнительным уровнем                                          |
| База                            | RDS PostgreSQL с шифрованием                                                     |
| Секреты интеграций              | Secrets Manager                                                                  |
| Резервирование                  | Снимки/копии с проверенными KMS-зависимостями, отдельный административный доступ |

Для ECS нужна именно **task role приложения**, не только execution role, используемая инфраструктурой запуска контейнера. SDK получает временные полномочия роли; постоянные IAM user keys в конфигурации не требуются. ([AWS Documentation][18])

Временный набор тоже содержит `AccessKeyId`, `SecretAccessKey` и `SessionToken`. Запрет должен касаться **постоянных пользовательских ключей**, а не названия поля. Для сервера вне AWS в этом профиле подходит **IAM Roles Anywhere** с X.509; его закрытый ключ сертификата по-прежнему требует защиты, в том числе через поддерживаемые TPM/PKCS#11-механизмы. ([AWS Documentation][19])

### Что хранить в Secrets Manager

Пароли и токены интеграций, которые нельзя заменить федерацией. **Не хранить там постоянный AWS access key как обход ограничения.**

Ротация Secrets Manager меняет секрет и значение в целевом сервисе. Приложению нужно обновлять кеш и соединения; ротация пароля не делает уже установленную сессию автоматически недействительной. ([AWS Documentation][20])

Для поддерживаемой конфигурации RDS PostgreSQL можно использовать IAM-аутентификацию вместо пароля. Но её токен действует **15 минут для установления соединения**: истечение токена не завершает открытую сессию БД. ([AWS Documentation][21])

### Как шифровать

Для строгого варианта — **AWS Encryption SDK до загрузки в S3**, а SSE-KMS оставить дополнительной защитой хранилища. SDK решает управление ключами данных и формат шифротекста; нужно явно ограничить допустимые KMS-ключи и проверять контекст расшифрования. ([AWS Documentation][22])

Я бы разделил KMS-ключи для серверного шифрования S3 и прикладного шифрования оригиналов. Это упрощает политики и не смешивает обращения S3 с прямыми запросами приложения в KMS.

RDS encryption покрывает данные хранилища, журналы, автоматические резервные копии и снимки, но не запрещает авторизованные SQL-запросы. Более того, отзыв KMS-прав у пользователя, создавшего RDS, **не отключает работающую БД**: сервис использует выданный grant. Пользовательские права отзываются в приложении и БД, не таким способом. ([AWS Documentation][23])

Сервисы можно разместить в приватных подсетях с VPC endpoints для KMS и Secrets Manager. Это исключает необходимость публичного интернет-маршрута к этим сервисам, но **не делает AWS-профиль независимым от AWS**. ([AWS Documentation][24])

**Vault поверх AWS для пилота не рекомендую.** При существующем корпоративном Vault его AWS engine следует использовать с `assumed_role` и собственной IAM role, а не создавать приложению IAM users с постоянными ключами. ([HashiCorp Developer][25])

## 6. Защищать нужно все копии, а не только аудио

| Данные                                                 | Предлагаемая защита                                                      |
| ------------------------------------------------------ | ------------------------------------------------------------------------ |
| Аудио, PDF/DOCX, крупные транскрипты                   | Шифрование содержимого до постоянного сохранения                         |
| Текст поручений и другие чувствительные поля БД        | При требовании защиты от DBA — шифрование в приложении                   |
| PostgreSQL: данные, WAL, временные таблицы             | Зашифрованные тома во всех местах размещения либо RDS encryption         |
| Промежуточные WAV, фрагменты речи, офисная конвертация | Память либо отдельное зашифрованное временное хранилище                  |
| Очереди и повторные задания                            | Преимущественно идентификаторы объектов, без полного текста              |
| Логи, трассировки, отчёты об ошибках                   | Без содержимого совещаний, DEK и секретов                                |
| Резервные копии                                        | Отдельное шифрование репозитория плюс сохранение прикладного шифротекста |

Шифрование чувствительных полей **до SQL** нужно именно для защиты от доступа через БД или логический дамп. `pgcrypto`, которому сервер получает ключ и открытый текст, не эквивалентно защите от администратора этого сервера. PostgreSQL прямо разграничивает эти модели. ([PostgreSQL][3])

Цена такого решения — ограничения обычного поиска и аналитики по зашифрованным полям. Для пилота я бы оставил открытыми только согласованные служебные атрибуты: идентификаторы, статус, технические даты. Не стоит одновременно изобретать собственное «поисковое шифрование».

Временные файлы требуют отдельного испытания после сбоя: учитывать буферизацию загрузок, конвертацию, аварийные дампы, swap и забытые каталоги обработки. Очистка по завершении плюс уборка по сроку жизни — обязательная проектная мера.

Для аудита фиксировать пользователя, сервис, объект, действие и решение о доступе, но не текст. В Vault полезны два независимых назначения аудита: если все настроенные устройства аудита недоступны, Vault перестаёт обслуживать запросы. В AWS отдельно включить **S3 data events** для обращений к объектам: по умолчанию они не журналируются. ([HashiCorp Developer][26])

## 7. Ротация, отзыв и восстановление — три разные процедуры

### Плановая ротация ключа

Нормальный сценарий: KEK версии 1 остаётся доступен для старых данных, новые записи используют версию 2. В Vault `rewrap` позволяет переобернуть зашифрованный DEK новой версией без выдачи открытого DEK процессу миграции. **Большой файл при этом переписывать не обязательно**, если используемый формат позволяет заменить обёртку ключа. Вручную менять заголовки произвольного SDK нельзя. ([HashiCorp Developer][2])

Не повышать `min_decryption_version` и не удалять старые версии, пока от них зависят действующие объекты или резервные копии. ([HashiCorp Developer][8])

В KMS автоматическая ротация сохраняет логический ключ и возможность расшифрования старым материалом. Но она **не меняет DEK и не перешифровывает файлы**. Переключение alias на совершенно новый KMS key тоже не мигрирует старые данные автоматически. ([AWS Documentation][27])

**Компрометация DEK — другой случай:** потребуется новый DEK и перешифрование содержимого. Плановая ротация KEK этого не исправляет. ([AWS Documentation][27])

### Отзыв доступа

| Что отзываем                       | Что необходимо сделать                                                                                    |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Право пользователя на совещание    | Проверять актуальные права при выдаче; прекращать разрешённые ранее длительные операции согласно политике |
| Vault-токен сервиса                | Отозвать service token **и запретить получение нового** скомпрометированной машинной идентичностью        |
| Учётные данные БД                  | Выполнить отзыв, отдельно проверить активные соединения и пул                                             |
| AWS-сессию                         | Отозвать разрешения существующей сессии и закрыть возможность получить следующую                          |
| Уже выданный открытый файл или DEK | Надёжно «забрать обратно» невозможно                                                                      |

Vault service tokens поддерживают отзыв. Но отзыв одного токена недостаточен, если сервис может немедленно пройти аутентификацию заново. ([HashiCorp Developer][14])

В AWS для ранее выданных сессий предусмотрен механизм `AWSRevokeOlderSessions` с условием по `aws:TokenIssueTime`. Он **не запрещает последующие новые сессии**, поэтому необходимо отдельно блокировать их выдачу. Изменения политик распространяются не мгновенно; фактическую задержку следует измерять. ([AWS Documentation][28])

Для пилота я бы установил проверяемую цель: **новая выдача оригинала через API прекращается не позднее 60 секунд после отзыва права**. Это проектный критерий, не гарантия AWS или Vault. Он требует проверки прав в приложении и отсутствия длительного кеширования разрешений.

### Восстановление

**Резервная копия считается пригодной только вместе с независимым способом получить все необходимые ключи.**

Для закрытого профиля сохранять согласованный набор:

```text
БД и WAL
+ зашифрованные объекты и их метаданные
+ snapshot Vault со всеми используемыми версиями ключей
+ конфигурация и версии форматов/библиотек
+ независимые материалы открытия Vault и backup-репозитория
```

Vault поддерживает создание и восстановление Raft snapshots. При проверке нужно дождаться фактического завершения восстановления и успешных операций: принятие команды restore ещё не доказывает готовность системы. ([HashiCorp Developer][29])

Для PostgreSQL подойдёт **pgBackRest** с шифрованием репозитория и восстановлением через WAL. Для файлов, готовых согласованных дампов и snapshots Vault — **restic**. Не заменять согласованный backup PostgreSQL копированием его работающего каталога произвольным файловым инструментом. ([pgBackRest][30])

Три особенно опасные ошибки:

**Единственный пароль backup хранится внутри того Vault, который этим backup нужно восстановить.** Нужна независимая защищённая аварийная копия.

**Backup данных новее backup ключей.** После ротации новые записи могут зависеть от версии KEK, которой нет в сохранённом состоянии Vault. Для пилота разумно приостановить запись на ротацию, сохранить состояние с новым ключом и только затем разрешить новые данные.

**Восстановили старые разрешения вместе с данными.** Перед открытием системы нужно применить актуальные блокировки, политики и новые сервисные credentials, а не вернуть в строй ранее отозванный доступ.

В AWS сгенерированный KMS-материал нельзя просто экспортировать как локальную резервную копию. Восстановление зависит от сохранности доступного KMS key; окончательное удаление ключа делает зависимый шифротекст невосстановимым. ([AWS Documentation][9])

Кроме того, **AWS Backup не всегда даёт независимый ключ восстановления**: для S3 поддерживается шифрование ключом backup vault, а RDS snapshots наследуют ключ исходной БД. Нужно проверять конкретную recovery point и её ключи. Дополнительное шифрование backup также не заменяет ключ прикладного шифрования внутри него. ([AWS Documentation][31])

## 8. Испытания, которыми принимать решение

Ниже **план приёмки, не результаты проведённых испытаний**.

| Испытание                                       | Как проводить                                                                                                                                                                       | Критерий успеха                                                                                                                               |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Файл без ключа не читается**               | Скопировать именно прикладной шифротекст и зашифрованный DEK на чистую машину без credentials, сети к ключевому сервису и кеша. Проверить аудио, PDF/DOCX и транскрипт              | Штатная библиотека не расшифровывает объект. С разрешённой ролью результат побайтно совпадает с контрольным оригиналом                        |
| **2. Старые данные доступны после ротации**     | Создать файлы и backup на версии 1; выполнить ротацию; создать файлы на версии 2. Открыть старые, новые и восстановленные из старого backup данные                                  | Все разрешённые объекты доступны. Для поддерживаемого rewrap меняется обёртка ключа без повреждения содержимого                               |
| **3. Отозванное право перестаёт работать**      | Начать с действующей пользовательской сессией, Vault-токеном или AWS STS credentials. Отозвать доступ и продолжать запросы **теми же credentials**, затем попытаться получить новые | Выдача прекращается в установленный срок; повторная аутентификация не обходит блокировку. Отдельно проверены активные соединения БД и задания |
| **4. Зашифрованный backup восстанавливается**   | Развернуть чистую среду без доступа к исходным серверам и их кешам. Использовать backup и независимые аварийные материалы                                                           | Восстановлены БД, объекты, ключи, связи «совещание → транскрипт → поручения → документы». Контрольные данные совпадают                        |
| **5. Подмена обнаруживается**                   | Изменить байт, обрезать файл, переставить части, подставить чужой зашифрованный DEK или контекст                                                                                    | Ошибка целостности; повреждённый результат не публикуется как готовый протокол                                                                |
| **6. Ключевой сервис недоступен**               | Остановить Vault либо запретить KMS после очистки кешей                                                                                                                             | Новое расшифрование блокируется; нет перехода к открытому хранению или резервному статическому ключу                                          |
| **7. Нет постоянных AWS-ключей**                | Проверить код, образы, CI, конфигурацию и credential-файлы; дождаться обновления временных credentials                                                                              | Работа продолжается через обновлённую роль. При недоступности штатной идентичности статический обход отсутствует                              |
| **8. Нет забытых открытых копий**               | Обработать тестовую запись с уникальными маркерами, включая аварийное завершение; проверить временные каталоги, логи, очереди и backup                                              | Открытое содержимое находится только в заранее разрешённых местах; временные копии удаляются по политике                                      |
| **9. Закрытый профиль действительно автономен** | Отключить внешнюю сеть, выполнить холодный запуск и восстановление                                                                                                                  | Аутентификация, открытие Vault, обработка, выдача и восстановление работают без AWS и внешних AI-сервисов                                     |

Для потокового шифрования важно корректно трактовать тест подмены: библиотека может уже выдать ранее проверенные сегменты, прежде чем обнаружит повреждение следующего. Критерий — **не признать неполный или повреждённый результат успешным**, а не обещать отсутствие любого вывода до конца многогигабайтного файла. ([Google for Developers][6])

В протокол испытаний записывать версии компонентов, идентификаторы ключей, применённые политики, время отзыва и последнего успешного запроса, контрольные хеши, журналы отказов, фактические **RPO** — допустимую потерю данных — и **RTO** — время восстановления.

## 9. Сравнение для небольшого пилота

Ниже — моя оценка эксплуатационной сложности, а не тарифное сравнение.

| Вариант                                                          | Сложность                                                                                          | Пригодность                                                                                                                                      |
| ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Закрытый: Vault + Transit + потоковое шифрование**             | Средняя/высокая: самостоятельно поддерживать Vault, машинную идентичность, backup и восстановление | **Основной выбор при обязательной автономности**. Нужен ответственный за эксплуатацию; без Enterprise потребуется проверка интеграции библиотеки |
| **AWS: роли + KMS + Secrets Manager, только SSE/RDS encryption** | Ниже: меньше собственных критичных сервисов                                                        | Хорошая базовая защита носителей, но **не выполняет буквальное требование о зашифрованном скачанном файле**                                      |
| **AWS: тот же набор + AWS Encryption SDK**                       | Средняя: дополнительный прикладной слой, но без собственного сервера ключей                        | **Рекомендованный AWS-профиль для сформулированных требований**                                                                                  |
| **Vault поверх AWS KMS/STS/Secrets Manager**                     | Наибольшая: две системы полномочий и жизненного цикла                                              | Оправдан при существующем корпоративном Vault; для нового малого пилота обычно избыточен                                                         |

**Практическое решение:** в закрытом контуре начать с изолированного Vault, отдельных ключей оригиналов и производных материалов, проверенной библиотеки шифрования и восстановления на чистых машинах. В AWS — использовать штатные роли, KMS, Secrets Manager и AWS Encryption SDK, без постоянных access keys и без лишнего Vault.

**Допускать реальные совещания стоит после четырёх доказанных результатов: шифротекст без ключей не раскрывается; ротация не ломает историю; отзыв блокирует последующие обращения; backup восстанавливается без исходной инфраструктуры.**
